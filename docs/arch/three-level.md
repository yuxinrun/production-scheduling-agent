# 三级智能体：C / M / A

先给结论，因为它决定了后面所有的设计：

> **三级不是为了「多智能体协作很酷」，是为了让权限不对称。**
> 排产系统里，越往下越了解局部、越往上越有写权限。
> 一个扁平的多智能体系统，要么权限给大了（出事），要么给小了（没用）。

LISA 的命名是「原子级 / 分子级 / 化合物级」（A / M / C）。这个名字有点化学课，
但它的实际含义很好记：**一道工序 / 一条链 / 全厂**。

## 二、14（或 16）个智能体逐个是谁

| 编号 | 名字 | 层级 | 权限 | 触发方式 | 失败长什么样 |
| --- | --- | --- | --- | --- | --- |
| C-01 | 全厂智能排产总控 | C | 写基线（须终审签名） | 定时（夜间全量重排 1~2h）+ 人工发起 | 全厂停摆；这层不允许「悄悄给出一个怪计划」 |
| C-02 | 跨厂产能协同 | C | 协同方案（双方调度长签名） | 状态机：需求发布→产能应答→方案协商→确认锁定，≤2h SLA | 对方厂拿到脱敏不当的数据；或协商超时无人知 |
| M-01 | 机加—热表链式协调 | M | 只读 + 编排建议 | 转序事件 | 热表炉等着机加的件，机加不知道炉子的时窗 |
| M-02 | 装配—试车联动 | M | 只读 + 编排建议 | 装配完工事件 | 部装干完了不知道台架哪天有空（现场原话） |
| M-03 | 齐套检查 | M | **不齐套硬阻断** | 三时点（排产前/排产后/开工前） | 开工才发现缺件——这层是唯一能挡住现场的闸门 |
| M-04 | 变更影响面评估 | M | 只读 + A/B 方案，**15min 未审自动升级** | 扰动事件（插单/故障/ECN） | 评估超时→人工凭经验拍→系统失去公信力 |
| M-05 | 锻造—钣金外协协调 | M | 只读 + 替代产能匹配（须审批） | 外协 ETA 更新 | 外协黑箱，回来晚了才知道 |
| M-06\* | 特殊过程联动 | M | **违规硬阻断，不可人工放行** | 检测窗口/有效期衰减 | 钛合金焊接件放了 21 天还往下走 |
| A-00\* | 数据点检与产能核算 | A | **只读** | 定时 + 入库时 | 门禁形同虚设，脏数据进排产链路 |
| A-01 | 锻造排产 | A | 只读建议 | 被 M/C 调用 | 组批合炉不合理，一炉只装半炉件 |
| A-02 | 机加工排产 | A | 只读建议 | 被调用 | 换型时间当成 0，一天多排 3 次换型 |
| A-03 | 表面热处理排产 | A | 只读建议 | 炉次事件 | 满炉率低 + 炉温均匀性不合格批次 |
| A-04 | 钣金焊接排产 | A | 只读建议 | 被调用 | 探伤返工回路没建模，计划永远乐观 |
| A-05 | 装配排产（部装/总装） | A | 只读建议 | 被调用 | 无限产能排出来的计划，落地即逾期 |
| A-06 | 试车排产 | A | 只读建议 | 台架日历 | 日计划达成率 50%（现场实测） |
| A-07 | 大修排产（MRO） | A | 只读建议 | 排故单 | 纸质排故单不在系统里，工时高度不确定 |

\* = A-00 在智能体定义文档里标注为「新增」，M-06 只出现在技术栈方案里。难度评估表（下一节）只有 14 行——它没算 A-00。

::: tip 这张表里最值得抄的一条
**「失败长什么样」这一列必须写。** 三级体系的设计工作，80% 就在这列里：
一个智能体的**边界**不由它的功能定义，而由它的失败模式定义。
你在设计评审时如果能说出「M-04 失败时会在 15 分钟自动升级到厂长」，
那这个设计就是完整的；如果只能说「M-04 会做影响面评估」，那还差得远。
:::

### 理由 1：故障半径

A 级出错，影响一个工序域；M 级出错，影响一条链；C 级出错，全厂计划作废。
**层级就是把故障半径写进架构。** 权限不对称之后，你可以对 A 级采取激进策略
（快速迭代、频繁上线），因为它的爆炸半径小；对 C 级就必须保守（双人复核、灰度、回滚基线）。
**如果你的系统里所有模块必须用同一种谨慎程度发布，说明你没有分层。**

### 理由 2：责任归属（军工场景的决定性理由）

出了事故要回答「谁决定的」。三级 + 审批链给了一个**可回答**的结构：

| 问题 | 答案 |
| --- | --- |
| 这个候选方案是谁生成的 | A-02，第 N 次调用，输入快照在审计里 |
| 为什么选 A 不选 B | 调度员张某某，电子签名，时间戳，理由字段 |
| 谁批准写入 MES | 室主任 / 生产指挥部（按工序域分派），终审记录 |
| 系统有没有自己做决定 | **没有**：A 只出建议，M 无权写，C 写基线必经签名 |

「AI 自己改了计划」在军工项目里不是技术问题，是**合同问题**。层级权限模型是它唯一的答辩材料。

### 理由 3：审批结构必须和组织结构同构

这一条最被工程师低估。**智能体的层级划分如果和现场的审批层级不一致，
审批人就看不懂自己在批什么**，于是要么乱批（失去护栏），要么不批（采纳率崩盘）。

LISA 的对应关系几乎是一对一的：

```text
A 级  ↔ 工段计划员 / 班组长的日常判断
M 级  ↔ 跨车间协调员（现场真实存在的角色，天天在打电话）
C 级  ↔ 计划科 / 生产指挥部的周计划与月计划
终审  ↔ 装试修由生产指挥部终审，其余室主任终审，超时升厂长
```

::: warning 先画组织图，再画智能体图
具体做法：**把现场的会签单、审批流、升级规则原文抄下来，再决定有几个智能体。**
如果某一级智能体在组织里没有对应角色，它大概不该存在——
或者它存在，但它的输出一定找不到人认领。
:::

## 四、层级之间的三个契约

不越权不是靠自觉，是靠三条可执行的契约。

| 契约 | 内容 | 落在哪 |
| --- | --- | --- |
| **调用方向** | 只允许 `C → M → A` 发起、`A → M → C` 回报。同级之间不直连，通过事件总线 | ABAC 策略：`caller.level ≤ callee.level + 1`，越权拦截 100% |
| **返回类型** | A 级返回的永远是**三方案 + 违约清单**，不是一个答案。M 级返回**协调后的可行域**，不重排 A 的内部顺序 | 接口 Schema 强约束，`plans: [A,B,C]` 是必填数组 |
| **时限与升级** | M-04 ≤15min、C-01 夜间全量 1~2h、C-02 协商 ≤2h、局部重排 ≤30min。超时不是失败，是**触发升级** | 状态机 + 定时器，升级动作本身进审计 |

**第二条是三级体系里最容易被偷懒实现的一条。** 把 A 级的返回从「三方案」压成「一个最优」，
等于把选择权从人手里夺走——然后你会发现采纳率上不去，
而团队以为是算法不够好。（真实的因果在 [采纳率是个组织问题](/build/adoption)。）

## 五、层级怎么分才不虚胖：什么时候别用三级

| 场景 | 建议 |
| --- | --- |
| 单工段、<200 工件、一条主要工艺路线 | **一个 A 级 + 一个 C 级就够**。三级是组织复杂度到了一定规模的产物，不是标配 |
| 跨 3 个以上工序域，且有真实的跨部门协调员岗位 | 三级齐全，M 级按「链」而不是按「部门」切 |
| 有外协 / 跨厂 | C-02 必须有，而且它是整个系统里最容易谈不下来的一个（密级 + SLA + 多方签署） |
| 计划口径本身还没定 | **先别建 C 级**。C 级要求「全厂一个口径」，口径没定时建它，你会把三个部门的分歧固化成代码 |

::: tip M 级该按「链」切，不按「部门」切
看 LISA 的 M 级命名：机加—热表、装配—试车、锻造—钣金外协。
每一条都是**工艺上真实耦合的两道工序**，而不是「生产部」「装配部」。
按部门切会得到一堆互相等通知的智能体；按耦合链切，每个 M 级都消灭一类真实的现场争吵。
:::

## 六、建设顺序：最聪明的那个要最后建

14 个智能体的**建设顺序**和它们的**难度评分**高度相关。技术栈方案里的难度是五维打分
（数据就绪 / 规则就绪 / 系统集成 / 组织协同 / 场景复杂度，各 1~5 分）后加权：

| 智能体 | 现状综合难度 | 叠加场景与 KPI 后 | 分档 |
| --- | --- | --- | --- |
| C-01 全厂总控 | 3.8 | **4.4** | 最高 |
| A-04 钣金焊接 | 3.4 | 4.0 | 高 |
| A-05 装配 | 3.2 | 4.0 | 高 |
| A-07 大修 | 2.8 | 4.0 | 高 |
| M-04 变更影响面评估 | 3.4 | 4.0 | 高 |
| C-02 跨厂协同 | 3.2 | 4.0 | 高 |
| A-03 表面热处理 | 2.8 | 3.6 | 高 |
| M-01 机加—热表链式 | 3.0 | 3.6 | 高 |
| M-05 锻造—钣金外协 | 2.6 | 3.6 | 高 |
| A-06 试车 | 3.2 | 3.6 | 高 |
| A-02 机加工 | 3.4 | — | 中高 |
| M-02 装配—试车联动 | 3.2 | — | 中高 |
| A-01 锻造 | 3.0 | — | 中 |
| M-03 齐套检查 | 3.0 | — | 中 |

三个读法：

1. **C-01 全厂总控最难，而且难在「依赖全部下级就绪」**——它不是最聪明的模块，是最晚的模块。
   项目里把它放在第一期做 Demo，等于在数据门禁连 70 都没过的地基上浇顶层。
2. **A 级里最难的是钣金焊接（4.0）**，因为它同时踩中三个不确定源：
   探伤合格率 60% 的返工回路、20 天有效期的特殊过程、外协黑箱。
   「难度」不是算法难度，是**不确定性密度**。这条在 [不确定性那一页](/problem/uncertainty) 有对应的建模办法。
3. **齐套检查 M-03 反而只有 3.0 分**——因为它的规则可结构化程度高，
   只是「9 要素归口待确认」。这说明：**M 级的难度是组织和数据问题，不是算法问题。**
   把 M-03 做不出来归因于「算法不行」，是这个项目里最贵的一次误判。

::: details 顺带一个真实的口径瑕疵
这份评分表自己的「难度分档」写的是：`≥4.0 高难度（5 个）`。
但按表中「上调后」的值数一下，≥4.0 的其实是 **6 个**；而 3.6 的四行被标成「高」，
按分档定义应属「中高（3.4~3.9）」。
这不是挑刺：**你的交付物里会出现这种不一致，因为分数是两次评审分别填的。**
应对办法不是骂回去，是在你的实现里**只使用「分档」而不是「分数」**——
分档直接决定谁主导开发（≥4.0 咨询方主导 + 客户深度配合，≤3.3 客户承担更多），
分数只用于排序。口径能对齐的地方只有分档。
:::

## 七、四种反模式（每种我都见过人认真做过）

| 反模式 | 长什么样 | 为什么崩 |
| --- | --- | --- |
| **智能体讨论群** | 五个 LLM 在群里对话，谁都能发言、谁都能改 | 没有层级就没有终止条件；结果取决于谁最后一个说话；无法审计「谁决定的」 |
| **A 级能写库** | 「工段自治嘛，让 A-02 直接回写 MES」 | 故障半径从「一个域」变成「全厂」，因为你无法预测别的域看到什么 |
| **M 级重算全局** | M-01 在协调机加/热表时，把全厂计划重排一遍 | 局部协调变成全局优化，时限从 15 分钟变成 1 小时，M-04 的 KPI 直接爆 |
| **C 级提前建** | 一期就做全厂总控出甘特图 | 它需要全部下级 + 全厂统一口径；建出来的是一张**没人认的图** |
