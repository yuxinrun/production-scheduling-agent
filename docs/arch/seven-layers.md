# 七层底座：排产 Agent 的责任边界图

「七层」听起来像 PPT 词汇。但你在现场待过两周就会明白：
**这七层不是架构师的审美，是七种不同的崩法。** 每一层存在，是因为有一个具体的事故类别只在那里发生，
并且只能在**那里**拦住。

本页按 [LISA 案例](/case/background) 主设计文档的 L0~L6 展开。
技术选型来自该项目的技术栈方案，其中「56 项能力点检」那一节是真实交付材料里的数字。

一句话总结每层的设计动机：

```text
L0  数据不合格，后面全错           → 所以门禁在最底下，不在中间
L1  取数口径必须只有一个来源        → 所以 MCP 只读优先、写权限单点
L2  LLM 会想跳过流程              → 所以流程写成显式状态机，不是 prompt
L3  LLM 会算错数                  → 所以数值一律不由 LLM 产出
L4  「齐套」有三种定义             → 所以本体是单一语义源
L5  系统会假装自己很行            → 所以影子模式和分歧采集是独立一层
L6  写错一次就是一次事故          → 所以写入是物理边界，不是配置项
```

::: warning 七层不是微服务划分表
现场最常见的误用：拿这张图去画服务拆分，于是得到七个服务、六次网络跳转、和一个
谁也复现不了的分布式 bug。

正确的关系是：**层 = 责任边界 + 依赖方向；服务 = 部署单位。**
一个服务可以横跨两层（比如 Java 的 MCP Server 同时实现 L1 接入和 L6 的脱敏），
一层也可以由三个服务共同实现（L3 的求解器 + 规则引擎 + SHACL 校验）。
**唯一不能破的是依赖方向**：L3 不许 import L2 的东西，L0 不许知道「排产」是什么。
:::

## 二、L0 数据基座：为什么门禁在最底下

排产系统 60% 的工程量在这里（[那一页](/build/data-first)）。L0 的四件事：

| 事项 | 具体要求 | 不做会怎样 |
| --- | --- | --- |
| **五维点检** | 完整性 / 及时性 / 一致性 / 准确性 / 唯一性，各维 ≥90% | 排出来的计划里，一半工序挂在「不存在的设备」上 |
| **编码映射** | 图号 ↔ 物料号 ↔ 工序号的双向索引，唯一可查 | 同一个零件在三个系统里是三个 ID，齐套检查永远算不对 |
| **版本有效性** | 工艺路线/图纸的生效区间，历史工单挂历史版本 | 用今天的工艺路线排三个月前的活，工时差 3 倍 |
| **溯源字段** | 每条数据带来源、时间、置信度；置信度 <0.7 强制复核 | 出问题时无人能回答「这条数据是谁的、什么时候的」 |

**关键设计**：L0 的门禁不是「报警」，是**阻断**。数据未达标不得进入排产链路，
并自动生成整改单。这一条在 LISA 里是硬约束（点检规则 R002）。

为什么必须是阻断？因为排产计划的产出物是要**下发到车间执行**的。
一个基于缺数据的计划，代价不是「计划不准」，而是**工人站在设备前等 4 小时**。
现场对系统的信任，是用这种代价换来的——一次就够。

## 三、L1 感知接入：只读工具面 + 事件总线

这一页详细讲 [MCP 接入层](/arch/mcp)。在七层图里只要记住三件事：

1. **智能体不碰数据库。** 它只看到「业务工具」，看不到表。这不是安全洁癖，是
   口径统一：一个「齐套率」在四个系统里有四种算法，让智能体自己拼必然拼错。
2. **读写分离到物理层面。** 本期 24 个工具里只有 1 个是写（`write_aps_plan`），
   它有独立的账号、独立的熔断策略。
3. **事件总线独立。** 插单、故障、缺料、军检提交这些扰动是**触发重排的唯一可靠通道**。
   「客户要变更评估 ≤15 分钟」这个 KPI，前提事件不丢不重（该项目要求投递可靠性 ≥99.99%）。
   轮询做不到，也没有审计。

## 四、L2 编排层：流程写成状态机，不写成 prompt

三级智能体（[那一页](/arch/three-level)）+ 五大模块（[那一页](/arch/five-modules)）住在这里。
七层视角只关心一个决策：

**为什么是显式状态机（LangGraph 那类），而不是「给 LLM 一段流程描述」？**

| | prompt 里的流程 | 代码里的状态机 |
| --- | --- | --- |
| 可追溯 | 只有对话历史 | 每个节点、每条边、每次跳转都有记录 |
| 可恢复 | 重跑，可能重复写库 | 检查点断点续跑 |
| 人工中断 | 「请等待确认」——LLM 会自己替你做决定 | 显式的 interrupt，流程真的停在那 |
| 越权控制 | 靠提示词求它别调 | 边不存在，调不到 |
| 军工验收 | **不给过** | 能演示 |

军工项目里「可追溯」是硬指标（审计覆盖率 100%）。
把流程放在 prompt 里，等于把审计链的完整性交给一个非确定性函数。

## 五、L3 能力组件：唯一会算数的那层

`求解器 + 规则引擎 + SHACL + 小模型 + 算法库`。这一层的**核心纪律只有一条**：

> **任何数值结论必须由这层产出，且必须由这层校验。LLM 输出的数值在呈现给用户之前，
> 要回到数据底座或规则引擎核一遍。**

这条纪律在 LISA 里被写成一条硬约束（数值类结论核验覆盖率 100%），原因很直接：
LLM 幻觉出来的不是一个数字，是一个**看起来合理的数字**——而车间里没人有时间验证合理性。

「数学上最优、业务上违法」是这一层的第二类事故。所以求解结果出门前还要过
SHACL 硬约束 + 规则引擎双校验。这两个校验是**独立的实现**，不是同一个函数的两次调用。
细节在 [写保护与降级链](/arch/guardrail)。

小模型（工时预测、满炉率、返工概率、外协 ETA）也住在这层，
以独立服务暴露。它们的定位是**给约束和参数提供更可信的取值**，不是替代求解器。
详见 [学习与大模型能做到哪步](/problem/learning)。

## 六、L4 数据与知识：本体是单一语义源

「本体 + 图谱 + 向量」三件套，缺一个都会漏：

| 组件 | 干什么 | 只有它时会漏什么 |
| --- | --- | --- |
| 本体（OWL 2 DL + Jena） | 概念、属性、公理；**约束的可校验表达** | 只有本体没有向量 → 规则召回靠人肉 |
| 图谱（Neo4j） | 关系推理、变更涟漪双向推演 | 只有图谱没有 SHACL → 推得出但拦不住 |
| 向量（Milvus + 嵌入） | 语义召回：68 条规则、840 个案例、600 条经验 | 只有 RAG → **约束不可校验**，LLM 会召回一段相似的话而不是一个可执行的规则 |

排产领域的 7 个核心类：`Order / Part / Operation / Resource / Constraint / Disturbance / Plan`。
为什么恰好是这七个，以及 `Disturbance` 为什么必须是一等公民（而不是 `Plan` 的一个字段），
见 [本体与 SHACL 护栏](/arch/ontology)。

## 七、L5 评测治理：唯一会说真话的一层

这一层最容易被砍掉，且砍掉的项目**没有一个活过第二年**。它有三件产出物：

- **四级指标**：L0 基座健康 / L1 价值流（WIP、MLT、OTD、FPY）/ L2 排产质量（采纳率、达成率）/ L3 过程（响应时长、违规数）。见 [案例 KPI](/case/kpi)。
- **影子模式**：系统排一版但不执行，与人工版并行跑，事后对比。这是唯一能在**不上生产**的前提下
  拿到可信效果数据的方法。
- **T+1 偏差回校**：实绩回传后，把「计划 vs 实际」的偏差回流给数据层和参数
  （工时、换型、良率），下一轮才准。

::: tip L5 为什么不能塞进 L2
塞进 L2 的话，评测逻辑和被评测的决策逻辑由同一个团队、同一份 prompt、同一次上线管理。
那不是评测，是自评。**独立成层的意思是：L5 有权说 L2 变差了，并且它的报告不需要 L2 同意。**
:::

## 八、L6 安全：四条硬线

| 硬线 | 数值 | 落在哪 |
| --- | --- | --- |
| 未审批写入拦截率 | 100% | 写入熔断网关（独立服务，不是求解器的一个开关） |
| 越权访问拦截率 | 100% | ABAC 策略执行点，全覆盖，包括智能体之间的调用 |
| 审计覆盖率 | 100% | 模型调用 / 工具调用 / 审批 / 写入四类事件，统一格式、防篡改 |
| 数据不出内网 | — | 私有化 + 脱敏不可逆 + 密级管控；跨网摆渡须审批联动 |

这四条**不是功能，是验收条件**。它们和「排得好不好」无关，但决定这个项目能不能签验收单。
细节见 [写保护、熔断与降级链](/arch/guardrail) 与 [审计链](/arch/audit)。

10 项「不满足」的分布（同一份材料）：

| 不满足项 | 数量 | 属于哪一层 |
| --- | --- | --- |
| 运筹求解：LP / MIP / 启发式 / 增量热启动 / 数值稳定性 | **5** | L3 |
| 本体建模 / SHACL 校验 / 图谱推理 | **3** | L4 |
| 消息队列（事件可靠性） | **1** | L1 |
| DAG 分析组件 | **1** | L2 |

**把这张表倒过来读，就是排产 Agent 的建设重点：**

```text
平台厂商给你的 21 项满足，基本都在「对话、表单、工作流、界面」这些通用能力上。
它不满足的 10 项，全部落在 L1 / L3 / L4 ——
也就是「数据可靠进来」「算得对」「语义说得清」这三件事。
```

**这不是巧合，是结构性事实。** 通用智能体平台的价值在 L2 和 L5 的通用部分；
而排产系统的价值**恰恰全在厂商不给的那三层**。换句话说：
如果你买一个平台就能做完排产，那这个排产系统也就不值得做了。

::: tip 但反过来：L2 也别急着自研
点检清单里 L2（编排/状态机/多级体系）只有一项不满足。
如果你的团队不强，**L2 用平台、L1/L3/L4 自建**是完全成立的路线（LISA 的材料里就并列给了
「平台底座 + 外挂」和「全栈自研」两条路线，并明确建议：**数据层 L0/L4 与能力层 L3 的设计
在两条路线里完全一致，先固化数据与规则，再定编排底座**）。
:::

## 十、建设顺序 vs 演示顺序（一句实话）

| | 顺序 | 为什么 |
| --- | --- | --- |
| **该按的顺序** | L0 → L1 → L4 → L3 → L2 → L6 → L5 | 数据和语义不固化，上面全是沙子 |
| **实际会被要求的顺序** | L2 → L5 的看板 → 回头补 L0 | 因为 L2 能演示，L0 只能开会 |

**这两者的差，就是排产项目的平均延期时长。** 你能做的最有价值的一件事，
是在第一次演示时就把 L0 的门禁数值一起放上去——
调研里这家厂的**数据质量五维自评不到 70 分，而门禁线是 90**（[37 项问题清单](/case/pain) 里的 A 类）。
把 L0 变成演示的一部分，是**唯一**能在不给工期的情况下补工期的办法：
一旦「今天数据只有 68 分」出现在大屏幕上，补齐数据的工期就不再需要你去争取了。
