# 审计链：让决策可回放

调研报告把车间现状写成三句话：**规则黑盒不可解释**、**执行数据断点**、**决策无留痕**。
《技术能力点检清单 V1.0》#49 给这三句话准备了一行：

> **49 全链路审计留痕（操作/调用/审批/数据版本审计）**
> Harness 要求：审计日志防篡改，密级标识与留痕要求符合 ZD-09
> 验收基准：**审计覆盖率 100%**（含模型调用 / 工具调用 / 审批 / 写入），留存期限达标
> P0 · 必须 · OpenTrek 满足状态：**部分满足**（调用日志与观测可用，防篡改与密级留痕需按保密要求加固）

军工四性里「可追溯」这一条不是给运维看的，是给**三年后的责任认定**看的——
同一份调研的 F 类问题写得很直白：排产决策责任认定缺失、AI 失误接受度低。
所以这一页不接受「我们打了日志」这种回答。三个问题，一个一个量：

1. 记什么？（四类事件、一种格式）
2. 记下来之后，怎么证明它没被动过？（哈希链 + 外部锚点，实测五种攻击）
3. 怎么证明它还能重算出**同一版方案**？（回放的五个输入）

## 一、记什么：四类事件、一种格式

#49 括号里点了四类：**模型调用、工具调用、审批、写入**。排产还有两件事必须进同一条链：
**求解**（因为方案是它出的）和**方案调整**（因为 #53 要归因）。
[五大模块](/arch/five-modules) 那条 `parent → digest` 骨架说的就是同一件事的生产版本。

一条记录里，下面这些字段少一个，后面就有一类问题答不出来：

| 字段 | 谁写 | 少它之后答不出的问题 |
| :-- | :-- | :-- |
| `seq` | 入链器 | 「审批发生在写入之前还是之后」——时间戳答不了（第六节实测） |
| `ts` | 入链器 | 业务时刻。对齐 MES 报工、ERP 到货靠它，不靠它定序 |
| `actor` | 调用方身份 | 「这是模型干的还是人干的」。ABAC 的主体标识，#48 |
| `kind` | 事件类型 | 覆盖率的分母。四类不齐，#49 就只是一句形容词 |
| `tool` + `inputs_digest` | MCP 层 | 「当时读到的到底是什么数据」。数据版本审计就落在这个摘要上 |
| `planBatchId` | 方案 | 幂等键、票据绑定对象、明细归属锚，三个机制共用它（[写保护](/arch/guardrail)） |
| `code_version` + `seed` | 编排层 | 「重跑一次还是这个方案吗」。没有这两项，回放无从谈起 |
| `budget` + `ev_used` | 求解器 | 第五节的核心：回放要按 `ev_used` 截断，不是按时间 |
| `bound` + `makespan` | 求解器 | 「这一版比最优差多少」。[下界与间隙](/problem/bounds) 那一页的数要有出处 |
| `degraded` | 降级链 | 「这份方案是 D 几的产物」。采纳率的分母要剔除它 |
| `ticket` | 审批 | 一次性票据的消费记录。#21 那句「熔断日志完整」 |
| `attribution` | 模型 | #53：方案调整 100% 附带归因说明 |
| `prev` + `hash` | 入链器 | 本页第二节的对象 |

::: tip 一种格式，不要四套日志
常见做法是模型调用进 LangSmith、工具调用进网关、审批进工作流引擎、写入进业务表。
于是「审计覆盖率」要跨四个系统算，跨系统的对账没人算，#49 就永远停在「部分满足」。
同一条 append-only 链上，`kind` 一个字段就分开了四类；对账是同表 count，不是一堆导出脚本。
:::

## 二、哈希链实测：五种攻击 × 三种防线

`audit_chain.py` 把上面那张表变成一条 12 个事件的链，然后扮演攻击者。
下面是本机真实 stdout（Python 3.12，纯标准库，逐行照贴）：

```text
[1] 一条 12 事件的决策链（#49 点名的四类事件都在）
    建链耗时 0.329 ms，链尾哈希 b7d69f22673f5d5f…，verify → 失配 0 条
    四类事件条数 = {'model_call': 2, 'tool_call': 3, 'approval': 2, 'write': 2}
    第 1 条 solve 带 degraded=D1、bound=139、ev=20000。降级标记进链不是为了好看：
    #41 说「降级演练通过」，演练的证据只能是这样一条带界带计数器的记录。
    外部锚点（HMAC-SHA256 over 链尾+条数+链头）= 4f6ff8bfc15c9e39…
```

然后是五种攻击：

```text
[2] 五种攻击 × 三种防线。√ = 检出，× = 蒙混过关
  A1 改一条：第 8 条 write 的 writtenDetailRows 105 → 10500（哈希没动）
      内部自洽校验 → 失配从第 8 条起，共 1 条：√
      序号连续性检查 → 无缺口：×
      外部锚点比对   → 锚点仍然吻合：×
      结论：这条攻击会被发现
  A2 改一条 + 从第 8 条起重算后面所有哈希（等价于整条重算，前 7 条结果不变）
      内部自洽校验 → 全部通过（链看起来是好的）：×
      序号连续性检查 → 无缺口：×
      外部锚点比对   → 链尾/条数与锚点不符：√
      结论：这条攻击会被发现
  A3 删一条：把第 7 条 approval 整条删掉，只重算第 8 条往后的 prev/hash（seq 不动）
      内部自洽校验 → 全部通过（链看起来是好的）：×
      序号连续性检查 → 缺口 5 处：√
      外部锚点比对   → 链尾/条数与锚点不符：√
      结论：这条攻击会被发现
  A4 = A3，但攻击者连 seq 一起重排成 1..11（上面那次重算多加一个参数而已）
      内部自洽校验 → 全部通过（链看起来是好的）：×
      序号连续性检查 → 无缺口：×
      外部锚点比对   → 链尾/条数与锚点不符：√
      结论：这条攻击会被发现
  A5 = A4，而且锚点文件也在他能写的盘上、密钥也在同一份 .env 里
      外部锚点比对 → 原锚点失配 √，但他自己签了一个新锚点 ed308d9405704bfa…，之后校验通过：×
      ⇒ 这就是 E5 要「一个只追加、LISA 写不了的落点 + 密钥单独交付」的全部理由。
        锚点跟链放同一块可写盘 = 没有锚点；没有密钥时锚定一律被拒（ANCHOR_SECRET_MISSING），
        宁可没锚点，也不写一个谁都能重算的假锚点。拷贝周期就是攻击窗口（清单建议 ≤ 一个工作日）。

  A1~A4 四种攻击的检出数：内部自洽校验 1/4、序号连续性 1/4、外部锚点 3/4，三条防线合起来 4/4
  没有任何一条单独防线能到 4/4——A1（改一条不动哈希）只有内部校验看得见，
  因为锚点签的是链尾指纹，中间某条被改而链尾没变时，锚点完全无感。
  这就是《投产配置清单》E5 那句「两条链互为反证」的字面意思：不是冗余，是覆盖面。
  A5（拿到密钥 + 能写锚点）任何内部机制都看不见，只能靠「LISA 写不了的落点」这个物理前提。
```

::: danger 「中间删一条就断链」——这句只在攻击者不重算时成立
[五大模块](/arch/five-modules) 那页写「审计链一旦成型，中间删一条就断链」。
实测结论要精确一点：A3 和 A4 两种删法，链的**内部自洽校验全部通过**（失配 0 条），
因为 prev/hash 是重算出来的，重算之后每一条都自证清白。
哈希链防的是「改完不管哈希」的那种攻击，也就是 A1。防不住「会算 SHA-256」的攻击。
真要防删，靠的是三样东西：**序号连续性、外部锚点、以及一个只有 INSERT 权限的数据库账号**。
:::

A5 是这一节的落点。攻击者如果同时满足「能写锚点文件」和「能拿到 HMAC 密钥」，
那么他签的新锚点和他的新链完全吻合，**任何软件机制都看不见**。所以 E5 原文要的是两件事：

1. 一个**只追加、LISA 写不了**的落点（WORM、日志集中平台、另一台主机的只追加挂载）；
2. 密钥走环境变量单独交付，**值永不落库、永不进日志**，变量名才进配置。

清单里还有两个细节值得抄：没有密钥时锚定一律被拒（`ANCHOR_SECRET_MISSING`）——
宁可没有锚点，也不写一个谁都能重算的假锚点；以及「拷贝周期就是攻击者可自由操作的窗口，建议不超过一个工作日」。
这句话的意思是：**锚点拷贝之间的每一分钟，都是 A5 的攻击窗口**。这是一个排班问题，不是加密问题。

## 三、审计覆盖率 100%：#49 后半句的可实现版本

覆盖率这一半才是 #49 真正难的地方，因为哈希链对它一点帮助都没有：

```text
[3] #49：审计覆盖率 100%（含模型调用/工具调用/审批/写入）
    只在「调了工具」和「写了 MES」时打日志，模型调用与审批不打：
    链长 8 条，内部自洽校验 → 失配 0 条；覆盖率 = 2/4
    序号连续性 → 缺口 0 处（1..8 连续，也查不出来）
    ⇒ 哈希链对「少记了两类事件」完全无感。防篡改和防漏记是两个东西，
       #49 的验收基准里那半句「覆盖率 100%」不是哈希链能给的。
    可实现的版本只有两条，都得自己写：
      ① 覆盖率当闸门：四类不齐就不许关闭这段会话（拒绝收尾，不是事后统计）；
      ② 跟外部事实对账：链里 write 事件 2 条，
         MES 侧 dispatchNo 去重后必须同数。对不上就是漏记，跟哈希一点关系都没有。
```

**防篡改 = 记下来的东西没被改；防漏记 = 该记的都记了。** 两个是正交的。
可实现版本只有两条路，都得自己写：

| 做法 | 机制 | 失败时的行为 |
| :-- | :-- | :-- |
| 闸门 | 四类事件不齐，这段会话不许关闭 | 会话收尾被拒，报 `AUDIT_INCOMPLETE` |
| 对账 | 拿链里的条数去和外部事实比 | 差异进报表，超阈值就停写 |

对账的三组数（都是同一条链上的 `count`，不用跨系统）：

- 链里 `write` 事件条数 = MES 侧 `dispatchNo` 去重后的条数。链多 → 有写没落库；MES 多 → **有落库没审计**，后者才是要停写的那种。
- 链里 `approval` 条数 = 票据消费记录条数（[写保护](/arch/guardrail) 那张一次性票据）。多出来一个 `write` 而没有对应消费 → 就是 #21 要拦的那一类。
- 链里 `model_call` 条数 = 网关侧调用计数。#34 那个「调用成功率 ≥99.5%」的分母必须来自审计链，不然两个数各说各话。

::: warning 「审计写入失败就停写」是覆盖率唯一的兜底
[MCP 接入层](/arch/mcp) 的告警表最后一行写的是：审计写入失败 → 出现即告警 → **暂停写工具**。
多数系统反着做：审计失败打一条 warn，然后继续写，事后靠日志重建——而重建出来的东西不能当证据。
代价要想清楚：审计库抖动的直接后果是**车间当天不能下发方案**。所以审计要有独立的连接池、
本地盘缓冲（先落盘再异步上传，落盘失败才算失败）、和一个明确的停写阈值。
这是可用性设计，不是安全口号。
:::

## 四、归因说明：#53 的 100% 也是入链前的校验

#53「白盒化解释」的验收基准是 **方案调整 100% 附带归因说明**，调度员确认可用性 ≥90%。
同一批调整记录，两种写法差出来的数：

```text
[4] #53：方案调整 100% 附带归因说明 —— 同一批调整记录，两种实现
    10 条调整里 8 条没带归因（模型输出不完整，这是常态）
    实现①「先入链，报表里再统计覆盖率」：入链 10 条，归因覆盖率 20%，耗时 0.12 ms
       → 差口 80 个百分点，而且事后补救不了：链不许改，改了 verify 就红。
    实现②「缺归因就拒收，补齐才入链」：入链 10 条，拒收 8 次，归因覆盖率 100%，耗时 0.11 ms
    代价不在时间上（两次都是 0.1x ms），在 8 次拒收重提，和一条「归因必填」的 schema 约束。
    「100%」不是统计目标，是入链前的一个必填校验。#21 那句「熔断日志完整」同理。
```

但实现②有一个必须承认的坑：**拒收后回填的归因不是当时的归因。**
脚本里那句「由 focusNode 与机器负载差分回填」是事后算出来的合理理由，
模型当时**是不是因为这个理由**改的，没人知道。审计能证明的只有「这条调整有一个已核对的理由」，
不能证明「这是模型脑子里想的」。这两件事在设计评审时要分开讲，不然 #53 会变成给模型编故事的机会。

三条落地写法：

1. `attribution` 是**结构化字段**，不是自由文本。里面放本体 IRI + 规则号 + 数值证据
   （例如 `rule:R012 / machine:M2 / load:136`），自由文本不算合格。理由见
   [本体、图谱与 SHACL 护栏](/arch/ontology)：SHACL 能校验形状，校验不了一段话。
2. 生成侧强制：让模型在输出方案时就带 `attribution`，Schema 不过就重试
   （[五大模块](/arch/five-modules) 那张反模式表的处方），而不是入链前用规则回填。
3. 「调度员确认可用性 ≥90%」是第二道门，人读的。它验证的是这条归因**看得懂**，
   第一道门验证的是它**存在且可核**。两道门都过，#53 才算满足。

## 五、可回放：审计链的最后一公里

留痕的终点不是「能查到」，是**能重算**。重算不出来，日志就只是一堆字符串。
同一条 20×5 算例、同一颗种子、同一个随机起点，回放 60 次，只换停止规则：

```text
[5] 可回放：同一份输入 + 同一个种子，能不能重算出同一版方案？
    算例 = 20 工件 × 5 机器（本机现造，各机器负载 [81, 86, 88, 93, 97] → 平凡下界 LB = 97）
    起点 = 同一颗种子(7)的随机派工，邻域 = 机器序列相邻交换。回放 60 次
    按「评估次数 ≤ 300」停：60 次 → makespan 1 种取值 [222]，方案指纹 1 种，单次 55.6 ms
    收敛于 makespan 222（vs 下界 +129%），实际用掉 286 次评估，指纹 d6c6b3177fb748f6
    ⇒ 停止规则只依赖计数器的话，「可回放」是免费的：输入 + 代码版本 + 种子 + 预算 = 同一版方案。
    按「墙钟 ≤ 12 毫秒」停（#41 那个 15 秒熔断的缩影），空载 60 次 → makespan 2 种取值 [225, 226]，方案指纹 2 种，评估次数落在 54~57
    同样 12 毫秒，但本机另开 2 个满载线程（等价于隔壁那个请求在吃核）：40 次 → makespan 2 种取值 [225, 237]，评估次数落在 6~58
    ⇒ 墙钟截断把「本机此刻的负载」变成了决策的输入。空载和带负载跑出来的方案不是同一版，
       而日志里那句「耗时 12ms」完全无法告诉你少了哪几十次评估。
       熔断预算一旦进了决策路径，「回放」在数学上就没了：你只能重现当年那次决策的分布，
       重现不了它本身。所以审计要记的是 ev / bound / elapsed 三个数，回放时按 ev 截断，
       而不是按时间截断——否则 #49 那句「可追溯」只是个形容词。
    用链里记下的 ev=286 回放 → makespan 222，与那条 solve 记录的指纹一致 = True
```

三条结论：

1. **#29 的「质量损失 ≤5%」和 #41 的「15 秒熔断」在审计侧会再撞一次。**
   [求解编排](/arch/solver) 量到的是同一条轨迹上的互斥（15 秒停在 gap 10.3%，进 5% 要 22.8 秒）；
   本页量到的是：一旦墙钟进了决策路径，那一次决策就**不可重放**。
   两条 P0 要同时留，唯一的写法是「按 ev 截断回放 + 把 elapsed 当属性而不是预算」。
2. **审计要记 `ev_used / bound / elapsed` 三件套**，缺 `bound` 就答不了「当时知不知道自己差多远」，
   缺 `ev_used` 就回放了个别的方案。
3. 表里那一行 makespan 222、vs 下界 +129% **不是算法结论**——随机起点 + 单遍相邻交换在这个规模上很弱，
   质量口径请看 [启发式与元启发式](/problem/heuristic) 和 [求解编排](/arch/solver)。这一页只用它验证一致性。

## 六、时间：定序与留存

```text
[6] 时间：#49 要求留存期限达标，H7 要求客户给 NTP 源。先问时间戳能不能定序
    12 条事件按 0.5ms 间隔打戳，第 7 条起被 NTP 校时回拨 2ms：
    按时间戳排序后 6/12 条落在错误位置上（其中 approval 排到了它批的方案之后）
    ⇒ 能定序的只有 seq + prev。时间戳的作用是「对齐业务时刻」（几点几分下发的），
       不是「判定因果」。时钟源不可信时，先坏的是归因链而不是报表。
    顺带一句 #49 的「留存期限达标」：军工审计通常按年计，链不许改，
       但密钥要轮换 —— 轮换后老锚点必须留档，否则三年后的审计页会一片红。

一句话：SHA-256 链管「改」，序号管「删」，外部锚点管「整条重算」，
      对账 + 闸门管「漏记」，ev 计数管「回放」。五种机制，缺一个就有一类攻击免费。
```

投产配置清单 H7 只要客户提供一件事：**NTP 地址**。看起来像运维细节，实际是审计前提——
上面这 6 条错位里，最要命的一条是「审批排到它批准的那次写入之后」，
它在报表里的表现是「这次写入没有审批」。用日志时间做因果判断的系统，
一次校时就把自己的证据链弄坏了。

留存期限（#49 后半句 + H5）另有两只咬人的狗：

- **密钥要轮换**。轮换之后老锚点必须原样留档并记录用过的密钥版本号，
  否则三年后审计页打开是一片红——不是链被改了，是没人能证明它没被改。
- **备份恢复会重算链**。清单第 9 节写的恢复流程里明确有一步「重置序列 → 逐表核对行数 → **重算审计链**」。
  这条流程本身是对的（恢复出来的库要能自洽），但恢复后的链**只恢复了自洽性，没恢复可信性**：
  它对外部锚点的匹配要靠备份头部记录的「审计链头」和当时拷贝到 WORM 的那份锚点来反证。
  演练恢复的时候，验收项里必须有一条「锚点比对通过」，不然第 2 节的 A2 就等于被自己人做了一遍。

## 七、反模式：这一页的坑，一行一个

| 反模式 | 看起来 | 实际上 |
| :-- | :-- | :-- |
| 审计等于应用日志 | 什么都不缺 | grep 出来的字符串不能当证据；A1 一改就没人知道 |
| 只在写入时打点 | 覆盖率「100%」（写都记了） | #49 四类里只有两类，实测 2/4，哈希链全绿 |
| 锚点跟链放同一块盘 | 备份很方便 | A5 免费：他自己签一个新锚点 |
| 密钥写进配置文件提交 | 部署简单 | 值一旦进版本库，锚点等于公开签名 |
| 给运维一个「修复审计链」按钮 | 排障友好 | 那个按钮就是 A2/A4，全链此后不可用 |
| 用时间戳排序定因果 | 顺序看起来自然 | NTP 回拨 2ms 就有 6/12 条错位 |
| 应用账号有 UPDATE/DELETE 权限 | 方便改错数据 | 一条 grant 就能把「只追加」变成形容词 |
| 回放按 elapsed 截断 | 昨天还能回放 | 今天机器负载一变，同一条记录回放出另一个方案 |

## 小结

1. #49 是两个东西：**防篡改**（改不了）和**防漏记**（没少记）。哈希链只管前者，且只管前者的一半。
2. 实测四种攻击的检出数：内部自洽校验 1/4、序号连续性 1/4、外部锚点 3/4，**并集才 4/4**。
   「库内链 + 库外锚点，两条链互为反证」是覆盖面拼图，不是冗余。
3. A5（拿到密钥 + 能写锚点文件）没有软件解，只有物理前提：只追加、LISA 写不了的落点 + 密钥单独交付。
   拷贝周期就是攻击窗口。
4. 覆盖率的实现只有闸门 + 对账两条；「审计写入失败就停写」是唯一的兜底，代价是审计库抖动会冻住下发。
5. 「100%」在 #49、#53、#21 里都不是统计目标，是**入链前的必填校验**。差别是能不能事后补救：链不许改。
6. 可回放需要五个输入（实例摘要、代码版本、种子、ev 预算、指纹比对）。墙钟熔断使回放只剩分布，
   所以 `ev_used / bound / elapsed` 三件套必须一起记，回放按 `ev` 截断。
7. 时间戳对齐业务时刻，`seq + prev` 定序。NTP 回拨 2ms 就能让「审批」排到它批准的写入之后。
