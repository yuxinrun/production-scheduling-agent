# 本体、图谱与 SHACL 护栏

[五大模块](/arch/five-modules)第四节说，规划段的产出必须是一个「可校验对象」，护栏不过就不产出方案。
这句话藏着一个前提：**得先有人定义「校验什么」。**

本页就是那个定义。它在 LISA 交付材料里叫《本体结构构建方案细化》，272 行，
7 个核心类、24 个对象属性、16 个数据属性、14 条一致性校验规则（SHACL 化）、7 类关键工序的 4M 插拔组件矩阵、9 条数据到本体的映射规则。

> **本体不是文档化的类图，本体是能被机器拒绝你的那张表。**
> 如果你的「本体」只能用来画给新人看，那它是 ER 图，不是本体。
> 检验标准只有一条：有没有一段代码，因为某个实例不满足某个形状，**把方案拦下来过**。

建模遵循四层模型：**核心类—属性—关系—约束**，并与通识模板 T1~T5、核心专识 ZD-01~08 建立映射，

| 目标 | 靠什么 | 组件（选型清单原文） | 失败时长什么样 |
| --- | --- | --- | --- |
| 语义可查 | 本体 + 三元组存储 | OWL 2 DL/EL + Apache Jena / RDF4J（SPARQL） | 问「哪些工序受 HC-05 作用」要人肉翻 Excel |

| 约束可校 | 形状 + 校验报告 | SHACL（pySHACL / TopBraid） | 「数据未达标不得进入排产链路」这句话没人能执行 |

## 二、七个核心类，30 条 mandatory 断言

原文表 1 完整搬下来。「核心属性」那一列斜杠分隔的字段数，就是该类在 SHACL 里的 `sh:minCount` 数量。

| 类 | 中文 | 定义 | 核心属性 | 条数 | 关联通识/专识 |
| --- | --- | --- | --- | --- | --- |
| `Order` | 订单 | 客户下达的生产任务 | 订单号 / 产品 / 数量 / 交期 / 优先级 / 军品属性 | 6 | T1 概念；ZD-01 规则 |
| `Part` | 零件/产品 | 被加工对象及其 BOM 结构 | 图号 / 材质 / 批次 / 关重件标识 | 4 | T5 基础；ZD-02 路线 |
| `Operation` | 工序 | 工艺路线中的作业单元 | 工序号 / 工时 / 前后约束 / 外协标识 | 4 | T2 方法；ZD-03 参数 |
| `Resource` | 资源 | 设备/人员/工装/物料的抽象 | 能力矩阵 / 日历 / 状态 / 技能等级 | 4 | T3 约束；ZD-05/06 |
| `Constraint` | 约束 | 排产须满足的限制条件 | 约束类型 / 强度 / 作用域 / 违约代价 | 4 | T3 约束；ZD-01 规则 |
| `Disturbance` | 扰动 | 执行过程中的异常事件 | 类型 / 级别 / 发生时刻 / 影响范围 | 4 | T4 场景；ZD-07 案例 |
| `Plan` | 排产方案 | 工序—资源—时间的指派结果 | 版本 / 指标 / 冻结窗口 / 状态 | 4 | ZD-07 案例 |
| | | | | **30** | |

类层次三层分叉：

- `Resource` ↓ **设备、人员、工装、物料**
- `Constraint` ↓ **硬约束、软约束**
- `Disturbance` ↓ **设备、物料、人员、质量、订单** 五类扰动（对齐 T4 场景体系）

::: tip 30 这个数字要记住，它比「本体有多大」有用
「核心类必备属性非空」是 HC-01 的全部内容。**30 条 mandatory 断言就是最小可用数据集的定义。**
L0 那道「五维点检 ≥90%」的门禁，落到字段级其实就是这 30 个槽位的填充率。
超过 30 条就要警惕：门禁必达标不了，或者达标了但没人信。
:::

**这七个类的顺序不是随便排的**，它就是排产域的主链路：订单—产品—工艺—资源—约束—扰动—方案。
把它和[数学模型页](/problem/model)对着看，每个类都能落到模型元素上：

| 本体类 | 模型里的对应物 |
| --- | --- |
| `Operation` + 工时 | 工序 `O_jk`、加工时间 `p_jk` |
| `Resource` + 能力矩阵/日历 | 机器 `M_k`、可用窗口、`Σp_jk ≤ cap_k` |
| `Part` + `hasRoute` | 工艺路线、Job Shop 的工序序列 |
| `Constraint` 硬/软 | 硬约束可行域 / 目标函数里的惩罚项 |
| `Disturbance` | 重排触发事件、鲁棒性区制的扰动集 |
| `Plan` + `assignedTo` | 决策变量 `x_jkt`（三元指派物化后的样子） |

**类图没变，但它让模型有了「可写入的地方」。** 这就是本体在工程上的位置：不是学术装饰，是解到数据库之间的那层模具。

## 三、关系设计：24 个对象属性里有两个坑

原文 24 个对象属性（类间关系）+ 16 个数据属性（类内字段）。关键八条：

| 对象属性 | 定义域 → 值域 | 含义 | 基数 |
| --- | --- | --- | --- |
| `hasPart` | Order → Part | 订单包含零件 | 1:N |
| `hasRoute` / `hasOperation` | Part → Operation | 零件工艺路线 / 工序序列 | 1:N **有序** |
| `precedes` | Operation → Operation | 工序先后约束 | M:N **传递** |
| `requiresResource` | Operation → Resource | 工序资源需求（含可替代） | M:N |
| `assignedTo` | Plan → (Operation, Resource, Time) | 方案的**三元指派** | M:N |
| `constrainedBy` | Operation / Plan → Constraint | 受约束作用 | M:N |
| `triggeredBy` | Plan → Disturbance | 方案由扰动触发重排 | N:1 |
| `handledBy` | Disturbance → ZD-07 案例 | 扰动与历史处置案例关联 | M:N |

### 坑一：`assignedTo` 是三元关系，OWL 里没有三元关系

OWL 的对象属性**永远是二元的**（一个定义域、一个值域）。`Plan → (Operation, Resource, Time)` 这种三元组必须**物化**：
把「一次指派」本身变成一个节点（reification / N 元类，俗称 `PlanItem`），拆成三条二元边：

```text
PlanItem: pi-0417
  ├─ assignsOperation → OP2
  ├─ usesResource     → M1
  └─ atInterval       → [5, 9]
Plan --hasAssignment--> pi-0417
```

这是本体落地时第一个真正的建模决策，也是很多人第一次就把 RDF 换成属性图的原因——
**Neo4j 的关系可以带属性**，一次指派就是一条 `ASSIGNED_TO {start: 5, end: 9}` 边，不需要中间节点。

LISA 的实际组合是两个都用（Jena/RDF4J 做本体与 SPARQL，Neo4j 做图谱与多跳推演），
前提是本体和图谱**共用同一套 IRI/ID**，否则两边会各自漂移成两个真相。

### 坑二：`precedes` 声明成传递属性，环会被静默「推成自反」

这是本页最想让程序员带走的一条。工序先后关系声明为传递属性，逻辑上非常自然：
A 先于 B、B 先于 C，那 A 先于 C。

但如果 A→B→C→**A** 呢？

传递性 + 一个环，推出的结论是 **A 先于 A**。在 DL 语义里这**不是不一致**——
推理机不会报错，它只是安静地把 `precedes(A,A)` 加进事实集。你的查询全都还能跑。
真正出事是在排产那一刻：一个要求 `start_A ≥ finish_A` 的约束永远不可满足，求解器返回不可行，
而错误信息说的是「产能不足」，不是「工艺路线有个环」。

所以 HC-12「工序先后关系无环」必须**显式检测**。我把闭包跑出来了：

```text
HC-12 单独看：传递属性的闭包展开
  方案 A: OP1→+['OP2', 'OP3']   OP2→+['OP3']   OP3→+[]
  方案 C: OP1→+['OP1', 'OP2', 'OP3']   OP2→+['OP1', 'OP2', 'OP3']   OP3→+['OP1', 'OP2', 'OP3']
```

方案 C 的三个节点每个都在自己的可达集里——环检测的本质就是这一行判据：`n in closure(n)`。
不用拓扑排序也能查，但拓扑排序更省（$O(V+E)$，不用算全闭包）。生产环境用后者。

### 数据属性（16 条里的 8 条关键项）

| 数据属性 | 所属类 | 类型 | 说明 |
| --- | --- | --- | --- |
| `priorityScore` | Order | Decimal | 订单优先级分（B-01 评分卡计算） |
| `dueDateRigidity` | Order | Enum | 交期刚性：**硬 / 软 / 弹性** |
| `stdDuration` / `setupTime` | Operation | Duration | 标准工时 / 换型时间 |
| `capabilityMatrix` | Resource | Matrix | 设备—工序能力矩阵（ZD-05） |
| `skillLevel` | Resource(人) | Enum | 技能等级：初 / 中 / 高 / 专家 |
| `strength` / `scope` | Constraint | Enum / Set | 约束强度（硬/软）与作用域 |
| `severity` / `rippleScope` | Disturbance | Enum / Set | 扰动级别与涟漪影响范围 |
| `frozenWindow` | Plan | Interval | 冻结窗口（原文写 **T-24h**） |

::: warning `frozenWindow` 的 T-24h 和规则里的「周计划前 3 天冻结」不是同一个窗口
排产规则主线里冻结窗口是**周计划前 3 天**（周滚动 3 锁 1 下发 3 展望），本体属性这里写 T-24h。
一个 24 小时，一个 72 小时，差三倍。HC-08「排产指派时刻落在资源日历可用区间内」和冻结窗口检查是两套逻辑，
但**谁拦谁、以哪个为准**必须定死：这直接决定 [M-04 变更影响面评估](/arch/three-level)算出来的是「违规」还是「正常顺延」。
这类两处口径不一致的地方，本体方案里我至少找到这一处 + 下一节的 HC 编号一处，评审时都要拎出来。
:::

## 四、护栏是可执行代码，不是概念

`HC-01 概念完备性：核心类必备属性非空`——这句话的工程量在哪？在于你能不能把它写成一段真会拒绝东西的代码。
下面这段是本页自己写的最小实现（纯标准库），把 HC-01 / 03 / 08 / 12 / 14 五条落成可跑的校验，
然后拿四个方案实例过闸。脚本在 [`/snippets/ontology_guardrails.py`](/snippets/ontology_guardrails.py)。

```python
def validate(plan):
    v = []
    for cls in ("Order", "Plan"):                     # HC-01 必备属性非空
        for f in MANDATORY[cls]:
            if f not in plan[cls]:
                v.append(("HC-01", f"{cls}/{plan['Plan']['版本']}", f, "缺失"))
    for f, allowed in ENUM.items():                   # HC-03 枚举值域
        val = plan["Order"].get(f)
        if val is not None and val not in allowed:
            v.append(("HC-03", ..., f, f"{val} ∉ {sorted(allowed)}"))
    for op, res, s, e in plan["ops"]:                 # HC-08 落在资源日历可用区间
        if not available(res, s, e):
            v.append(("HC-08", op, f"{res}[{s},{e}]", "不在日历可用区间"))
    for n, rs in closure(plan["precedes"]).items():   # HC-12 先序关系无环
        if n in rs:
            v.append(("HC-12", n, "precedes+", f"{n} 可达自身（成环）"))
    # HC-14 数量守恒：交付 + 报废 + 报工未结 + 在制 = 订单，四项都不得为负
    ...
    return v
```

实跑输出（四个方案各埋一种违例，方案 A 是干净的）：

```text
7 个核心类的必备属性合计 = 30 条 mandatory 断言
资源日历 = [('M1', 0, 12), ('M1', 16, 24)]（12—16 为维护窗）

四个方案过护栏：SHACL 风格报告

方案 A  conforms = True
    （无违例，可以进入排产链路）

方案 B  conforms = False
    HC-08   focusNode=OP1                    path=M1[13,18]    不在日历可用区间

方案 C  conforms = False
    HC-12   focusNode=OP1                    path=precedes+    OP1 可达自身（成环）
    HC-12   focusNode=OP2                    path=precedes+    OP2 可达自身（成环）
    HC-12   focusNode=OP3                    path=precedes+    OP3 可达自身（成环）

方案 D  conforms = False
    HC-01   focusNode=Plan/v13               path=冻结窗口         缺失
    HC-03   focusNode=Order/MO-2026-0417     path=军品属性         待定 ∉ ['否', '是']
    HC-03   focusNode=Order/MO-2026-0417     path=交期刚性         很硬 ∉ ['弹性', '硬', '软']
    HC-14   focusNode=Order/数量               path=报工 ≥ 交付+报废   报工26 < 交付24+报废3=27，差 1 件
```

三个可以从输出里直接读出来的结论：

1. **一个违例往往连带一串。** 方案 C 的一个环，报出三个节点的违例——这是闭包的正常结果，
   但如果不做归并，调度员会看到「三条错误」而以为出了三件事。报告层要按**强连通分量**聚合。
2. **`conforms` 必须是整体判定。** 方案 D 同时踩三条，任何一条单独放行都是不合规。
   校验器输出「首个违例」就够骗过 UI 了，但审计需要全量结果。
3. **「数量守恒」写不出等式，只能写成三个不等式。** 我一开始按 `订单 = 交付 + 报废 + 在制` 写，跑出来方案 A 也「违例」——
   因为**已报工但未了结**的那部分没有位置。正确的守恒是四类之和：交付 + 报废 + 报工未结 + 未报工在制 = 订单，且四项非负。
   这是这页唯一一个我自己先写错、跑一遍才发现的地方，值得记下来。

## 五、OWL 与 SHACL：一个推理，一个拒绝

为什么方案原文写「HC-01~14 **并以 SHACL 形状（Shape）形式落地**」，而不是「用 OWL 公理表达」？
因为两者的世界假设根本相反。

| | OWL（本体、推理） | SHACL（形状、校验） |
| --- | --- | --- |
| 世界假设 | **开放世界 OWA**：没说的事，既不真也不假 | **封闭世界 CWA**：范围里没出现，就是没填 |
| 「`外委标识` 缺失」 | 什么都推不出来，**不报违例** | 触发 `sh:minCount 1`，**报违例** |
| 典型问题 | 「OP3 是否必然在 OP1 之后？」（推理） | 「这批订单能不能进排产链路？」（门禁） |
| 输出 | 推出的新事实（可能是无穷闭包） | 校验报告：`sh:conforms` + 每条 `sh:result`（focusNode / path / value / severity） |
| 语义 | 「什么是对的」 | 「什么必须满足」 |
| 工具 | Jena / RDF4J，SPARQL 查询 | pySHACL / TopBraid，形状文件即门禁配置 |

本页脚本专门把这个反差跑了一遍：

```text
开放世界陷阱：如果 Operation 实例只写了 {工序号, 工时}，没写「外委标识」呢？
  缺失的必备属性 = ['前后约束', '外委标识']
  OWL 推理机：不报。OWA 下「没人说」不等于「假」，可能只是数据没录。
  SHACL 形状：报。mandatory 缺失 = validation result，按 HC-01 禁止入库。

同一条缺失，两套语义给出相反结论——这就是 HC-01~14 要 SHACL 化、不能只靠 OWL 的原因。
```

这一点为什么在军工排产里是生死问题：
**L0 门禁的原文是「数据未达标不得进入排产链路」——这是一个拒绝权。**
拒绝权必须建立在封闭世界语义上；开放世界语义永远不会说「不」，它只会说「我不知道」。
反过来也成立：如果你用 SHACL 去表达「工序 A 先于 B、B 先于 C，所以 A 先于 C」，那是把推理硬塞进校验器，
写出来的是一堆 SPARQL 约束，可维护性为零。

::: tip 分工口诀，抄下来贴在评审材料第一页
- **约束可校** → SHACL。它有拒绝权，输出可当审计证据。
- **关系可推** → OWL + 推理机 / 图遍历。它只负责推出新事实，不负责放行。
- **两者共用同一套 IRI**，且校验永远在推理**之后**再跑一遍（推出来的事实也要过形状）。
- 求解器（[COPT 那一页](/arch/solver)）的结果，同样要回过来过一次 SHACL/HC——
  这就是「数学上最优、业务上违法」唯一的拦截点。
:::

## 六、HC-01~14 全表

原文表 4 完整列出。执行时机：**规则引擎在数据入库与本体实例挂载时自动执行**，

## 七、图谱：涟漪推演的物理载体

本体给形状，图谱给**传播**。M-04 变更影响面评估要求「图谱涟漪双向推演 ≤15min」，
它要的是沿 `precedes` / `requiresResource` / `hasPart` 三组边做**双向**遍历：

```text
设备故障 / 工序延误
   ├─ 正向（下游）：precedes+  → 受牵连的后续工序
   ├─ 资源面：同一 Resource 上的其他 assignedTo → 争抢同一窗口的批次
   ├─ 订单面：hasPart 反查 → 波及哪些订单，是否军品、交期刚性是什么
   └─ 反向上游：缺件 → 齐套要素 → 到货承诺（ASN）
```

为什么关系型库在这里难受：多跳递归要写递归 CTE，深度可变、路径要留痕（白盒归因要求「为什么判定受影响」能解释），
还要按 `rippleScope` 做范围收敛。属性图把这三件事变成一条查询：

```cypher
// 示意：从故障工序出发，沿先序与资源占用双向扩散，带路径返回
MATCH path = (o:Operation {id: $failed})-[:precedes|requiresResource*1..6]-(x)
WHERE ALL(r IN relationships(path) WHERE r.effective = true)
RETURN x, relationships(path), length(path) AS hops
ORDER BY hops LIMIT 200
```

三点工程提醒：

- **`effective` / 版本有效性**必须落在边上。工艺路线有版本，`precedes` 也有版本——用旧版路线推影响面，算出来的全是过时结论。
  「版本有效性校验」在 L0 是数据要求，在图谱是**查询必须带的谓词**。
- **双向 ≠ 无向。** 下游用 `precedes` 正向，上游用反向；混成无向会把「A 依赖 B」和「B 依赖 A」当成同一件事，涟漪半径直接算错一倍。
- **深度上限就是 15 分钟预算。** 上面这条写 `*1..6`。6 跳在真实工艺图上已经能覆盖一条从毛坯到试车的链；
  不设上限的遍历在稠密资源图上会炸（同一台设备挂几千个批次的 `assignedTo`）。

另外两处「图谱比表格强」的不可替代场景：

1. **HC-05 业务流程闭环**——「订单—工艺—排产—执行—交付链路实例闭环可追溯」，这是一条路径存在性查询，天然是图的题。
2. **`handledBy` → ZD-07 异常案例**，这是案例推理（CBR）的边：新扰动进来，先在图上找同类历史扰动，
   把当年处置方案作为 A/B/C 三案的候选。纯向量检索做不到「同类」的严格定义（同为缺料但工序不同，处置完全两样），
   图上按类型 + 工序 + 资源三条件过滤才能给出「可比的过去」。

## 八、4M 插拔：本体方案里最有价值的一句工程决策

原文 1.5：面向七类关键工序，按 4M（机 / 人 / 料 / 法）维度定义**插拔式数据组件**，
每个工序的资源能力、人员资质、物料规则与工艺参数封装成可插拔组件，建模时按需挂载，
**工艺变更或设备替换时局部更新，避免全量重建**。

对程序员的三条含义：

- **组件边界 = 变更影响面的边界。** ECN 改的是「切削参数包」，那影响面就该收敛在粗加工 × 法这一格 + 它的下游 `precedes`，
  而不是「整条工艺路线相关订单」。没有这个粒度，M-04 算出来的影响面一定是「全厂」，调度员看一眼就驳回。
- **版本挂在组件上，不是挂在订单上。** 四个格子里有两个明确写着「版本」（精加工工艺规程版本、试车大纲版本）。
  组件版本号 + 生效时点是排产时的**取值口径**，也是事后追溯「为什么当时这么排」的证据。
- **别把 4M 建成四张宽表。** 插拔的意思是「按需挂载」——某工序没有外协，就不要为它造空列。
  建模形态是 `Operation --usesComponent--> Component4M {dim: '机', version: 'v3'}`，一个工序挂 0~4 个组件。

## 九、数据—语义双链路：映射规则九条

原文 1.6：每条通识/专识数据通过映射关系挂载到本体节点，**条目 ID 与本体 IRI 双向索引**，
支持由数据查语义、由语义反查数据。

| 数据目录/模板 | 挂载本体节点 | 映射方式 | 用途 |
| --- | --- | --- | --- |
| T1 概念定义 | 全部核心类 | concept_id ↔ 类/属性 IRI | 术语对齐、语义消歧 |
| T2 原理方法 | Plan / Constraint | 方法条目 ↔ 求解策略配置 | 算法选型依据 |
| T3 通用约束 | Constraint | 约束模式实例化 | 通用约束模板复用 |
| T4 典型扰动场景 | Disturbance | 场景模式 ↔ 扰动类型体系 | 扰动识别与分级 |
| ZD-01 排产规则 | Constraint / Order | rule_id ↔ 约束实例 | 规则库语义索引 |
| ZD-02~04 工艺数据 | Operation / Part | 参数字段 ↔ 数据属性 | 工艺语义查询 |
| ZD-05/06 资源数据 | Resource | 台账记录 ↔ 资源实例 | 能力推理 |
| ZD-07 异常案例 | Plan / Disturbance | 案例 ↔ 方案/扰动实例 | 案例推理 CBR |
| ZD-08 专家经验 | Constraint / 规则 | 经验条目 ↔ 软约束 | 经验复用 |

**「双向」这两个字是本页和[审计链](/arch/audit)的接缝。** 单向（数据 → 语义）只能做检索；
双向才能做两件事：

1. **解释**：方案里某个工序被排在 3 号炉，反查 → 这条指派引用的约束实例 → 规则 ZD-01-R0xx → 原文条款。这就是「白盒归因」的落地路径。
2. **治理**：某条规则被修订（版本 v7→v8），正向查所有挂载它的约束实例与历史方案，才知道哪些历史结论要重算、哪些可以作废不追。
   ECN 归档与规则复审的评分卡都依赖这条边。

注意 T2 那一行「方法条目 ↔ **求解策略配置**」：本体连的是**算法选型依据**。
也就是说 [ε-约束、字典序、加权求和](/problem/multiobjective)这些策略选择，在这个体系里是有数据实体承载的，
不是硬编码在 Python 里。这条边做好了，C-01 的「目标权重动态调整」才谈得上留痕。

## 小结

- 本体的价值判据只有一条：**有没有代码因为它而拒绝过东西。**
- 七个类、30 条 mandatory 断言 = 最小可用数据集的定义，也是 L0 五维点检的字段级落点。
- `assignedTo` 是三元关系，OWL 里必须物化；`precedes` 是传递属性，环不会报错，只会推出「A 先于 A」——HC-12 必须显式查环。
- **拒绝权属于 SHACL，推理属于 OWL。** 开放世界语义永远不会说「不」。
- HC-01~14 和 137 条约束里的 HC-01~11 是两件事，改名（建议 DC-01~14）比合并更省事。
- 4M 插拔组件就是变更影响面的边界；双向 IRI 索引就是白盒归因和审计溯源的通路。
- 两处口径待澄清：冻结窗口 T-24h vs 周计划前 3 天；HC 编号撞车。
