# 写保护、熔断与降级链

[求解服务怎么编排](/arch/solver) 那一页处理的是「算不出来怎么办」。
本页处理另外三个问题，它们有一个共同点：**都不是算法问题，是接口契约问题。**

1. 算出来了，而且算得挺好——**谁允许你写进 MES？**
2. 15 秒到了——**熔断的是这一个请求，还是整个求解进程？**
3. 兜底规则出方案了——**业务知道这是降级产物吗？**

《技术能力点检清单 V1.0》给这三件事各留了一行：#21 Write-Through Shield（未审批写入拦截率 100%）、
#41 异常降级与熔断（算法超时熔断 15 秒，求解超时自动转启发式，模型故障转规则兜底；P0，状态
**部分满足**，备注「沙箱超时熔断可用，业务降级链路需自建」）。
本页把这三行变成可执行的东西，并且实测了 #21 那条百分比。

## 一、写路径只有一个门：`write_aps_plan`

《MCP 接入方案》V1.0 的 24 个工具里，**写工具只有 1 个**。80 个业务入参里 7 个属于它，
5 个 Scope 里 `mcp:mes:write` 只授予它一个工具。这是整个接入层最正确的一个设计决定：

> 攻击面从「24 个工具」收缩成「1 个工具的 7 个参数」。
> 只读面再宽也不会长出牙；写面再窄也必须当城门守。

| 入参 | 语义 | 门的位置 |
| :-- | :-- | :-- |
| `planBatchId` | 批次号 | 幂等键：同批次不重复写（第 3 节 C3） |
| `containerId` | 容器（卡）号 | 明细归属校验的锚（C9） |
| `workflowId` | 工艺路线 | 工序合法性 |
| `apsType` | 1 正排 / 2 倒排 / 3 瓶颈排产 | 口径要与方案声明一致 |
| `apsType2` | 1 无限产能 / 2 有限产能 | **1 的结果不许写进有限产能表**（C10） |
| `details` | 明细数组 | 冻结窗口、日历、资质都在这里判（C8） |
| `confirmTicket` | 确认票据 | 本页的主角 |

返回体 6 个字段：`planBatchId / accepted / writtenMainRows / writtenDetailRows / status / message / traceId`，
并且**任一明细失败整体回滚，返回首个失败原因**——没有「写了 80 行、第 81 行崩了」这种中间态。

::: warning 时间线上的坑：写工具排在 M2
方案的里程碑是 M1（10/30–11/3）、M2（11/27–11/30）、M3（12/24–12/31），每月放 8 个工具，
而 `write_aps_plan` 明确挂在 **M2**。意味着 M1 期间演示「端到端闭环」的项目，
写的这一半其实是**纸上的**——读工具全通、方案能出、但落不了 MES。
这不是坏事，坏事的是没人在 M1 就把第 2~3 节的闸门代码写完并演练过。
:::

## 二、十道闸：规则清单，以及每条的来源

护栏规则本身不神秘，难的是**每条都有出处**。出处不同的规则，改起来找不同的人。

| 规则 | 拦什么 | 出处 |
| :-: | :-- | :-- |
| R1 | 目录外的工具名不放行（灰度残留、拼错的 `write_aps_plan_v2`） | 本页整理，配合 [MCP 命名 lint](/arch/mcp) |
| R2 | 写动作前缀违规：`apply_ / approve_ / submit_ / save_ / delete_ / update_ / set_` | 本页整理（注册期就该拦，运行期再拦一道） |
| R3 | Scope 受众：只读 token 调写工具 → `insufficient_scope`，且不返回数据 | 方案第 4 章 |
| R4 | 必填业务入参缺失（同一份 80 参数表） | 方案第 5 章 |
| R5 | 幂等：`planBatchId` 已消费 → 返回首次结果，不重复写 | 方案第 7 章（写回语义） |
| R6 | 审批票据：一次性、服务端签发、绑定 `planBatchId + details` 摘要、TTL、消费即失效 | **本页整理**（方案只写了「confirmTicket」这个字段名） |
| R7 | 冻结窗口内的工序改动需要例外审批 | 点检清单 #24 后半句 + 本体 HC |
| R8 | 明细里有不属于该容器的工序 → 整体拒绝，返回首个失败原因 | 方案第 7 章 |
| R9 | `apsType2=1`（无限产能）的结果写进有限产能表 → 拒绝 | 本页整理（口径冲突） |
| R10 | 载荷自由文本里的疑似指令 → 不阻断写入，但降级为人工复核 | 本页整理，见 [MCP 第九节](/arch/mcp) |

R6 与 R10 是本页加进去的。加这两条的理由分别是：

- **R6**：方案里 `confirmTicket` 只出现了一次（在 `write_aps_plan` 的入参表里），没有类型、没有生命周期。
  一个没定义类型的审批字段，等于把审批权交给调用方——而调用方是模型。
- **R10**：工具返回的自由文本（ASN 备注、外协说明、检验描述）会进提示词。
  写入请求的 `details[].remark` 同理。**它是数据，不是指令**，但默认实现里它两者都是。

::: tip 护栏和目录必须共用一份表
R4 用的必填参数表，如果和 `tools/list` 返回的 `inputSchema` 是两份各自维护的清单，
那它们一定会在某一天漂移：目录改了参数、护栏还按老的拦，于是**合法请求被误拦**——
而误拦在演示里看起来像「护栏生效了」，是最容易被放过的缺陷。
本页的脚本把 24 工具 / 80 入参写成一份常量，[mcp_catalog.py](/snippets/mcp_catalog.py) 用同一份算体积。
:::

## 三、实测：12 个请求，两种 `confirmTicket`

[guardrail_probe.py](/snippets/guardrail_probe.py) 实现了上面 10 条规则，
然后拿 12 个请求打一遍：1 个正常下发、1 个重放、3 个注入、7 个越权。
**两次运行只有 `confirmTicket` 的实现不同，10 条规则一条没改。**

### 实现 A：把 `confirmTicket` 当布尔用（`if not args["confirmTicket"]: deny`）

```text
实现 A：confirmTicket 当布尔用
用例   判定     命中规则     符合预期     说明
C1   allow  —        √        正常下发：计划员在界面上点了同意
C2   allow  —        × 期望 deny模型幻觉里自己补了一句 confirmTicket=true（没人审批）
C3   dedup  R5       √        同一 planBatchId 重放第二次（网络抖动后重试）
C4   deny   R3       √        只拿只读 token 的宿主调用写工具
C5   deny   R1       √        目录外的工具名 write_aps_plan_v2（灰度残留）
C6   deny   R1,R2    √        有人注册了 apply_plan（写动作前缀违规）
C7   deny   R4       √        缺 containerId 的写请求
C8   deny   R7       √        要改冻结窗口内（t<600）的工序，没走例外审批
C9   deny   R8       √        明细里混进另一张卡的工序（部分写风险）
C10  deny   R9       √        apsType2=1（无限产能）的结果写进有限产能表
C11  review R10      √        写请求的备注字段里带提示注入载荷
C12  allow  —        × 期望 deny拿着上一次审批留下的过期票据再写一遍

越权 / 未审批写入用例 7 个，被拦住 5 个 → 未审批写入拦截率 = 71%（#21 要求 100%）
12 个用例里判定与预期不符 2 个：['C2', 'C12']
合法请求被误拦：C1/C3/C11 全部放行
```

### 实现 B：服务端一次性票据（绑定批次号 + 明细摘要，带 TTL，消费即失效）

```text

用例   判定     命中规则     符合预期     说明
C1   allow  —        √        正常下发：计划员在界面上点了同意
C2   deny   R6       √        模型幻觉里自己补了一句 confirmTicket=true（没人审批）
C3   dedup  R5       √        同一 planBatchId 重放第二次（网络抖动后重试）
C4   deny   R3       √        只拿只读 token 的宿主调用写工具
C5   deny   R1       √        目录外的工具名 write_aps_plan_v2（灰度残留）
C6   deny   R1,R2    √        有人注册了 apply_plan（写动作前缀违规）
C7   deny   R4       √        缺 containerId 的写请求
C8   deny   R7       √        要改冻结窗口内（t<600）的工序，没走例外审批
```

::: danger `confirmTicket` 不能是模型能填的布尔
这是 [MCP 接入层](/arch/mcp) 第十节埋的那颗雷，本页把它引爆：
如果 `confirmTicket: boolean`，那**审批这个动作在协议上不存在**——
模型幻觉里补一句 `true`，写请求就合法了；护栏十道闸全部放行，因为「人已经确认过了」。
此时 #21 的「未审批写入拦截率 100%」在数学上永远做不到（实测 71%）。

票据必须满足四条，缺一条就退化回布尔：
① 由服务端签发，模型侧没有任何函数能生成它；
② 绑定被审批内容的摘要（本页用 `sha256(planBatchId + details)`，改了明细票据即作废）；
③ 有 TTL（审批完一小时才拿来用，应该重新审一次）；
④ 一次性消费（重放直接 dedup，不再写第二遍）。
:::

顺带看一眼 C3：`planBatchId` 幂等在两种实现下都生效，判定是 `dedup` 而不是 `allow`——
**重试不是第二次审批**。这条在 MES 侧看是「同一批次只出现一次」，
在计划员侧看是「我点了三次下发，MES 里只有一份」。少了这个，写保护就只是拦外人。

## 四、15 秒熔断：先问「谁的 15 秒」

#41 原文：**算法超时熔断 15 秒**。方案与清单里 15 这个数字出现了不止一次，各指不同的东西：

| 出处 | 原文里的 15 | 主语 |
| :-- | :-- | :-- |
| #41 异常降级与熔断 | 算法超时熔断 15 秒 | 一次求解调用 |
| #12 机理模型 | 硬性计算超时熔断默认 15 秒 | 一次机理计算（节拍平衡 / 换刀损耗 / 拼炉优化） |
| #20 A/B 双方案 | ≤15 分钟出双方案 | 一轮交互 |
| 设计文档 | 变更评估 ≤15 分钟 | 一次变更影响分析 |

四个 15 里两个是秒、两个是分钟。写进代码之前，必须逐条确认单位、主语和**层级**。
本页 [上一节](/arch/solver) 给了个具体理由：20×5 那个算例第一次进 5% gap 要 22.8 秒，
15 秒熔断切下去只能停在 10.3%。**熔断预算不是安全余量，它是质量红线的一部分。**

三条落地要求：

1. **请求级熔断，不是进程级。** 沙箱超时熔断已经可用（这是 #41 状态写「部分满足」的原因），
   但进程级熔断会把同池并发的其它请求一起杀掉。真实负载是四种混跑的：
   夜间全量 1~2 小时、变更评估 ≤15 分钟、局部重排 ≤30 分钟、计划员点击的秒级重算。
2. **熔断时保留界。** 上界（incumbent）和下界（best bound）一起交回，降级链才有的可谈。
   丢掉界之后启发式接着跑，产出的是一个没人知道好坏的方案，#47「数值类结论须经数据底座核验」
   当场失去抓手——没有参照值可核。
3. **熔断次数要出报表。** 「今天 240 次求解里 37 次熔断」和「全部正常」是两个完全不同的系统状态，
   但只在报表里存在时才可能被看见。

另外记一次口径冲突（评审现场一定会被问）：点检清单 #24 写「重排响应 ≤5 分钟」，
设计文档写「局部重排 ≤30 分钟、变更评估 ≤15 分钟」。同一件事三个数。
本页能给的唯一诚实说法是：**这三个数都不是算法决定的，是熔断预算 + 名额排队决定的**；
先把 5/15/30 选一个钉死，再按 [求解编排](/arch/solver) 那条轨迹反推需要多少秒、几并行。

## 五、降级链要自建的部分：故障 → 动作 → 谁签字

「求解超时自动转启发式，模型故障转规则兜底」这一句话里，
真正需要设计的不是转换本身，而是**每一次转换都要有人知道、有人负责、能撤销**。

| 故障 | 检测信号 | 自动动作 | 必须落进日志 | 谁收到 |
| :-- | :-- | :-- | :-- | :-- |
| MIP 超 15 秒 | 请求级 deadline 到期 | 带 incumbent/bound 转启发式 | degraded=D1, gap, bound | 计划员（方案标灰） |
| 启发式也没在预算内收敛 | 评估次数 / 墙钟双限都到 | 转规则兜底（SPT / 主动调度） | degraded=D3, 预估损失 | 计划员 + 调度长 |
| 大模型不可用 / 超时 | 调用成功率跌破 #9 的 99.5% | 走模板 + 规则，不经过模型 | strategy=rule, 模板版本号 | 运维 + 计划员 |
| 模型输出违反护栏 | 本体 HC / SHACL 校验失败 | **不产出方案**，回传违规清单 | 违规规则号 + focusNode | 算法（改提示词没用的那种） |
| MES 写回部分失败 | 任一明细拒绝 | 整体回滚，返回首个失败原因 | traceId, writtenDetailRows=0 | 计划员 |
| License 池取不到 | 排队时长 > 阈值 | 排队并出报表，不降级 | queueMs, pool 水位 | 运维 |

两条最容易被省掉：

- **降级标记要进方案本身**，而不只在日志里。因为采纳率是拿方案跟人比出来的：
  降级方案（规则兜底那种，本页 [上一节](/arch/solver) 实测在 4×3 上损失 50%）如果混进统计，
  #23「模板生成方案合法率 ≥98%」和 ≥85% 采纳率都会被稀释或虚高——**取决于谁在算**。
  一个可执行的口径：采纳率的分母只统计 degraded 为空的方案，degraded 单列一栏报数。
- **降级必须可撤销。** D3 规则兜底出的方案一旦被采纳，第二天 MIP 恢复了，要不要重排？
  这需要一个明确策略（默认建议：**不自动重排**，冻结窗口已经吃进这批活了），
  并把它写进 [审计链](/arch/audit)——否则回放时会看到一份「没人批准过的降级」。

::: tip #41 的验收是「演练通过」，演练要注入的不是流量
拔网线、把 License 名额占满、让 MES 写接口返回部分失败、把上游某个必填字段掏空、
让模型输出一个带工序环的方案。每个场景问三个问题：**多久发现、往哪掉、日志里能不能复原。**
清单备注写「业务降级链路需自建」，自建出来的东西能不能过验收，就看这五个场景能不能演完。
:::

## 六、第二道门：数字必须带出处

写保护管的是「能不能落库」，#47 幻觉检测管的是「说的话能不能核」。
两条基准原文：**抽检幻觉检出处置率 100%，数值类结论核验覆盖率 100%**（P0，部分满足）。

「覆盖率 100%」的唯一可实现版本是：**方案里的每一个数字都有取数凭据**，形如

```text
齐套率 82%  ← get_order_shortage(orderNo=..., plannedStartFrom=...)
             @2026-11-05T09:12:03  traceId=8f1c…  口径=关重件九要素
```

没有这个结构，「核验覆盖率」只能靠抽检，而抽检永远做不到 100%——**这是口径问题，不是执行问题**。
有了这个结构，护栏（[本体那页](/arch/ontology) 的 HC-07 工时一致性 ±20%、HC-08 日历边界）
和数字溯源用的是同一批字段：一个说「这个指派在形状上合法吗」，一个说「这个数字从哪来」。

反例就在本页第一节的参数表里：`apsType2=1`（无限产能）。
无限产能的结果在数学上是**合法的**，护栏很难拒绝它——它不违反任何形状约束。
它违反的是**口径**：拿着「假设产能无限」的排产结果去写有限产能表。
这类违规只有写在闸门（R9）里，不会写在 HC 表里。

| 反模式 | 看上去 | 实际 | 出处 |

## 小结

- 24 个工具里只有 1 个写工具，`mcp:mes:write` 也只授 1 个工具——写面窄是设计决定，
  但它排期在 **M2**，M1 期间「端到端」的写这一半是纸上的。
- 十道闸里 R6（票据形态）和 R10（注入载荷）是本页补的；**#21 那条 100% 在布尔票据下最多做到 71%**。
- 护栏的强度 = 最弱那个参数的类型。加规则条数不会把 71% 抬到 100%，改票据类型会。
- 四个「15」主语不同（算法 15 秒 / 机理 15 秒 / 双方案 15 分钟 / 变更评估 15 分钟）；
  熔断必须**请求级 + 保留界 + 出报表**，它是质量红线的一部分，不是安全余量。
- 降级链要自建的三件东西：degraded 标记进方案、采纳率分母剔除降级样本、降级可撤销策略。
- 数字必须带出处（工具名 + 入参 + 取数时刻 + traceId + 口径），否则 #47 的「覆盖率 100%」在口径上就做不到。
