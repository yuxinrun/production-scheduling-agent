# 智能体五大模块与执行控制

LISA 的主设计文档里，一个智能体由**五大模块 + 执行控制**构成，
并且明确写了一句：`L2 智能体编排层（Harness：三级智能体 + 五大模块）`。

大多数团队把这五个词实现成五个 class。这是本页要纠正的第一件事：

> **五大模块不是功能划分，是留痕划分。**
> 一个智能体的实现可以有零个、一个或十个 class，
> 但它的**执行记录必须有这六段**，一段都不能少。

理由很硬：军工要求「决策链路全程留痕、可回放」。审计 schema 就是这五加一段。
你的模块划分如果和审计段对不上，回放的时候就会出现「这一步发生了什么，日志里没有」。

## 二、逐段拆：做什么、禁止什么、失败长什么样

| 段 | 产出物 | 失败长什么样 | 谁兜底 |
| --- | --- | --- | --- |
| **感知** | 结构化工具返回 + 完整调用参数 | 拿不到某工序的工艺路线，模型开始**自己编**一条 | 强制 `missing_fields` 上报；缺关键字段直接不进入规划段 |
| **记忆** | `fact + source + confidence` 三元组 | 把上个月的换型次数当成这个月；或者把「偏好」当「约束」 | 置信度 <0.7 强制复核；记忆条目有过期时间 |
| **推理** | 可展示的 thought 链 | 推理链写得头头是道，结论完全错 | 数值一律由 L3 产出（[七层底座](/arch/seven-layers) 第五节） |
| **规划** | 子任务链 + 护栏结论 | 分解出 200 个子任务，跑不完；或分解结果绕过冻结窗口 | 护栏不过 → 不产出，只产出「不可行 + 原因」 |
| **决策** | A/B/C 三案 + 影响面 | 只有一案（人变成橡皮图章）；或三案差异太小（人无法判断） | 三案必须**在关键维度上互相冲突**，否则不提交审批 |
| **执行控制** | 写回结果 / 拦截记录 | 拦截没生效，或者拦截了但没人知道（静默失败） | 拦截必发通知；未审批写入拦截率 100% 是可测的 |

::: warning 「三案必须互相冲突」这条，是决策模块唯一难实现的地方
如果 A/B/C 是同一个解的三次微调，人只能签 A。采纳率会很高（因为没得选），
但那个「人工确认」就变成了合规装饰——**这在军工审计里比低采纳率更危险**。

真实项目里 A/B/C 的构造方式是（LISA 的 M-04 变更影响面评估就是这么定义的）：

- **A 协同重排**：影响面内的活全重排，局部最优，代价是扰动大
- **B 原地顺延**：只把后续活往后推，扰动最小，代价是交期风险
- **C 折中**：只动瓶颈资源，其余不动，代价是解释成本高

三个方案在「交期 / 稳定性 / 利用率」上各赢一项。这才是人在选东西。
:::

## 三、「记忆」这一段最容易被做坏

LISA 的智能体定义文档给每个智能体都写死了记忆内容。抄几条真实的，感受一下差别：

| 智能体 | 记忆里放什么（原文要点） | 为什么是这些 |
| --- | --- | --- |
| A-00 点检与产能核算 | 五维点检历史达标轨迹、数据缺口模式库、产能基线版本、瓶颈台账变更记录 | 它的职责是门禁，门禁要**趋势**不要快照 |
| A-03 表面热处理 | 炉批历史、合炉兼容记录、实际能耗、返工入炉案例；文档明写「记忆库同步承担**工时基线自学习**」 | 这家厂**没有标准工时**（消耗定额一年维护一次），所以工时基线只能从记忆里长出来 |
| A-04 钣金焊接 | 焊接历史排产、探伤合格率分布、返工工艺案例、外协交付记录；文档明写「APS 采纳率仅 20~30%，记忆库用于**偏差根因归因**」 | 采纳率这么低的系统，记忆的第一用途是解释为什么被驳回 |
| C-01 全厂总控 | 全厂计划版本基线、夜间全量重排历史、KPI 达成轨迹、调度员偏好修正记录（**意图推理**） | 顶层要维护的是「口径」和「谁说过什么」 |

三条从这些真实条目里能读出的设计原则：

1. **记忆是结构化事实，不是文本。** 「探伤合格率分布」是一个可被求解器消费的参数，
   不是「我记得探伤老是不过」。前者能进模型，后者只能进 prompt。
2. **每条记忆必须有来源。** A-03 的实际能耗来自 MES 报工，返工入炉案例来自 QMS。
   没有来源的记忆在审计里等于**没有记忆**。
3. **「意图推理」这四个字要当心上。** 文档原话是把「调度员偏好修正记录」用于意图推理。
   这是全站最危险的一句话：把人的历史驳回行为**推断成偏好**，然后自动排产。
   正确做法是把偏好做成**显式可关闭的配置项**（"我偏好少换型"这种由人勾选的话），
   而不是模型从行为里反推出来的隐含画像。见 [采纳率是个组织问题](/build/adoption)。

  ]"
  note="这条链值得抄的地方：它把「加权求和」放在第三步而不是第一步。作者知道加权会漏掉非凸前沿上的点，所以先用 ε-约束把不能让步的目标钉死，再拿加权当快速近似。这是把数学路线编排成工程流水线。"
/>

**规划段的三条纪律，从这条链里直接抽出来：**

1. **每一步都有名字。** S1~S5 能进审计日志。`"strategy": "S4"` 是可回放的；
   `"AI 想了想觉得应该先锁交期"` 不可回放。
2. **每一步的输入输出是对象。** S1 的输入是目标函数 + ε 值，输出是一个约束模型。
   于是任何一步出错都能单独重跑——这是「状态可恢复」的真实含义。
3. **最后一步不是算法。** S5 交回给人。规划链的终点必须是人能理解的东西（Top-5 + 满意度），
   不是一个标量最优值。

## 五、一个能跑的骨架：六段 + 可重放的 trace

下面这个骨架把六段串起来，每段产出一条**带 parent 摘要**的日志——
这样审计链天然形成一条哈希链，改一段就断链。完整文件在
[`/snippets/five_modules.py`](/snippets/five_modules.py)。

```python
def in_window(plan):
    b = plan["ops"][0]
    return b["start"] + b["dur"] <= b["end"], "工序落在资源可用窗之外"


GUARDRAILS = [
    lambda plan: (len(plan["violations"]) == 0, "HC 硬约束必须为 0 违反"),
    lambda plan: (plan["horizon"] <= 7 * 24, "排产窗口不得超过一个冻结周期"),
    in_window,
]


def run(agent, order, tools, approvals):
    t, prev = [], None

    def emit(stage, payload):
        nonlocal prev
        e = Trace(agent, stage, payload, parent=prev).to_log()
        prev = e["digest"]
        t.append(e)

    obs = {name: fn(order) for name, fn in tools.items()}   # 1 感知
    emit("perceive", {"tools": list(obs), "obs": obs})

    mem = [{"fact": "上月同型件换型 3 次/日",                 # 2 记忆
            "source": "ZD-05/设备实绩", "confidence": 0.81}]
    emit("recall", {"used": mem})

    w0, w1 = obs["resource_calendar"]["free_window"]          # 3 推理
    thought = f"{order['op']} 尝试排入 {obs['resource_calendar']['machine']} 的窗口 {w0}-{w1}"
    emit("reason", {"thought": thought})

    plan = {"ops": [{"op": order["op"],                       # 4 规划：可校验对象
                     "res": obs["resource_calendar"]["machine"],
                     "start": w0, "dur": order["p"], "end": w1}],
            "horizon": 72, "violations": []}
    for check in GUARDRAILS:
        ok, why = check(plan)
        if not ok:
            plan["violations"].append(why)
    emit("plan", {"plan": plan, "guardrails": len(GUARDRAILS)})

    proposals = [{"id": "A", "value": plan},                  # 5 决策：只出三案，不选
                 {"id": "B", "value": None}, {"id": "C", "value": None}]
    emit("decide", {"proposals": [x["id"] for x in proposals], "auto_approved": False})

    approved = any(a["plan_id"] == "A" for a in approvals)    # 6 执行控制
    action = "write" if approved else "blocked"
    emit("execute", {"action": action, "reason": None if approved else "无电子签名"})
    return {"plan": plan, "action": action, "trace": t}
```

实跑输出：

```text
窗口内: action=blocked  violations=[]
   stages: ['perceive', 'recall', 'reason', 'plan', 'decide', 'execute']
窗口外: action=blocked  violations=['工序落在资源可用窗之外']
   stages: ['perceive', 'recall', 'reason', 'plan', 'decide', 'execute']
有签名时: write
最后一条 trace: {"ts": "2026-11-05T09:16:43", "agent": "A-02", "stage": "execute",
 "digest": "3bcd32fca845", "parent": "4bde17b522ed",
 "payload": {"action": "blocked", "reason": "无电子签名"}}
```

**三个「一眼能看出来」的设计点：**

- 「窗口内」这一行 `violations=[]` 但 `action=blocked`：**护栏过了也不许写**。
  可行性与授权是两件事，混在一起就会变成「解没问题就自动下发」。
- 护栏是**函数列表**，不是 if-else 硬编码。HC 约束的增删就是列表增删，能配置、能单测、能按智能体分组。
- `parent` 指向前一条的 `digest`。审计链一旦成型，**中间删一条就断链**，
  这比「日志权限管控」这种软措施硬得多。

## 六、一个智能体的完整规格：十个要素

LISA 的智能体定义文档对每个智能体用**固定十个要素**描述：
`名称 / 职责 / 规划 / 记忆 / 本体 / 配置 / 权限 / 输出 / 接口 / 技能与工具`。

这个模板值得直接抄，因为它是**能验收的单位**。用 A-00 填一遍（内容取自真实定义文档）：

| 要素 | A-00 数据点检与产能核算智能体 |
| --- | --- |
| 名称 | Data Check & Capacity Accounting Agent |
| 职责 | 订单/工序/资源/日历/约束五维点检（达标率 ≥90% 为验收 KPI）；全厂产能基线核算与瓶颈台账维护；缺口整改单生成 |
| 规划 | T+1 批量点检状态机：五维抽取 → 达标判定 → 缺口定位 → 整改单派发 → 复核闭环；点检不达标即阻断对应智能体上线（L0 门禁） |
| 记忆 | 达标轨迹、缺口模式库、产能基线版本、瓶颈台账变更 |
| 本体 | 数据质量本体（五维 ↔ 字段映射）；产能资源本体（设备/人员/工装能力视图） |
| 配置 | 五维阈值 ≥90%、点检时点 T+1、缺口分级参数、产能核算口径（分设备标准工时基准） |
| 权限 | 只读 ERP/MES/WMS/QMS/APS 全域；**无业务写入权**；点检结论直达评测治理层与 C-01 |
| 输出 | 五维点检报告、缺口清单与整改单、产能基线表、瓶颈台账、上线门禁结论 |
| 接口 | 入：四个系统的适配器；出：评测治理层、C-01、全部原子级（门禁信号） |
| 技能/工具 | 五维规则点检、缺口归因、产能核算；数据质量规则引擎、字段映射服务、产能核算模型 |

::: tip 用这个模板做设计评审，效率极高
评审时逐行问三个问题：**这一行有具体数值吗？这一行的失败模式是什么？这一行谁签字？**
上表里「权限：只读、无业务写入权」是一行能验收的规格；
「权限：合理」是零行。「配置：五维阈值 ≥90%」能测试；「配置：按需调整」不能测试。
:::

## 七、五种把五大模块做歪的方式

| 歪法 | 症状 | 处方 |
| --- | --- | --- |
| 只有推理，没有规划 | 系统输出是一大段话，没有可执行的计划对象 | 强制结构化输出 + JSON Schema 校验，不过就重试 |
| 规划不过护栏 | 「计划看着挺合理，但设备根本不存在」 | 护栏在**规划段内**执行，不是在执行控制段才查 |
| 记忆做成对话缓存 | 每次跑都记得上次聊了什么，但不记得上次的**实绩** | 记忆库的写入方是 L4 数据层，不是 LLM 的上下文 |
| 决策段被跳过 | 系统直接下发，人只在事后收到通知 | 采纳率 ≥85% 的前提是人真的有得选。没有决策段的系统拿不到这个数 |
| 执行控制做成前端弹窗 | 「点确认才写」——但 API 仍然可以被直接调 | 熔断必须在**服务端**、在写账号那一层。弹窗是 UI，不是网关 |
