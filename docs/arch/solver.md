# 求解服务怎么编排

[五大模块](/arch/five-modules) 那条 S1→S5 规划链，最后一步是「把问题交给求解通道」。
[本体与护栏](/arch/ontology) 那页把「校验什么」定完了。两页之间缺的那一段是本页：

**谁来算、算多久、算不出来往哪掉、掉下去以后界还剩什么。**

这四问在《某某智能排产智能体技术能力点检清单 V1.0》里对应五行。我把这五行抄下来，
然后写了 [`solver_budget.py`](/snippets/solver_budget.py) 在真实算例上逐条量。
结论提前放这儿：**五行全写着「不满足」，而其中三条基准的写法本身就没法验收。**

## 一、先把验收单摊开：求解/算法引擎，0 / 0 / 5

点检清单总共 56 条能力，满足 21、部分满足 25、不满足 10。「求解/算法引擎」这个域一共 5 条，
P0 两条、必须四条，满足 0、部分 0、**不满足 5**——它是全表唯一一个 100% 不满足的域。

| # | 能力 | 验收基准（原文） | 级别 | 状态 / 卡点 |
| :-: | :-- | :-- | :-: | :-- |
| 27 | LP 线性规划 | LP 求解收敛率 100%，万级变量求解 ≤60 秒 | P0 必须 | 不满足：平台不含运筹求解器，须外挂 COPT 集群 |
| 28 | MIP 混合整数 | 时限内求得可行解率 ≥99%，硬约束零违规 | P0 必须 | 不满足 |
| 29 | 启发式 | 求解时间 ≤ 精确求解 10%，方案质量损失 ≤5% | P1 必须 | 不满足：算法库自研 |
| 30 | 增量求解 | 增量重解耗时 ≤ 全量求解 20%，冻结窗口内方案不变 | P1 必须 | 不满足 |
| 31 | 数值稳定性 | 数值异常有诊断报告，IIS（最小不可行子集）输出可用 | P1 | 不满足 |

三条值得停一下的信息：

1. **第 27 行的备注是整个项目的架构事实**：平台不含运筹求解器。这不是「算法选型」问题，
   是「算力从哪来」问题——第 27 行的 Harness 要求写着「求解器集群独立部署，License 满足并发」。
2. **#31 是全表唯一一条「非必须」 yet 不满足**的能力。也就是说：连清单自己都没把数值诊断当硬要求。
   而 MIP 建模的人都知道，模型不可行时最贵的就是这个——见第五节。
3. 旁边还有两条相关但状态不同的：**#41 异常降级与熔断**（算法超时熔断 15 秒，求解超时自动转启发式，
   模型故障转规则兜底）P0 部分满足，备注「沙箱超时熔断可用，业务降级链路需自建」；
   **#25 依赖分析**（DAG 拓扑与关键路径）P0 不满足，需外挂图分析组件。

前两条基准（#27 万级变量 ≤60 秒、#28 可行解率 ≥99%）本页量不了——手上没有 COPT/Gurobi，
纯标准库跑不出 LP 松弛。所以下面全部围绕 **#29 / #30 / #41**，而且这三条恰好是最有嚼头的。

## 二、#29 的左半边：「≤ 精确求解 10%」是一条停止规则

先跑最小的一台机器：4 工件 × 3 机器（就是 [精确与界限](/problem/bounds) 那页的算例），
精确通道 = 机器顺序全枚举。

```text
[4×3] 精确通道：机器顺序全枚举 13,824 个，无环可评估 2,256 个 → 最优 makespan = 20
      耗时 0.185s，评估 2,256 次（每次 = 一遍拓扑推进）
      爬山 预算   100 → makespan 20（损失   0.0%）     2.33ms = 精确的   1.26%   评估   100 次 / 重启   4 轮
      爬山 预算   300 → makespan 20（损失   0.0%）     6.66ms = 精确的   3.61%   评估   300 次 / 重启  13 轮
      爬山 预算 3,000 → makespan 20（损失   0.0%）    66.13ms = 精确的  35.79%   评估 3,000 次 / 重启 128 轮
      SPT 一条规则 → makespan 30（损失 50%）  0.097ms = 精确的 0.052%
      下界对照：平凡下界 = 17，最优 = 20 → 下界离最优 17.6%；拿它当分母报「损失」，同一个方案从 17.6% 缩到 15.0%
```

四件事，一件比一件不舒服：

**① 三行爬山拿到的都是最优（损失 0.0%），但时间占比从 1.26% 一路涨到 35.79%。**
质量一点没变，因为 300 次评估早就收敛了；剩下的 2,700 次在原地扰动、原地失败。
于是 #29 前半句「求解时间 ≤ 精确求解 10%」在这台 4×3 上是否达标，
取决于你在第几次评估停手。这不是算法属性，是**停止规则**属性。
清单里没写预算怎么定——没写评估次数上限、没写墙钟、没写「精确求解」用哪个求解器什么时限。
验收现场这四个空都得填，填的人不是算法同学。

**② SPT 用 0.052% 的时间，拿到 50% 的损失。**
同一条链上「时间」和「质量」是同一个旋钮的两端。基准里两条各卡一个位置，
而 0.052% 和 1.26% 都满足「≤10%」，30 和 20 却是两个方案。
所以光看前半句，最派工规则都算「通过」。**基准必须成对读，不能分行签。**

**③ 分母陷阱第三次出现。** 平凡下界 17、最优 20，同一个方案报 17.6% 还是 15.0%，
只看你除的是哪一个。这条在 [精确与界限](/problem/bounds) 已经讲过，本页再钉一次：
「质量损失 ≤5%」的分母是最优值，而最优值在你交付的那个规模上不存在（下一节实测）。

**④ 13,824 个组合里只有 2,256 个无环**——精确通道有 83.7% 的枚举落在非法空间里。
这就是为什么「全枚举」不是「精确算法」，它是带着可行性剪枝的枚举。

::: tip 验收现场该问的四个问题
「精确求解 10%」——精确是哪个求解器、什么时限、什么机器？
「≤10%」是 P50 还是 P99？夜间全量和插单急改用同一个百分比合理吗？
「质量损失 5%」——分母是最优还是下界？给出下界怎么算的？
预算是评估次数还是墙钟时间？换硬件以后这条基准自动漂移，谁来重测？
:::

## 三、#29 的右半边 + #41：规模上去以后，两条基准在同一条轨迹上互斥

把实例放大到 20 工件 × 5 机器（每台机器 20 道工序），机器顺序的组合数是

```text
[20×5] 20 工件 × 5 机器，每机器工序数 [20, 20, 20, 20, 20] → 机器顺序组合数 ≈ 8.524e+91（精确通道在这里不存在）
       每机器负载 [122, 116, 136, 94, 127] → 平凡下界 = 136
   预算   2,000 → makespan  163    0.38s  评估    2,000 次  重启   11 轮   vs 下界 gap  19.9%   15 秒熔断内收工
   预算  20,000 → makespan  154    3.77s  评估   20,000 次  重启   95 轮   vs 下界 gap  13.2%   15 秒熔断内收工
   预算 120,000 → makespan  142   22.81s  评估  120,000 次  重启  532 轮   vs 下界 gap   4.4%   15 秒熔断内跑不完
```

**这三次跑用同一颗种子**，所以 2,000 / 20,000 / 120,000 不是三个实验，
是同一条搜索轨迹的三个截断点。做任何求解器对比的第一条纪律就是这个：
不同种子的两次跑，差 3 个单位可能全是噪声；同种子的截断点才允许你画曲线。
（本页第一版脚本就栽在种子没统一，加上随机重启撞环退化成原地不动，
三个预算报出同一个 219——看着像「邻域太窄」，实际是重启一次都没生效。）

然后 #41 的 15 秒熔断进来。同一条轨迹，改成只给墙钟、不限评估：

```text
   同一条轨迹，改成只给 15 秒墙钟（评估不限）→ makespan 150，用掉 15.00s，评估 78,961 次 / 重启 351 轮，gap 10.3%
   ⇒ #29 要「损失 ≤5%」：轨迹上第一次进 5% 是 142（gap 4.4%），花 22.8s = 熔断线的 1.5 倍
      #41 要「15 秒熔断」：卡在 15s 只能停在 150（gap 10.3%）。
      两条基准各占这条轨迹的一头，中间没有同时满足的解——除非加算力或换算法。
```

::: danger 这两条基准不是「都挺严」，是互斥
#29 要损失 ≤5%，#41 要 15 秒熔断。在本页这个 20×5 算例上，同一条轨迹第一次进 5% 需要 22.8 秒。
也就是说：**同时签这两条，等于签了一张做不到的验收单。**
三条出路，选哪条都要留痕：加算力（并行多起点、把 22.8 秒压进 15 秒）、换算法（邻域搜索 + 剪枝，
或者上约束规划）、或者改基准（把 5% 改成「vs 下界 gap ≤X%」，并且把 X 定在你实际能在时限内达到的地方）。
最糟的处理是让两条基准同时留在清单上，然后每次验收都报「已满足」。
:::

补一句口径纪律：上面宣布 4.4% 那档「可以宣布满足 ≤5%」，是因为下界 ≤ 最优 ⇒
vs 下界的 gap ≥ vs 最优的损失。**gap ≤5% 是损失的充分条件，不是等价条件。**
反过来说，如果只有 vs 下界 10.3% 的数，你不能宣布损失 10.3%，只能宣布「不低于 10.3% 的那个上界」。
这一条在 [quiz](/quiz) 里也是考点。

## 四、#30 增量重解：前半句好过，后半句是构造出来的

先给一份「已经下发到车间」的方案——4×3 的精确最优，开工时刻如下：

```text
[插单] 车间正在执行下面这份已下发的方案（4 工件精确最优）：
       makespan = 20，工序开工时刻 = 0.0@0 0.1@7 0.2@13 1.0@0 1.1@3 1.2@7 2.0@0 2.1@8 2.2@13 3.0@2 3.1@8 3.2@19
       各机器负载 = [17, 17, 14] → 瓶颈在机器 0 和 1
       冻结窗口 [0,6) = [(0, 0), (1, 0), (1, 1), (2, 0), (3, 0)]
       按前缀写法各机器的固定段 = {0: [(0, 0)], 1: [(1, 0), (3, 0)], 2: [(2, 0), (1, 1)]}
```

三种急单各跑一遍：全量重排（枚举到最优）对增量重排（钉住前缀 + 4,000 次评估爬山）。

```text
  [急单走闲机器] 新工件工序 = [(2, 3)]
      全量重排：枚举 69,120 个机器顺序（无环 11,280）→ 最优 20，耗时 1.01s
      增量重排：20（比全量差 0.0%），耗时 0.096s = 全量的 9.5%（红线 20%）→ 评估 4,000 次 / 重启 256 轮
      冻结工序开工时刻变化 = 无 → 基准后半句「方案不变」满足
      同预算放开冻结 → 20，冻结的价格 = 0 个时间单位（这单插得进去，白冻）
  [急单压瓶颈] 新工件工序 = [(0, 7)]
      全量重排：枚举 69,120 个机器顺序（无环 11,280）→ 最优 24，耗时 1.00s
      增量重排：24（比全量差 0.0%），耗时 0.097s = 全量的 9.6%（红线 20%）→ 评估 4,000 次 / 重启 308 轮

  [急单三道工序全走] 新工件工序 = [(0, 4), (1, 5), (2, 3)]
```

### 4.1 「耗时 ≤ 全量 20%」这条为什么会赢

因为**分母是全量枚举**。多插一道工序，机器顺序的组合数从 69,120 跳到 1,728,000，
全量耗时 1.01s → 25.45s，而增量那一侧几乎不变。于是比例从 9.5% 掉到 0.4%。

> 分母越大，比例越好看。#30 前半句在这台小机器上怎么测都过。
> 它真正约束的是别的东西：如果你的「全量」是一个 30 秒的启发式而不是精确枚举，
> 20% 就变成 6 秒——那条红线立刻开始咬人。所以落地时要写死**分母的定义**，
> 最好写成绝对时限（「扰动场景秒级响应」，清单原文这句比百分比有用）。

顺带第三条急单值得单独看一眼：全量精确重排**单是这一步**就 25.45 秒，超了 #41 的 15 秒熔断。
一条插单急改，如果坚持「重新算到最优」，熔断了也还没算完。增量重排不是性能优化，是**能不能在时限内交卷**。

### 4.2 「冻结窗口内方案不变」这条，写法决定一切

先说正确写法。冻结不是「把冻结工序挑出来放前面」，是**还原已下发方案在各机器上的前缀**：

```python
def freeze_prefix(base_order, st, until):
    """机器 k 的前 cut[k] 格按已下发方案原样钉死。
       cut[k] = 该机器上最晚一道冻结工序的位置 + 1。"""
    cut = {}
    for k, seq in base_order.items():
        idx = [i for i, n in enumerate(seq) if st[n] < until]
        cut[k] = max(idx) + 1 if idx else 0
    return cut
```

搜索时 `first_free(k) = cut[k]`，任何交换/扰动只能发生在固定段之后。这样冻结工序的开工时刻
按构造不可能改变——**注意这句话的性质：它不是算法算得好的结果，是搜索空间被削掉一块的结果。**

现在说偷懒写法，也是本页第一版真实写错的地方：`[x for x in seq if x in frozen] + [其余]`。
看起来同样「保住了冻结工序的相对顺序」，实测（20×5，冻结 17 道）：

```text
[上规模] 20×5：下发方案 makespan = 154（预算 20,000 那一跑）
       急单 = [(0, 8), (1, 5), (2, 3), (3, 2), (4, 6)]（第 21 个工件，5 道工序）→ 新平凡下界 = 139
       冻结窗口 [0,15) = 17 道 / 105 道，各机器固定段长 = {0: 2, 1: 3, 2: 3, 3: 5, 4: 4}
       前缀钉死 → 155（vs 下界 11.5%），3.97s，重启 104 轮
       全放开、同预算 → 158（vs 下界 13.7%），3.95s，重启 85 轮

[偷懒写法] 不设前缀，先自由搜、再把冻结工序「挑出来放最前」：
       makespan 158，同样 17 道冻结工序，开工时刻变了 2 道 = {(17, 1): (3, 5), (12, 0): (11, 3)}
```

`(12, 0)` 从 11 挪到了 3，**提前**了 8 个单位。车间会怎么看这个「提前」？机床在 t=3 到 t=11 那段时间
本来腾给了别的活——那是另一张工单的占用。计划员拿到的新方案会显示「这道工序早八点开工」，
现场执行不了，于是整版方案在车间眼里作废一次。

::: warning 冻结的不变量只有按 (机器, 位置) 钉死才成立
「集合置顶」的实现能骗过单元测试（相对顺序确实没变，断言 `frozen 的先后 == 原来 == True` 会绿），
骗不过车间。写这条的代码评审时只问一句：**你钉的是位置还是集合？**
顺便，这条要求压根不是算法要求，是搜索空间构造要求——所以清单把它放在「求解/算法引擎」域，
验收时应该同时看一眼 [护栏](/arch/guardrail)：位置不变量也可以由护栏事后拒绝。
:::

### 4.3 冻结值多少钱：测出来是负的，而这才是重点

```text
       ⇒ 两次结果的差 = -3 个时间单位。注意它是负的——
          不是「冻结反而赚了 3」，是同预算下两边都没撞到最优，
          差值里混着搜索噪声。真正的冻结代价 = opt(冻结) − opt(自由) ≥ 0，
          而这两个 opt 在本页的规模上都不可知。4×3 上它是 0，也不是「冻结不花钱」，
          是那个规模怎么搜都撞得到最优。
```

钉住 17 道的那一跑反而比全放开的跑得更好（155 vs 158）。这不合直觉，但完全合理：
**搜索空间变小了，同一个预算下收敛更快**。而两个都是启发式结果，谁都没撞到最优，
所以它们的差里混着噪声，不能当成「冻结的收益」。

严格说，冻结的真实代价是 `opt(冻结) − opt(自由)`，它 ≥ 0（可行域被删了一小块），
但这个量在你手上永远算不出来——它需要两个最优值，而最优值就是本页第三节那个 8.5e91。

于是落地上必须承认一件事：

> #30 写了「冻结窗口内方案不变」，没写「不变值多少钱」。
> 而「为了不动这 17 道工序，整班交付最多愿意慢多少」是一个**业务签字**，不是一个算法输出。
> 你能给业务的只有夹逼：一个下界（负载 / 交期）和几个候选方案各自的 gap，
> 外加一句「冻结以后最好的是 155，放开以后最好的是 158，两者都离下界 139 很远」。
> 这条在 [精确与界限](/problem/bounds) 里叫「你永远活在夹逼里」，在本页它变成了一张签字栏。

::: tip 为什么「保留界」不是锦上添花
MIP 在 15 秒时给你的不只是「还没算完」，它给了两个数：incumbent 154、best bound 139。
带着这两个数交给启发式，你能立刻知道启发式的 155 离「已知的最好可能」有多远，
也才知道该不该继续烧算力。丢掉界，启发式就变成一个不知道自己好坏的输出——
然后 #47 那条「数值类结论须经数据底座核验」就没有东西可核验。
本页第三节的整条 gap 曲线，前提是每一档都有同一个下界。
:::

另一半也要说清楚：**D3 规则兜底的代价是可以量化的**。本页 4×3 上 SPT 给 30，最优 20，损失 50%。
50% 的 makespan 损失在很多厂里等于交期违约一片，所以「转规则兜底」不是免费保险，
它是一条需要业务预先批准的处置方案（谁批准、批准什么、是否自动通知计划员）。
清单里那句「模型故障转规则兜底」后面没有这一栏，落地要补。

## 小结

- 点检清单「求解/算法引擎」5 条全不满足，是全表唯一 0 达标的域；#27 的备注写明了架构事实：**平台不含运筹求解器**。
- **#29 前半句是停止规则**：同一算法，预算 100→3,000，时间占比 1.26%→35.79%，质量一直是 0 损失。
- **#29 后半句在规模化以后缺分母**：20×5 上最优不可知，只有 vs 下界的 gap；两个口径不同源，不能互换着报。
- **#29 与 #41 互斥**：同一条轨迹第一次进 5% 要 22.8 秒，15 秒熔断只能停在 gap 10.3%。
- **#30 前半句靠分母会自己达标**，后半句靠「前缀钉死」的构造达标——写成集合置顶会改掉已下发方案的开工时刻。
- **冻结的价格测出来是 −3**，因为两边都是启发式、都有噪声；真实代价是 `opt(冻结) − opt(自由)`，量不出来，只能夹逼 + 业务签字。
- **降级链的关键动作是「换算法但保留界」**；规则兜底要预先报出代价（本页实测 50% 损失）。
