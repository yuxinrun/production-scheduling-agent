# 不确定性：排队、鲁棒与重排

排产模型里的 `p_j = 6 小时` 是**谎言**，只不过是一个方差很小的谎言。
现场的真实情况是：加工时间有分布、设备会坏、急单会插、探伤会不合格、外协会说「明天到」。

应对只有三种，**你的系统必须同时实现这三种**：

| 层 | 时机 | 手段 | 成本 |
| --- | --- | --- | --- |
| **预测** | 排产前 | 把 `p` 从点估计换成分布估计（GBDT / 分位数回归 / 经验分位） | 数据 |
| **缓冲** | 建模时 | 安全时间、安全产能、批次间隔 | 交付速度 |
| **重排** | 扰动发生后 | 右移 / 局部重排 / 全量重排，按影响面选 | 计算与信任 |

**只上一层的项目都会翻车。** 只做预测不做重排，设备一坏就崩；
只做重排不做缓冲，你的计划每天都在剧烈变化，计划员会放弃你的系统。

## 一、排队论：为什么「排满」是错的

两条公式，足够解释现场 80% 的现象。

### Little 定律：`L = λ · W`

稳态下，平均在制 = 平均到达率 × 平均停留时间。三量必须同单位。

```text
λ = 12 件/天，W = 7.5 天   →  WIP = 90 件
想把 WIP 压到 60 件，λ 不变 →  W 必须降到 5.0 天
```

这条恒等式的工程价值：**WIP、交付周期、吞吐量三者只能自由两个**。
计划员说「我要 WIP 降一半，交付时间也别变」，你可以直接用这条公式告诉他这不可能。

### Kingman 近似：等待时间在利用率 1 附近**发散**

```text
E[Wq] ≈  ( ρ / (1 − ρ) )  ×  ( (C_a² + C_s²) / 2 )  ×  E[S]
          ↑ 利用率项，凸      ↑ 变异项                ↑ 服务时间均值
```

| 利用率 ρ | `C_a=C_s=1` 时 `Wq/E[S]` | 车间常见 `C_a=1.4, C_s=1.6` |
| --- | --- | --- |
| 0.50 | 1.00 | 2.26 |
| 0.70 | 2.33 | 5.27 |
| 0.80 | 4.00 | 9.04 |
| 0.85 | 5.67 | 12.81 |
| 0.90 | 9.00 | 20.34 |
| 0.95 | 19.00 | 42.94 |

**读法**：在 `C_s=1.6` 的车间里，把瓶颈设备从 85% 排到 92%，等待时间不是涨 8%，是**翻倍**。
这就是「提高瓶颈利用率」这个 KPI 的隐藏代价，也是为什么排产模型必须留缓冲。

::: warning Kingman 是**近似**，别把它当定理引用
它是重流量极限下的结果，`C_a`、`C_s` 是到达与服务时间的变异系数（CV = 标准差 ÷ 均值）。
低利用率时它会低估，多机串联时误差累积。
**但它的方向永远正确，而且方向就是全部要点：负载接近产能时，等待是发散的。**
写进方案时用「趋势」而不是「数值」，或者干脆自己跑一次离散事件仿真校准。
:::

## 二、返工不是「概率 40% 会返工」这么简单

LISA 现场有一个数字很扎眼：**探伤合格率 60%**（无损检测一次通过率）。
很多人会把它建模成「40% 的工单多走一道工序」，然后加一次产能。**这是错的，而且错得很多。**

如果返工后重新检测、合格率仍是 60%，那么工序次数是几何分布：

```text
一次通过概率  p = 0.6
期望尝试次数  E[N] = 1/p = 1.667
期望返工轮数  E[N] − 1 = (1 − p)/p = 0.667 轮

→ 这道工序的期望产能占用是名义值的 1.667 倍，不是 1.4 倍
→ 需要返工的工件，其「额外等待 + 重新排队」的周期影响远大于加工时间本身
```

四个必须一起改的东西：

1. **产能**：`p_effective = p × (1/p_detect)`，别只加一次。
2. **时间窗**：特殊过程有效期在返工期间**继续衰减**（焊后 20 天不会因为你返工就暂停）。
3. **交期承诺**：合格率的方差决定你的 OTD 承诺能不能兑现。用分位数而不是均值承诺。
4. **瓶颈**：返工会让检测台与热表工序**二次排队**，它们往往才是真正的隐藏瓶颈。

```python
import random

def expected_capacity_factor(p_pass: float, trials=200_000):
    """蒙特卡洛估计：含返工的期望工序次数，顺带看看 95 分位有多惨。"""
    counts = []
    for _ in range(trials):
        n = 0
        while True:
            n += 1
            if random.random() < p_pass:
                break
            if n > 20:                       # 现实中会走「让步/报废」分支，必须有上限
                break
        counts.append(n)
    counts.sort()
    mean = sum(counts) / len(counts)
    return mean, counts[int(0.95 * len(counts))]

for p in (0.9, 0.75, 0.6):
    mean, p95 = expected_capacity_factor(p)
    print(f"合格率 {p:.2f} → 期望工序次数 {mean:.2f}（理论 {1/p:.2f}），"
          f"95 分位 {p95} 次  → 最坏情况产能是名义的 {p95} 倍")
```

```text
合格率 0.90 → 期望工序次数 1.11（理论 1.11），95 分位 2 次  → 最坏情况产能是名义的 2 倍
合格率 0.75 → 期望工序次数 1.33（理论 1.33），95 分位 3 次  → 最坏情况产能是名义的 3 倍
合格率 0.60 → 期望工序次数 1.67（理论 1.67），95 分位 4 次  → 最坏情况产能是名义的 4 倍
```

**看 95 分位那一列。** 60% 合格率意味着每 20 个工件就有 1 个要反复走 4 次检测——
期望值只告诉你「平均多 0.67 次」，尾部才决定你的台架窗口会不会被击穿。
这恰好解释了为什么现场需要「冻结窗口 + 缓冲」这种看起来很浪费的组织手段：
它们不是在保护平均值，是在保护尾部。

::: tip LISA 文档里那一行「返工贝叶斯网络」
交付文档把「返工贝叶斯网络」列为支撑技能（与 GBDT 工时预测、GPR 满炉率、生存分析维修 ETA 并列）。
**上面这段几何分布就是它的最小版本**：先按工序独立，再让节点之间有条件依赖
（某类材料 + 某台设备 + 某个焊工 → 合格率分布不同）。
先跑起来独立版本，再加依赖，顺序别反。
:::

## 三、鲁棒优化：只保护「最坏 Γ 个」

**Bertsimas–Sim（2004）** 的预算不确定集是现代现场最实用的鲁棒模型：

```text
名义加工时间  p̄_j
不确定幅度    p̂_j            （比如 ±30%）
预算参数      Γ               假设「任意 Γ 个工件同时变坏」

约束：  Σ p̄_j x_ij  +  max_{S ⊆ J, |S| ≤ Γ}  Σ_{j ∈ S} p̂_j x_ij   ≤  T_i   ∀ 机器 i
```

- `Γ = 0` → 完全乐观（名义模型）
- `Γ = |J|` → 全部同时变坏（保护过度，产能腰斩）
- 中间取值 → **「概率保证 vs 产能损失」的显式旋钮**

它的工程价值在于：**Γ 是能和车间主任讨论的参数**。
「你觉得一个月内最多有几台设备会同时出问题？」——这就是在问 Γ。
回答通常是 2~5，而不是「全部」。于是你的产能损失从 30% 降到 6~8%。

**「稳健的代价」（price of robustness）** 一定要算出来给管理层看：

```python
# 鲁棒代价 = 同样交期承诺下，名义模型能接的单 vs 鲁棒模型能接的单
def solve(capacity, durations, jobs):
    """这里用贪心装填示意；真实项目用 MILP/CP。返回能接下的工单数。"""
    n, used, taken = len(durations), 0, 0
    for j in sorted(range(n), key=lambda i: -jobs[i]["value"]):
        if used + durations[j] <= capacity:
            used += durations[j]
            taken += 1
    return taken

jobs = [{"id": i, "value": v, "p": p, "risk": p * 0.3}
        for i, (p, v) in enumerate([(8, 5), (6, 9), (12, 4), (4, 7), (9, 6), (7, 3), (5, 8)])]
CAP = 34

nominal = solve(CAP, [j["p"] for j in jobs], jobs)
gamma = 2
# Γ=2：最坏情况下，被选中的工单里有 2 张额外多花 risk 时间
worst = sum(sorted([j["risk"] for j in jobs], reverse=True)[:gamma])
print(f"名义可接 {nominal} 单；Γ={gamma} 时最坏额外工时 {worst:.1f}h "
      f"≈ 少接 {worst / (CAP / nominal):.1f} 单  ← 这就是「稳健的代价」")
```

```text
名义可接 5 单；Γ=2 时最坏额外工时 6.3h ≈ 少接 0.9 单  ← 这就是「稳健的代价」
```

也就是说：**用不到一张单的代价，换掉了「两台设备同时出问题就全线崩」的风险。**
Γ 的选择就是把这句话变成参数。

::: details 为什么不直接用「均值 ± 2σ」加 buffer
因为**加法错误**。多张工单的不确定性不完全叠加（它们不会同时坏），
简单加 2σ 在 200 张工单上会加出 400 小时的缓冲，产能直接消失。
Γ-预算的正确之处是它显式约束**同时变坏的数量**，而不是「每个都变坏」。
另一条常见路是分位数卷积（把分布做数值卷积取 90 分位），比加 σ 准，但计算贵、可解释性差。
:::

## 四、扰动来了怎么办：先分类，再选策略

动态调度领域最常被引用的组织框架是 **Ouelhadj–Petrovic（2009）** 的三维描述：
**扰动是什么 / 用什么方法响应 / 响应手段是什么**。照这个形状建你的路由表。

### 扰动的七个域（LISA 的原文分类，56 条规则按这七个域写）

| 域 | 代号 | 典型影响 | 首选响应 | 为什么 |
| --- | --- | --- | --- | --- |
| 设备故障 | GZ | 该机器上的工序全部待转移 | 局部重排 + 涟漪推演 | 影响面清晰，全量重排是浪费 |
| 物料 / 齐套 | WL | 工单不许开工 | **右移**（不改变顺序，只推时间） | 右移最稳定，成本最低 |
| 紧急插单 | CJ | 插入新工单，挤占瓶颈 | 冻结窗口外重排 + 审批 | 军品急件的规则通常是**未定义**的，先问人 |
| 返工 | FG | 工序重复 + 二次排队 | 状态机 + 返工回路建模 | 不是「一次额外加工」，见第二节 |
| 订单变更 | DD | 交期/数量变化 | 全量夜间重排 | 目标函数变了，局部改不动 |
| 检测 / 军检 | TS | 停点、窗口占用 | 预约型资源重排 | 外部资源的日历你控制不了 |
| ECN 工程变更 | ECN | **追溯在制品**：已开工的要不要停 | 影响面评估 + 人工决策 | 这是工艺决策，不是排产决策 |

### 三种响应手段的代价

```text
① 右移 Right-shift        顺序完全不变，只推后开工时刻
   成本最低、最稳定；缺点：计划会一路向前漂移，越漂越乐观

② 局部重排 Partial rescheduling   冻结窗口外、受影响工序内重排
   平衡选择。LISA 的 KPI「局部重排 ≤30min」「变更评估 ≤15min」就是在约束这一档

③ 全量重排 Full rescheduling      整盘重来
   质量最好、稳定性最差。同一批工单可能全部换顺序，车间会拒绝执行
   → 所以它的节奏应该是「夜间全量」，不是「实时」
```

**稳定性是有目标的，不是副作用。** 重排问题通常写成双目标：

```text
min  ( 新计划的质量   ,  新计划与旧计划的偏离度 )

偏离度常见写法：
  max_j |C'_j − C_j|          最大完工漂移
  Σ_j |C'_j − C_j|            总漂移
  Σ_j [顺序改变的对数]         机器内顺序翻转数（车间最讨厌这个）
  已下达 / 已开始工单的数量     硬冻结，不参与偏离计算
```

**只优化质量的重排系统一定会失败。** 它每天给出一个「更好但完全不同」的计划，
现场的反应是回到 Excel。这是 LISA 文档里「无限产能排产且逾期不重排」被列进 P0 的另一面：
不重排是错，乱重排也是错。

## 五、交互：一次扰动会传到多远

涟漪推演（LISA 要求 ≤15min 出 A/B 方案）和**重排**是两件不同的事，很多项目把它们混了：

| | 涟漪推演 | 重排 |
| --- | --- | --- |
| 目标 | 回答「影响面有多大」 | 生成新计划 |
| 算法 | 图上传播 + 最长路 + 缓冲扣减 | 求解器 / 局部搜索 |
| 时限 | **≤15 分钟，通常应 <1 分钟** | 30min ~ 2h |
| 是否写库 | **只读**，只出报告 | 走审批链才写 |
| 失败时 | 降级为「影响未知，需人工判断」 | 降级为右移 |

## 六、这一页的落地清单

1. **每个 `p_j` 存三个字段**：`p_nominal`、`p_std` 或分位数、`data_source`。
   只有均值的数据，鲁棒与缓冲都做不了。
2. **Γ 做成配置项，并且能在 UI 上调。** 让计划员自己选择保守程度，比你替他选更有效。
3. **返工用几何分布校正产能**，不要用「×1.4」这种拍脑袋的系数。
4. **重排分三档**（右移 / 局部 / 全量），并且**每档有时间预算和触发条件**，路由表进代码。
5. **目标里必须有稳定性项**。没有它，你的采纳率会掉——这是组织问题还是算法问题？都是。
6. **冻结窗口按工序域设**，不要全厂一个值。试车台架的锁 3 天和数控车的锁 3 天不是一回事。
7. **尾部优先**。用 95 分位承诺交期，用均值评估产能。混用的那天就是 OTD 崩的那天。
