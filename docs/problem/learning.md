# 学习与大模型：RL 与 LLM 能做到哪步

这一页最大的风险是我把它写成推销页或者写成否定页。所以先立规矩：
**每一句「能做」都给出证据类型，每一句「不能做」都给出失效条件。**

先给结论表，后面全是论证：

| 你期待它做的事 | 现实 | 证据强度 |
| --- | --- | --- |
| RL 端到端解出作业车间，质量超过 CP-SAT | **没有**。在训练分布内接近，在**没见过的实例规模/形状上明显退化** | 论文自报 + 泛化研究（Song 等 2023） |
| RL 学一条派工规则，比人写的规则稳 | **能**，尤其在多目标、动态到达的场景 | 长期文献（Park 等 2021 一类 GNN+DRL） |
| RL 选 ALNS 的算子 / 选分支变量 | **很能**，而且不要求你解释它 | 这是本手册最推荐 RL 落地的一处 |
| 机器学习估参数（工时、故障 ETA、合格率） | **这才是真正的金矿**。它给的是启发式和缓冲的输入 | 工业实践成熟 |
| LLM 把「人话需求」变成 MILP/CP 模型 | **能，但要人审**。基准上仍有可观错误率 | Chain-of-Experts / OptiMUS / ORLM 一系 |
| LLM 直接给排产方案（不用求解器） | **不能**。它会发明不存在的约束，也会忘掉你写进去的约束 | 见第四节的实测数字 |

## 一、强化学习：三种范式，三种命运

排产的 RL 论文汗牛充栋，但按**状态怎么表示**分，其实只有三类。
分类比选型重要——因为它决定了你的模型能不能在新产品上线时活下来。

| 范式 | 状态表示 | 动作 | 代表工作 | 命运 |
| --- | --- | --- | --- | --- |
| **特征 + RL** | 手工特征向量（剩余工时、队列长度、关键路径标记） | 选下一个派工的工件 | 早期 TD-Gammon 式尝试、大量 2000 年代工作 | 稳、可解释、天花板低。**今天很多「AI 派工」其实是这一类** |
| **图 + 深度 RL** | 析取图 / 工序图上的 GNN 嵌入 | 选工序、或选机器 | Park–Sim 等 2021（动态作业车间，AAAI 一系）；L2D（Zhang 等，NeurIPS 2021）把工序当作序贯决策 | **训练分布内很漂亮**；换规模、换工艺路线就退化 |
| **RL 当控制器** | 邻居是求解器，状态是搜索进度 | 选分支变量 / 选割 / 选算子 | NeuroCut、LLM4MIP 那一族 | **最被低估、最容易落地的一类**。不碰排产的正确性，只碰效率 |

::: warning 泛化是这类工作的阿喀琉斯之踵
调度实例之间的差异极大：产品换型、工艺路线调整、新设备导入，都会改变状态分布。
「在随机生成的 10×10 实例上训练，在 15×15 上测试」这类实验设定，
和真实厂里「今年 108 个核心产品 × 28 道工序，明年上 3 个新型号」完全不是一回事。
**任何承诺「学一次管三年」的 RL 排产方案，都要先问它在没见过的工序域上的表现。**
:::

### RL 真正该放的三个位置

1. **算子选择（本手册推荐指数最高）**。ALNS 里有一堆 destroy/repair 算子，
   用 contextual bandit / UCB 学「当前状态下哪个算子最可能改进」。
   见第六节可跑代码。这不需要端到端可微、不需要大量实例、失败也只是没改进。
2. **参数回归**。ATC 规则的方差参数 `h`、缓冲大小、Γ 预算、每台设备的实际节拍——
   **这严格说不是 RL，是监督学习，但它是排产里 ML 的 80% 价值**。
3. **派工层的实时决策**。设备空出来的那一秒要选下一个工件，规则太笨、全量重排太慢，
   RL 的策略网络毫秒出结果。位置是 A 级智能体的 Copilot 建议，不是执行者。

## 二、LLM-for-OR：把「人话」变成「模型」

大模型在排产里的**正确位置是建模层与解释层，不是求解层**。
这条边界不是理念，是过去几年基准测出来的。

| 系统 | 思路 | 值得知道的点 |
| --- | --- | --- |
| **NL4Opt** | 「自然语言 → 优化模型」的竞赛数据集 | 提供了可复现的评测底座，也暴露了准确率的天花板 |
| **Chain-of-Experts**（2024） | 多智能体 + MCTS，把建模拆成「专家子任务」，配 IndustryOR 真实工业题集 | 说明**流程编排**比单模型规模更有效 |
| **OptiMUS**（MIT，2024） | LLM 建模 + 调用 Gurobi/CPLEX 求解 + 复核 | 「让模型写模型，让求解器算答案」的标准形状 |
| **ORLM**（NeurIPS 2024 一系） | 用合成 + 真实数据微调开源 LLM，专攻 OR 建模 | 证明**微调小模型**在这类结构化任务上能打赢通用大模型 |
| **OptiGuide**（MIT） | 解完之后用 LLM 做解释与 what-if 分析 | **这是 LLM 在排产里最被低估的用法**：把影子价格翻译成人话 |
| **LLM4MIP**（2025） | 用 LLM **替换分支/割选择里的启发式规则**，配数据增广与 prompting | 定位准确：LLM 进的是「求解器的内部策略」，不是「问题的答案」 |
| **MASC / 反思式排产** 一类 | 多智能体 + 自反思处理现场扰动 | 方向对，但**公开可复现的工业验证很少**，看到这类名字请回源核对 |

## 五、什么情况下你根本不该上学习

1. **实例太少。** 一个新厂只有 3 个月历史数据，监督学习的方差比它的偏差还大。
   先用规则，攒数据，再说。
2. **规则就能打赢。** 这是最常发生的情况。**必须先有一个「规则基线」**：
   没有基线的 ML 项目无法证明自己有用，也无法在退化时发现。
3. **约束违规不可容忍。** 军工、医疗、航空：硬约束违背率必须为 0。
   学习型策略的输出是概率性的，它**必须**被一个确定性校验层包在后面。
4. **解释义务。** 「AI 决定的」不是一句能被接受的回答。若审计要求逐条归因，
   就把 RL/LLM 放在不影响结论的辅助位置（算子选择、取数、解释措辞）。

## 六、一个立刻能用的 RL：给 ALNS 挑算子

这是本手册唯一建议**现在就写**的强化学习：**contextual bandit 选 destroy/repair 算子**。
不需要环境模型、不需要大量实例、失败的最坏结果是「这一轮没改进」。

```python
import math, random

class OperatorSelector:
    """UCB1：按「历史改进率 + 探索奖励」挑 ALNS 算子。
       每个算子的 arm 记录 (成功改进次数, 被选次数)。"""
    def __init__(self, operators, c=1.5):
        self.ops = list(operators)
        self.wins = {o: 0.0 for o in self.ops}
        self.counts = {o: 0 for o in self.ops}
        self.c = c                      # 探索强度：越大越敢试冷门票

    def pick(self):
        total = sum(self.counts.values()) + 1
        def ucb(o):
            n = self.counts[o]
            if n == 0:
                return math.inf         # 没试过的先试一次，别让它永远进不了
            avg = self.wins[o] / n
            return avg + self.c * math.sqrt(math.log(total) / n)
        return max(self.ops, key=ucb)

    def update(self, op, improved, reward=None):
        r = (1.0 if improved else 0.0) if reward is None else reward
        self.wins[op] += r
        self.counts[op] += 1

# 模拟：三个算子，真实改进率 0.30 / 0.12 / 0.05，跑 3000 轮会怎样？
from collections import Counter

random.seed(0)
truth = {"critical_block": 0.30, "random_job": 0.12, "machine_move": 0.05}
sel, picks, hits = OperatorSelector(truth), [], 0
for _ in range(3000):
    op = sel.pick()
    picks.append(op)
    ok = random.random() < truth[op]
    hits += ok                                   # 真实发生了改进才算一次
    sel.update(op, ok)

c = Counter(picks)
print("被选次数：", dict(c))
print("最优算子占比：%.1f%%" % (100 * c["critical_block"] / len(picks)))
print("UCB 实际改进数：", hits)

random.seed(1)                                  # 对照：闭着眼睛随机选算子
random_hits = sum(1 for _ in range(3000)
                  if random.random() < truth[random.choice(list(truth))])
print("纯随机选的期望改进数：", random_hits)
```

实测输出（Python 3.12）：

```text
被选次数： {'critical_block': 2501, 'random_job': 318, 'machine_move': 181}
最优算子占比：83.4%
UCB 实际改进数： 768
纯随机选的期望改进数： 470
```

**同一个搜索骨架、同一批随机数流，只是换了「怎么挑算子」，改进次数从 470 涨到 768（+63%）。**
而且最差的算子并没有被彻底饿死——它还是被试了 181 次，
这正是探索项存在的意义：**如果现场变了（新设备、新产品），它能在几十轮内重新发现。**

这就是本手册推荐从这一处切入强化学习的原因：不需要环境模型、不需要海量实例、
失败的最坏结果是「这一轮没改进」，而且收益能用一个计数器说清楚。

三个必踩过的坑：

1. **`counts == 0` 必须返回 `inf`**，否则冷门票永远进不了竞争，UCB 退化成贪心。
2. **奖励不要用「目标值下降量」的原始值**（量纲会随进度变化，晚期算子永远吃亏）。
   用**相对改进率**或者归一化后的值。
3. **算子的性能会随搜索阶段漂移**（早期 `random_job` 有效，后期 `critical_block` 有效）。
   真要做，就加滑动窗口衰减——那时它就从 bandit 变成非平稳 RL，成本立刻上一个台阶。

## 七、务实的落地顺序

```text
第 0 步   规则基线：SPT / EDD / CR / ATC 写清楚，能一键复现，有指标
   ↓      （这一步 90% 的团队跳过，然后花三个月证明 ML 比「没基线」好）
第 1 步   参数回归：工时 / 合格率 / 维修 ETA。监督学习，输出进缓冲与模型参数
   ↓      收益立竿见影，风险最低
第 2 步   算子选择：本节的 bandit。嵌在 ALNS / LNS 里
   ↓
第 3 步   局部策略：派工层的 RL，只在冻结窗口外、只出建议
   ↓
第 4 步   LLM 交互层：取数、解释、建模助手 + 人工评审
   ↓
第 5 步   （可选）端到端 GNN+RL —— 只有前四步都跑通、且有几千实例的数据时才谈
```

::: tip 一条判断标准
任何「学习」组件，问三个问题就能决定要不要上：
① 它出错时，最坏结果是什么？（慢 / 质量差 / 违规 / 写错库）
② 有没有确定性兜底？（右移、规则解、SHACL 校验）
③ 有没有基线可以比较？（没有基线就不要上线）
第 ④ 个问题是：**能不能给它一个只读的接口面**。能，就上；不能，先想清楚。
:::
