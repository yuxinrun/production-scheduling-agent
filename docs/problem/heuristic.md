# 启发式与元启发式：现场真正在跑的

上一页讲「怎么算到最优」。这一页讲**车间里 95% 的排产实际是怎么出来的**：
一条排序规则，或者「规则 + 局部搜索」。

先说清一件事，因为它决定了你的架构：**启发式不是精确算法的降级版，是另一种产品**。
精确算法交付的是「证明」，启发式交付的是「经验」。现场对这两样东西的需求不一样：

| | 精确 | 启发式 |
| --- | --- | --- |
| 计划员信不信 | 「它说最优」——需要解释为什么 | 「一直是这么排的」——不需要解释 |
| 能不能复现 | 能（同一模型同一时限） | **要看随机种子** |
| 改一条规则 | 重跑，结果可能大变 | 直接改权重，行为可预期 |
| 上线成本 | 建模与数据 | **调参与回归** |

::: tip 真实项目里最常见的成功组合
**规则打底 + CP 精排 + 局部搜索改进 + 精确兜底（小窗口）**。
纯元启发式上线且活过一年的排产系统，比我预期的少得多。原因在本文第七节。
:::

## 一、调度规则：最便宜的启发式，也是带定理的那批

规则 = 给所有可排工序算一个 key，取最小（或最大）。就一行代码。
**但这一行代码背后有一批 1955 年就开始的正确性定理，值得你背下来——
因为它们是排产里少数的「免费午餐」。**

<DispatchLab
  eyebrow="互动 · 派工规则实验室"
  title="同一批活，六种规则六种命运"
  lead="改一改右边的加工时间、交期和权重，看哪个规则在哪个指标上赢。你会发现没有常胜将军——这就是多目标的入口。"
  glow="teal"
  note="单机、一台一个活、非抢占。所有指标都在下面六行甘特里实时重算。SPT / EDD / WSPT 的最优性只在单机成立；一旦是作业车间，它们全都只是启发式。"
/>

| 规则 | key（越小越先） | 最优性 | 出处 |
| --- | --- | --- | --- |
| FIFO / FCFS | 到达时刻 `r_j` | 无 | 车间默认行为 |
| **SPT** 最短加工时间 | `p_j` | `1‖ΣC_j` 与 `1‖平均流程时间` **最优** | Smith 1956（及 Conway–Levey–Maxwell 1967） |
| **SPT 变体** | `p_j` 降序 = LPT | 平行机 makespan 的 **(4/3 − 1/(3m)) 近似** | Graham 1966/1969 |
| **WSPT** 加权最短 | `p_j / w_j`（或 `w_j/p_j` 降序） | `1‖Σ w_j C_j` **最优** | Smith 1956 |
| **EDD** 最早交期 | `d_j` | `1‖L_max` **最优** | Jackson 1955 |
| **Moore–Hodgson** | EDD 排，遇逾期就踢掉当前最长的一个 | `1‖ΣU_j`（逾期**个数**最少）**最优** | Moore 1959 / Hodgson 1966 |
| **CR** 关键比率 | `(d_j − t) / p_j` | 无（动态版 EDD，现场最常用之一） | — |
| **ATC / SL Lack** | `−exp(−(d_j − p_j − t)/h) · (w_j/p_j)` | 无，但**对机器方差敏感时表现极好** | Lee–Pinedo–Scudder 1993 |
| Johnson | 两机流水：短的排两头 | `F2‖C_max` **最优** | Johnson 1954 |
| 关键路径规则 | 优先动关键路径上的工序 | 无 | 一堆实现 |

三条要记住的「但是」：

1. **每一条最优性定理都带 `1‖` 前缀。** 一旦有紧前约束、多台机器、或者两个目标同时存在，
   它立刻降级成启发式。别把「SPT 最小化平均流程时间」印在你的产品页上，
   而你的实际场景是 `Jm|prec|Σw_jT_j`。
2. **规则之间互相打架。** SPT 让平均在制漂亮但可能压死急件（交期远的短件插队）；
   EDD 保最大延期但对长件毫无办法。这就是为什么「按什么排」永远是政治问题。
3. **动态规则要用当前时刻。** CR 和 ATC 的 key 随 `t` 变，所以它们是**事件驱动**的：
   每次有设备空了就重新算一遍。写成「早上排一次全天」的 CR 不是 CR。

::: details 为什么 ATC 里有个指数项（这是唯一一个值得看的规则公式）
`ATC_j = exp(−(d_j − p_j − t)/h) · p_j / w_j`，取最小。
`h` 是**方差参数**：现场加工时间的不确定程度。
直觉是——离交期越远，这个工件的「紧迫度折扣」越接近 0；一接近交期就指数上涨。
`h → ∞` 时它退化成 WSPT，`h → 0` 时退化成「谁最紧急排谁」。
**为什么这对你有意义：** 你的系统里 `h` 应该是**测出来的**，不是拍出来的。
拿历史报工数据算每条工序的 `实际/预估` 方差，直接给 `h`。
LISA 那类项目里「标准工时缺失或不准」是 P0 问题，本质就是在说这个参数拿不到。
:::

## 二、LPT：少数能给你证明的启发式

平行机 `Pm‖C_max` 是排产里最容易讲清的近似例子。
**LPT（Longest Processing Time first）**：把活按从大到小排序，每次都丢给当前负载最小的机器。
复杂度 `O(n log n)`，而且它有**上界**。

```python
import itertools

def lpt(jobs, m):
    """最长优先：每个活丢给当前负载最小的机器。"""
    loads = [0] * m
    for j in sorted(jobs, reverse=True):
        k = min(range(m), key=lambda kk: loads[kk])
        loads[k] += j
    return max(loads)

def brute_opt(jobs, m):                       # 只有小规模才敢穷举：m^n
    best = None
    for a in itertools.product(range(m), repeat=len(jobs)):
        loads = [0] * m
        for j, k in zip(jobs, a):
            loads[k] += j
        best = min(best or float("inf"), max(loads))
    return best

for jobs, m in [([4, 4, 3, 3, 3, 3, 3], 2), ([2, 2, 2, 2, 3, 3, 3], 3),
                ([5, 4, 4, 3, 3, 3, 3, 3, 3], 2)]:
    ub, opt = lpt(jobs, m), brute_opt(jobs, m)
    naive_lb = max(sum(jobs) / m, max(jobs))
    bound = 4 / 3 - 1 / (3 * m)
    print(f"m={m} LPT={ub}  OPT={opt}  真实比值={ub/opt:.3f} (理论上界 {bound:.3f})")
    print(f"      朴素下界={naive_lb:.2f}  → 你会向老板报告的间隙={100*(ub-naive_lb)/ub:.1f}%")
```

实测输出（Python 3.12）：

```text
m=2 LPT=13  OPT=12  真实比值=1.083 (理论上界 1.167)
    朴素下界=11.50  → 你会向老板报告的间隙=11.5%
m=3 LPT=7  OPT=6  真实比值=1.167 (理论上界 1.222)
    朴素下界=5.67  → 你会向老板报告的间隙=19.0%
m=2 LPT=17  OPT=16  真实比值=1.062 (理论上界 1.167)
    朴素下界=15.50  → 你会向老板报告的间隙=8.8%
```

**这张表里最重要的信息在最后一行。**
LPT 的真实比值从没超过理论上界，但你用「总工时 ÷ 机器数」这个朴素下界算出来的间隙，
是真实值的 **2~3 倍**。原因很简单：`max(Σp/m, max p)` 是 `OPT` 的下界而不是 `OPT` 本身，
它比 `OPT` 更小，所以 `UB − LB` 更大。

> **推论**：报告的间隙永远包含两部分——
> ① 你的解离最优有多远（这一部分靠更强的下界可以缩小），
> ② 最优离你的下界有多远（这一部分是问题本身，缩不掉）。
> 计划员看到「间隙 19%」会以为系统很差，实际是「你的下界很弱」。
> 这是 [下界与间隙](/problem/bounds) 那一页的主题。

/>

**Shifting Bottleneck（动态瓶颈）** 值得单独讲，因为它是「启发式 + 精确算法」的样板：

```text
1. 暂时只考虑工艺路线，算出每台机器的「松弛」问题（各工序的 est / lst）
2. 对每台机器解一个 1 | r_j, q_j | C_max —— 这是 Carlier 1982 的分支定界，单机、能算到最优
3. 挑使 makespan 增量最小的那台机器（瓶颈），把它的优化顺序「固化」进图
4. 重复 2~3，直到所有机器都排完
5. 反复迭代直到无改进
```

它好在三点：**每步都精确求解一个小问题**、**天然给出「哪台机器是瓶颈」这个解释**、
**规模能上到几百道工序**。它坏在一点：一次只动一台机器，容易卡在局部。

## 四、元启发式：四大家族怎么选

| 家族 | 记忆 | 并行性 | 参数 | 可解释 | 什么时候选它 |
| --- | --- | --- | --- | --- | --- |
| **模拟退火 SA**<br>Kirkpatrick 1983；Van Laarhoven–Aarts–Lenstra 1992 用于 JSP | 无 | 容易（多链） | 少（初温、降温率、终止） | 差 | 邻域设计好了、想要一个稳的改进器 |
| **遗传 / 进化 GA·NSGA-II**<br>Holland 1975；Deb 2002 | 种群 | **最容易（岛屿模型）** | 多（交叉/变异/种群/选择） | 差 | 多目标、要一堆非支配解给计划员挑 |
| **禁忌搜索 TS**<br>Glover 1986；Nowicki–Smuta 1996 用于 JSP | 禁忌表 | 难 | 中（禁忌长度、候选数） | **中**（能说「因为刚动过」） | 单目标、需要强局部改进、有好的邻域 |
| **大邻域搜索 LNS / ALNS**<br>Shaw 1998；Ropke–Pisinger 2006 | 算子自适应权重 | 容易 | 少（算子集） | **好**（每次改动 = 摧毁一段 + 重建一段） | **今天多数新项目的默认选择** |
| 变邻域 VNS / 迭代局部搜索 ILS / GRASP | 视具体 | 容易 | 少 | 中 | 想省事、想要多种子投票 |

::: warning ALNS 的名字要写对
Ropke 与 Pisinger 2006 提出的是 **Adaptive Large Neighborhood Search**。
它胜出的原因不是聪明，是**工程性**：算子（destroy/repair）可以单独写、单独测、单独开关，
每个算子的历史表现还能自适应加权。相比之下 GA 的「交叉」在排产里既难定义又难解释。
:::

## 五、邻域设计 > 算法选择（这是本页唯一要你记住的一句）

**「换哪种元启发式」几乎不重要；「允许动哪几个工序」才重要。**

作业车间局部搜索的第一定理（Balas–Vazacopoulos 1994 等一系列工作）：

> **不改动关键路径的顺序，makespan 不会变短。**

于是任何「随机交换两个工序」的邻域，绝大多数采样是**白做的**——
它们落在非关键弧上，目标值纹丝不动，你的搜索全在平地上打转。

真正有用的邻域（按性价比排）：

| 邻域 | 定义 | 为什么有效 |
| --- | --- | --- |
| **关键块内相邻交换** | 把关键路径切成若干「块」（同机连续段），只在块内交换相邻两个 | Nowicki–Smuta 1996：块首/块尾的特定交换就足以覆盖改进方向。邻域从 `O(n²)` 缩到 `O(n)` |
| **块端点插入** | 把块头/块尾的工序插到块内其他位置 | 打破块结构，能跳出纯交换的局部最优 |
| **机器重指派** | 把一道柔性工序换到另一台机器 | FJSP 必备，通常和排序邻域交替使用 |
| **段反转（block move）** | 块内一段整体倒序 | 一次改动可控、易解释「我把这三件调了顺序」 |
| **LNS 摧毁/重建** | 随机挑一个工件（或一个时间窗内的全部）摘掉，用规则重插 | 每次改动都是**一小片重排**，天然对应现场「局部重排 ≤30min」的需求 |

```python
# 关键块相邻交换的最小可用局部搜索：makespan 目标，作业车间
# 1) 在析取图上跑最长路，得到关键路径  2) 只在关键路径的「块」内交换相邻工序  3) 改进就接受
def critical_blocks(schedule):
    """返回关键路径上按同机分段后的块列表：[(machine, [op_i, op_j, ...]), ...]"""
    # 实现要点：
    #   head[o] = 源点到 o 的最长路；tail[o] = o 到汇点的最长路
    #   o 在关键路径上 ⟺ head[o] + p_o + tail[o] == makespan
    #   同机器上连续的关键工序合成一个块
    ...

def local_search(schedule, time_budget_s=20):
    start = time.monotonic()
    best = schedule
    while time.monotonic() - start < time_budget_s:
        improved = False
        for machine, block in critical_blocks(best):
            for i in range(len(block) - 1):
                cand = best.swap_on_machine(machine, block[i], block[i + 1])
                if cand.feasible() and cand.makespan() < best.makespan():
                    best, improved = cand, True
                    break
            if improved:
                break
        if not improved:
            break                     # 邻域走空 → 局部最优
    return best
```

三个必须做对的细节：

1. **可行性检查不是可选的。** 关键块交换**可能**造出环（`i` 在 `j` 前 + 工艺路线要求 `j` 在 `i` 前）。
   交换前查一次受影响的最长路，比交换后修复便宜。
2. **增量评估。** 每次重算全图最长路是 `O(n)`，一次局部搜索要做上万次；
   实际实现只重算受影响节点的 `head`。这一步做不好，元启发式比精确算法还慢。
3. **终止判据写成「时间 + 无改进」两个**。只看时间会让你的结果随机器负载漂；
   只看无改进会在大邻域上跑到天荒地老。

1. **可复现。** 固定随机种子 + 固定时间预算 + 记录求解器版本。
   你的验收测试要能回答「上周三那个方案为什么今天复现不出来」。
2. **回归。** 元启发式没有「正确性」只有「统计上的好坏」。
   所以你需要**留一个基准测试集**（历史实例 + 已知解），每次改代码就跑，比较总改进与最坏退化。
   这件事在 [评测：影子模式与人机分歧](/build/eval) 里详细讲。
3. **可解释。** 输出的不能只是新甘特，必须有「改了什么 / 为什么改 / 影响哪些工单」。
   LNS 天然好解释（摧毁段 + 重建），GA 天然最差。这是选型时最被低估的一条。
4. **兜底。** 元启发式最坏情况是没有可行解或者质量崩掉。
   必须有一条永远能出的**规则解**（比如 right-shift 当前计划），
   以及一个「质量低于阈值就放弃本次改动」的熔断。见 [写保护、熔断与降级链](/arch/guardrail)。

## 七、LISA 项目里的启发式长什么样

从真实交付文档里能读出这套配置（**注意：这是这一家厂的选择，不是通用答案**）：

- **原子级智能体 A-01~A-07**：各工序域内的排产，具体技能里明确写着**组批合炉、换型优化、瓶颈保护、
  齐套联动、台架窗口、返工回路、不确定性区间排程**——七种都是「域内构造式 + 局部改进」的形状。
- **支撑技能是小模型，不是大模型**：GBDT 估工时、GPR 估满炉率、贝叶斯网络估返工、
  生存分析估维修 ETA。它们给的是**启发式的参数**，不是启发式的解。
- **形态四档**：采纳率 <60% 只做观察，60~75% 出建议，75~85% 半自主，≥85% 才自主执行。
  这条阶梯意味着启发式的输出**默认不写库**——写权限是逐级挣来的。
- **验收 KPI**里没有任何一条是「最优解」：采纳率 ≥85%、夜间全量重排 1~2h、
  变更评估 ≤15min、局部重排 ≤30min、齐套率 60%→100%。
  **全是关于速度与信任的指标。** 这份合同本身就是对「启发式 vs 精确」这个问题最好的回答。

::: warning 一个我没法核实的点
上面这些能力（GBDT 工时预测、GPR 满炉率、贝叶斯返工网络）在交付文档里是**规划项**，
不是已验证的实测精度。文档里同时写着「虚拟设备人员负荷未核实」「维修时间预估不准」。
所以别把它们读成「这套小模型已经能用了」——那是一条待办，不是一个成果。
:::
