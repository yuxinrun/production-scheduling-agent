# 精确算法：分支定界、割平面、约束传播

「精确算法」的意思不是「一定算得出最优」，是**只要它说最优，那就是最优，并且它可以给你证明**。
这条区别决定了你什么时候该为它付钱。

所有精确算法都是同一句话的变体：

> **不断把「所有可能的解」切成小块，每块要么算出一个具体解，要么用一个界证明整块不值得再算。**

排产里最有名的分支定界是 **Carlier–Pinson（1982/1984）** 对单机问题
`1 | r_j, q_j | C_max` 的算法。为什么单机算法能解作业车间？
因为作业车间的每个子问题就是一台机器上的排序，而每台机器上的排序正是这个单机问题——
它也是 **Shifting Bottleneck** 启发式的内燃机，见 [启发式与元启发式](/problem/heuristic)。

```text
1 | r_j, q_j | C_max    ← 每台机器一个实例
     r_j = 工序 i 的最早开始时刻（来自紧前传播）
     q_j = 工序 i 之后剩余的关键路径长度（tail）
```

`r_j` 与 `q_j` 都来自**析取图上的最长路计算**，这就引出下一节。

## 二、析取图：排产问题的图形真相

作业车间的经典表示是 **Roy–Sussmann 析取图（1964）**：

- 节点 = 工序（外加虚拟源点 `S` 与汇点 `T`）
- **合取弧**（conjunctive）：同一工单的紧前关系，方向固定，权 = 加工时间
- **析取弧**（disjunctive）：同一机器上的两个工序，**方向未定**，必须二选一

```text
        合取弧（工艺路线，方向已定）      析取弧（同机竞争，方向待定）
  o ────────────────────────► o          o ◄─────────────────────► o
                                          （选一个方向 = 决定谁先做）

一个可行排程  ⟺  把所有析取弧定向后，图上无正权环（无环）
makespan      ⟺  定向后图中 S → T 的最长路径
```

两个立刻可用的结论：

1. **makespan = 关键路径。** 所以「降低 makespan」的唯一有效动作是**改变关键路径上的顺序**——
   非关键路径上的任何改动都不会让解变好。这条推论能把你 90% 的搜索剪掉。
2. **分支 = 给一条析取弧定向。** 分支变量天然就是「哪两个工序的先后还没定」，
   而不是「某个 0/1 变量等于几」。这就是为什么调度专用的分支策略比通用 MILP 分支强得多。

::: warning 「无环」是个硬约束，别用罚函数绕过
析取弧定向出现环 = 这个方案在物理上不可能执行（A 在 B 前 + B 在 A 前）。
如果你把「不许重叠」写成大 M 的软约束，求解器**有可能**给你一个带环的方案——
它违反罚函数最小化的方向，但大 M 不够大时它就会这么干。
排产里「同机不重叠」必须是硬约束或者 `NoOverlap`，没有例外。
:::

## 三、传播：不求解也能砍掉 99% 的分支

这是约束规划（CP）真正的武器，也是**排产里投入产出比最高的一段代码**。
传播（propagation）不改变目标、不做假设、**结论一定是真的**，所以它永远安全。

| 技术 | 出处 | 说什么 | 强度 |
| --- | --- | --- | --- |
| **区间界传播** | 基本 | `start ≥ earliest`，`end ≤ latest`，沿紧前弧做最长路 | 必做，几乎免费 |
| **Not-First / Not-Last** | El Baggadi 等 | 若工序 `i` 无论如何都不能是同机上的第一个/最后一个，抬高/压低它的界 | 便宜，常有惊喜 |
| **Edge-Finding** | Baptiste–Le Pape，1996 | 若 `i` 的最晚完工 ≤ `j` 的最早开始，则 `i` 必定排在 `j` 之前——**即使它们中间还有别人** | 强，经典 O(n log n) |
| **能量推理**<br> Energetic Reasoning | Baptiste–Cousté–Tchernaïtchanski | 时间窗 `[est, lst]` 内必须消耗的能量 `Σ p_j` 不能超过该窗内机器的可用产能 → 反推每个工序必须被推迟/提前的量 | 最强也最贵；对**紧负荷**窗口极有效 |
| **时间窗重叠检测** | — | 两个工序的强制时间窗相交且都必须独占机器 → 直接判不可行 | 最便宜的剪枝 |
| **累计资源剪枝** | `Cumulative` | 同一时刻所有可选区间的需求和 ≤ 容量，做平衡检测 | 人/工装/能源约束必用 |

能量推理的直觉（这是唯一一行值得背的公式）：

```text
对任意时间窗 [t1, t2]：
    强制能量  E_req(t1,t2) = Σ_{est_j ≥ t1 且 lst_j + p_j ≤ t2} p_j
                            + Σ_{跨窗的工序} (必然落在窗内的部分)
    可用能量  E_avl(t1,t2) = (t2 − t1) × capacity          （扣掉日历停机）

    若 E_req > E_avl  →  当前域不可行，直接剪掉
    否则 → 反解出每个工序最早必须推迟多少，收紧它的 est
```

::: tip 为什么「先建模约束再谈优化」是对的
上面的每一项都在**不做任何目标假设**的情况下缩小搜索域。
这意味着：即使你的目标函数写错了、权重拍得乱七八糟，传播仍然是有效且无害的。
反过来，如果你的模型缺了约束，再聪明的目标函数也救不了。
现场最常见的排产求解慢，原因前三名是：**日历没进模型**（[建模那一页](/problem/model) 的 bug #1）、
**时间窗太宽**（没有先跑一遍前向/后向传播）、**big-M 太大**（把硬约束写成了松弛）。
:::

## 四、割平面：从线性松弛里切出整数

**Gomory 割（1958）** 的思想：线性松弛的最优解是分数（比如 3.5 件产品），
从单纯形表里那一分数的行推出一条**对所有整数解都成立、但把这个分数点排除掉**的线性不等式，
加进去重新解。反复做，直到解是整数。

单靠割平面几乎不可能收敛，所以今天的形式是 **branch & cut**：
分支定界的框架 + 每个节点上切几刀。

排产里最有用的两种「割」，其实更像**预处理**：

- **Crowder–Padberg 预处理（1980）**：在建模阶段用变量上界收紧系数
  `a_ij ← min(a_ij, b_i)`，并把大 M 缩到实际可达的范围。这不算割，但它常常把 LP 松弛质量提高一个档次。
- **析取推理割**（disjunctive cuts / balance cuts）：同机两工序要么 A 先要么 B 先，
  据此推出一条对两个分支都成立的线性不等式——
  等于**不用分支就把两个子问题的界合并**。Carlier–Dyer 界、`sum of processing times` 类界都是这一族的亲戚。

::: details 为什么「LP 松弛紧不紧」是个大问题
LP 松弛的最优值是 MILP 里最好的下界来源之一。
同一个排产问题，两种建模方式的 LP 松弛可能差 40%：
时间索引模型（`x[o,k,t]`）的 LP 松弛通常非常紧，但变量数是 `操作 × 机器 × 时段`；
big-M 析取模型的松弛几乎没用（M 一大，`y` 取 0.5 就能骗过约束），但变量数少一个数量级。
**紧界 vs 少变量**——这是建模时的核心权衡，也是为什么大项目会同时留两个模型做对照。
:::

## 五、CP-SAT 为什么今天能打

CP-SAT（Google OR-Tools）在 2020 年代把「精确算法」这词重新定义了。
它的关键不是「约束规划」这四个字，是三件事叠在一起：

1. **CDCL 式的冲突学习**（借鉴 SAT 求解器，Ohrimenko–Stückrath–Wunderlich 2009 把 lazy clause generation 与 MIP 结合）：
   搜索里失败一次，就把「为什么失败」学成一条子句，永久剪掉同类分支。
   这是它和传统 CP 最大的差别——**传统 CP 不学习，CP-SAT 学**。
2. ** portfolios / 多 worker**：`num_search_workers=8` 起，8 个线程跑不同的搜索策略与不同的随机种子，
   谁先出界谁更新。排产实例的方差极大，portfolio 是稳赚的设计。
3. **内建 LNS**（Large Neighborhood Search）：拿到可行解后，随机冻结一部分、重解剩下的。
   每个改进都会更新上界 → 剪枝更狠。**这让它同时是精确算法和元启发式**。

战绩（这些数字是公开可查的，引用前建议回源核对）：
2021 年前悬了 30 多年的 JSPLib 算例 `la21`（15×10）被 Perron–Refalo 的 CP-SAT 推到最好已知值 1046，
`ft20` 的 1165 也是同一批工作——**用的是开源 Apache-2.0 的求解器，不是商业授权**。

```python
# 带 gap 日志的 CP-SAT：这才是生产环境该有的写法，不是 Solve() 一行完事
from ortools.sat.python import cp_model

model = cp_model.CpModel()
# ……建模见上一页的 FJSP 片段……
model.Minimize(makespan)

solver = cp_model.CpSolver()
solver.parameters.max_time_in_seconds = 600
solver.parameters.num_search_workers = 8
solver.parameters.log_search_progress = True          # 求解器自己的统计，值得读

class Reporter(cp_model.CpSolverSolutionCallback):
    def __init__(self, target):
        super().__init__()
        self.__target = target
        self.__last_gap = None
    def on_solution_callback(self):
        ub = self.ObjectiveValue()
        lb = self.BestObjectiveBound()
        gap = 100 * (ub - lb) / max(1, ub)
        if self.__last_gap is None or gap < self.__last_gap - 0.05:
            print(f"[{self.WallTime():6.1f}s] UB={ub:.0f}  LB={lb:.0f}  gap={gap:4.1f}%")
            self.__last_gap = gap
        if gap <= self.__target:                       # ← 达到目标间隙就收手
            self.StopSearch()

status = solver.Solve(model, Reporter(target=1.0))
if status == cp_model.OPTIMAL:
    print("证明最优，无间隙")
elif status == cp_model.FEASIBLE:
    print(f"这不是最优，只是可行。gap = {100*(solver.ObjectiveValue()-solver.BestObjectiveBound())/solver.ObjectiveValue():.1f}%")
else:
    print("无可行解。先怀疑模型写错了，再怀疑产能真的不够")
```

这段代码里的三行，比算法选择更能决定你的系统能不能上线：

- **`StopSearch()` 按间隙停**：你的 SLA 应该写在 gap 上（「gap ≤ 1% 或 10 分钟，取先到」），不是写在时间上。
- **`FEASIBLE` 与 `OPTIMAL` 走不同的 UI 分支**：前者必须在页面上写明「未证明最优，最多比最优差 x%」。
- **无可行解 ≠ 产能不足**。默认假设是「模型约束写错了」，因为人工计划每天都在执行——
  见 [建模四步 Checklist](/problem/model) 里那条最便宜的模型校验。

## 六、我的规模能不能精确解？

这不是「NP-hard 吗所以不能」的问题。实际取决于三个数：**工序数、机器数、时间窗宽度**。

| 规模 | 现实预期 | 该怎么做 |
| --- | --- | --- |
| ≤ 30 工序，单机或平行机 | 秒级到分钟级，通常能证明最优 | 直接 CP-SAT / MILP，别上启发式 |
| ≤ 150 工序，作业车间（JSPLib 的 la 系规模） | 分钟级到小时级；`la` 系部分算例至今没被证明最优 | 时限 + gap 停止；准备好「未证明」的措辞 |
| 20 × 20（`ft20` / `yn` 系） | **世界级求解器跑几小时仍可能留 gap**；`yn1–yn4` 至今 0/4 被证明 | 这就是「你要最优」这句话的物理上限。改用启发式 + 报告相对历史基线的改进 |
| 500 ~ 5000 工序（一个中型厂的夜间全量） | 全局精确基本不可能 | 分解：按工序域切块 + 拉格朗日协调跨块共享资源 + 域内精确 |
| > 10⁴ 工序 | 只有分层与滚动 | 冻结窗口内精确、窗口外粗排，见 [性能](/build/perf) |

::: warning 上面这张表有一个前提
它假设你的约束是「教科书形状」（紧前 + 同机不重叠 + 时间窗）。
一旦加上**序列相关换型 + 批处理炉子 + 人员累计资源 + 细碎日历**，
同样的规模数字会掉一到两个档次。真实项目里，把工序数从 1000 砍到 300（一次只重排一个域）
通常比换求解器有效得多。
:::
