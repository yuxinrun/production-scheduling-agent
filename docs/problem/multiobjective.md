# 多目标：Pareto、ε-约束、字典序

排产需求文档里一定会有这一句：**「交期、成本、设备利用率、加班，都要兼顾。」**
这句话的数学后果，就是这一页。

先给三个结论，后面全部用来证明它们：

1. 「都要」不是一个目标函数，是**一组解**。你交付的必须是集合，不是单个方案。
2. **加权求和会系统性漏掉前沿上的一部分解**——不是「近似」，是数学上永远取不到。
   本页有个可复现的例子：10 个非支配解里，扫 201 组权重只能命中 4 个。
3. 把多目标问题做成产品的方式不是「找到正确的权重」，
   是**让计划员在前沿上选点**，并且系统记住他选了哪个。

---

## 一、支配、前沿、理想点：三个词说清

```text
解 A 支配 解 B   ⟺   A 在所有目标上不差于 B，且至少在一个目标上严格更好

Pareto 前沿      =   所有「不被任何解支配」的解
理想点           =   每个目标各自最优时的那个点（通常是不可达的）
```

一个必须会算的漏斗（下面第七节有完整可跑代码）：

| 层 | 数量 | 含义 |
| --- | --- | --- |
| 全部排列 | 720 | 6 个工件的单机排序 `6!` |
| 不同的**目标向量** | 344 | 很多顺序给出同样的 (ΣCj, ΣwjTj) |
| **非支配**的点 | **10** | 真正的 Pareto 前沿 |
| 加权求和能取到的 | **4** | 剩下 6 个是「unsupported」，**换多少权重都拿不到** |

**从 720 到 10**：前沿是很小的集合，这是好消息——它可以完整呈现给人看。
**从 10 到 4**：这是坏消息，而且是加权求和的结构性缺陷，不是调参不到位。

## 三、三条降维路线，和它们的数学后果

| 方法 | 怎么写 | 能保证什么 | **代价**（重点看这列） |
| --- | --- | --- | --- |
| **加权求和** | `min Σ α_k f_k(x)`，`α ≥ 0, Σα = 1` | 每个 α 给一个非支配解；α 全正 ⇒ 严格非支配 | **只能取到凸包上的 supported 解**。前沿非凸时，中间那些点无论怎么调权重都取不到（本例 6/10）。多目标 <span class="psa-chip">Das–Dennis 1997</span> 系统讨论过这个盲区 |
| **ε-约束** | 一个目标进函数，其余变成 `f_k(x) ≤ ε_k` | **能取到非凸前沿点**，只要 ε 选得对 | ε 太紧 ⇒ 不可行；ε 太松 ⇒ 退化成一个目标。要生成整条前沿得**扫 ε**，且不能靠等距扫（会留空洞） |
| **字典序** | 分层求解：第一层最优解作为第二层的约束 | 优先级严格，解唯一、可解释 | **一步排错，全盘皆输**。第一目标的最优解集合可能非常冗余，第二层在里面挑到的「好解」在第一层看是任取的 |
| **理想点法 / 切比雪夫** | `min max_k (f_k(x) − f_k^ideal)/(f_k^nad − f_k^ideal)` | **也能取到非凸点**，且天然给一个「离理想点多远」的分数 | 需要先用单目标解算出理想点与反理想点（多跑几次求解）；对归一化敏感 |
| **模糊满意度** | 给每个目标一个隶属函数，最大化满意度 | 现场最喜欢，因为「满意度 82%」听得懂 | 隶属函数形状是人定的——**你把政治写进了数学，但看起来像科学** <span class="psa-chip">Bellman–Zadeh 1970</span> |

::: warning 加权求和漏点这件事，实践中被低估
大多数人以为「权重调得够细就扫全了」。本页的例子里扫了 **201 组权重**，仍然只命中 10 个里的 4 个。
根因不是精度，是**几何**：加权超平面只能贴住前沿的凸包外侧。
在排产里前沿通常**不是凸的**——因为拖期有 `max(0, ·)`，在「刚好不拖期」那个拐点前后，交换比突变。
**结论：想用加权扫前沿的，改用 ε-约束或切比雪夫。**
:::

## 四、ε-约束是排产里最好用的那一个

因为它和现场的话对得上。现场不说「最小化 0.4×交期 + 0.6×成本」，
现场说：**「拖期不许超过 20 小时，在这个前提下把设备负荷做平。」**
这句话**就是** ε-约束，一个字都不用改。

```python
# CP-SAT 里的 ε-约束前沿扫描：一个目标进函数，另一个当约束
from ortools.sat.python import cp_model

model_proto = build_model(jobs, machines)     # 见建模那一页
obj1 = make_objective(model_proto, "tardiness")   # 加权拖期
obj2 = make_objective(model_proto, "workload")    # 机器负荷

def solve_with_epsilon(eps=None):
    """eps=None 表示只最小化拖期；否则要求拖期 ≤ eps，最小化负荷。"""
    m = model_proto.clone()                        # 每次重建，别在旧模型上加约束
    o1, o2 = m.objective_tardiness, m.objective_load
    if eps is None:
        m.Minimize(o1)
    else:
        m.Add(o1 <= eps)                           # ← 这就是「拖期不许超过」
        m.Minimize(o2)
    s = cp_model.CpSolver()
    s.parameters.max_time_in_seconds = 20
    st = s.Solve(m)
    if st in (cp_model.OPTIMAL, cp_model.FEASIBLE):
        return s.Value(o1), s.Value(o2)
    return None

# 第一步：先把两个目标各自的最优跑出来，拿到区间（也是理想点与反理想点）
t_min, t_at_t = solve_with_epsilon(None)           # 拖期最优 → (t_min, ?)
_, l_min = None, None
m = model_proto.clone(); m.Minimize(m.objective_load)
s = cp_model.CpSolver(); s.parameters.max_time_in_seconds = 20
s.Solve(m); l_min = s.Value(m.objective_load)
l_at_t = None
m = model_proto.clone(); m.Minimize(m.objective_load)   # 负荷最优时的拖期
s.Solve(m); l_at_t = s.Value(m.objective_tardiness)

# 第二步：沿拖期方向扫 ε。步长用「整数目标的自然步长」，不要用等距百分比
frontier = []
eps = t_min
while eps <= t_at_t:
    r = solve_with_epsilon(eps)
    if r and (not frontier or r != frontier[-1]):
        frontier.append(r)
    eps += max(1, (t_at_t - t_min) // 20)          # 20 步左右扫完

for t, l in frontier:
    print(f"拖期上界 ε={t:>4}  →  加权拖期={t:>4}  负荷={l:>4}")
```

三个实现细节，都是踩过才知道的：

1. **每次重新 clone 模型**。在同一个模型上反复加 `Add(o1 <= eps)`，约束会累积，
   第二次扫的时候直接不可行——这是 ε-约束最常见的 bug。
2. **别用等距百分比扫 ε**。整数目标的可行值常常很稀疏，等距扫会大量撞车（同一个解重复命中），
   还会在前沿的陡峭段留下空洞。做法：先用两端点定出区间，再按 `区间/20` 起步，
   命中的解重复就跳过。
3. **不可行的 ε 不是失败，是信息**。「拖期压到 12 小时时，负荷不可能低于 X」——
   这句话本身就是给计划员的答案，而且是唯一诚实的答案。

## 五、算法层的选项（什么时候需要真正的多目标算法）

前沿点不多（本例只有 10 个）时，**ε-约束循环就够用**。
点多了（目标 > 3、或前沿稠密到上千个）才需要动用进化族：

| 算法 | 一句话 | 在排产里的实际使用 |
| --- | --- | --- |
| **NSGA-II**（Deb 2002） | 非支配排序 + 拥挤度，维护稠密前沿 | 最流行，但**目标 ≥ 4 时拥挤度失效**，前沿退化成「只剩两端」 |
| **NSGA-III**（Deb–Jain 2013） | 用参考点取代拥挤度，专治高维目标 | 4~8 个目标时用这个 |
| **MOEA/D**（Zhang–Li 2007） | 把多目标分解成一组**单目标**子问题协同优化 | 概念上和 ε-约束是近亲，大规模时更稳 |
| **PALETTE / 交互式** | 让人在前沿上逐步表态，系统只算他关心的那一段 | **最适合做产品**：算得少、答得准、现场接受度高 |

::: tip 一个反直觉的建议
**先假设你要的目标数 ≤ 2**，用 ε-约束。
每多一个目标，前沿从一条线变成一个面，再变成高维流形——
可视化、解释、选择成本全部指数上升，而计划员做决策时**通常还是只看两三个**。
需求里写了 6 个目标时，先问「哪 2 个是你真正会用来拍板的」，剩下 4 个降级为**约束**。
这一步能把 6 目标问题变回 2 目标问题，是全手册性价比最高的一次简化。
:::

## 六、把前沿做成产品：这才是这一页的重点

求解器给你一个前沿，用户面对的是「10 个方案选哪个」。
这一步没做好，前面所有数学都白干——因为计划员会在 30 秒内关掉你的页面去打电话。

/>

三条 UI 层面的硬要求：

1. **不要显示「综合得分」。** 一个加权出来的分数会把前沿压成一个排序，
   等价于你偷偷替用户选了加权求和，还漏掉了 6/10 的解。
2. **显示支配关系，不显示排名。** 「方案 3 在两个指标上都不如方案 2」是可验证的；
   「方案 3 得分 87」不是。
3. **让「驳回」和「改成什么」一起记录。** 只记采纳率没有信息量；
   记「他把炉子那三个批次拆开了」才知道你的哪条约束或哪个权重错了。

## 七、可复现代码（本页图表的数据源，实测过）

```python
import itertools

P = [9, 6, 4, 3, 4, 5]        # 加工时间
D = [23, 28, 33, 28, 28, 9]   # 交期
W = [3, 2, 2, 6, 1, 1]        # 权重
n = len(P)

pts = {}                       # (ΣCj, ΣwjTj) -> 第一个到达它的顺序
for perm in itertools.permutations(range(n)):
    t = sumC = sumWT = 0
    for i in perm:
        t += P[i]; sumC += t
        sumWT += W[i] * max(0, t - D[i])
    pts.setdefault((sumC, sumWT), "".join("ABCDEF"[i] for i in perm))

allp = sorted(pts)
par = [p for p in allp if not any(q[0] <= p[0] and q[1] <= p[1] and q != p for q in allp)]

# 扫 201 组权重，看加权求和能命中前沿上的哪几个
mc = max(p[0] for p in par)
mt = max(p[1] for p in par) or 1
hit = set()
for i in range(201):
    a, b = i / 200, (200 - i) / 200
    hit.add(min(par, key=lambda p: (a * p[0] / mc + b * p[1] / mt, p[0])))

print(f"排列 {len(list(itertools.permutations(range(n))))} 个 "
      f"→ 不同目标向量 {len(allp)} 个 → 非支配 {len(par)} 个 → 加权命中 {len(hit)} 个")
for p in par:
    print(f"  ΣCj={p[0]:>4}  ΣwjTj={p[1]:>4}  顺序={pts[p]}"
          f"  {'加权取不到' if p not in hit else '加权能取到'}")
```

```text
排列 720 个 → 不同目标向量 344 个 → 非支配 10 个 → 加权命中 4 个
  ΣCj=  90  ΣwjTj=  31  顺序=DCEFBA  加权能取到
  ΣCj=  91  ΣwjTj=  27  顺序=DCFEBA  加权取不到
  ΣCj=  92  ΣwjTj=  24  顺序=DFCEBA  加权取不到
  ΣCj=  93  ΣwjTj=  19  顺序=DCEFAB  加权取不到
  ΣCj=  94  ΣwjTj=  15  顺序=DCFEAB  加权能取到
  ΣCj=  95  ΣwjTj=  12  顺序=DFCEAB  加权能取到
  ΣCj=  99  ΣwjTj=   9  顺序=DCFAEB  加权取不到
  ΣCj= 100  ΣwjTj=   6  顺序=DFCAEB  加权取不到
  ΣCj= 101  ΣwjTj=   3  顺序=DEFABC  加权取不到
  ΣCj= 102  ΣwjTj=   0  顺序=DFEABC  加权能取到
```

顺手验证了两件事：**SPT 顺序（DCEFBA：3,4,4,5,6,9）确实是 `ΣCj` 的最优 90**；
而它的加权拖期是 31，是前沿上最差的一端——**同一个顺序，两个目标的两端**。
把工件数改成 8（`8! = 40320`）再跑，你会看到前沿点数涨到几十个，加权命中率更低。

## 八、LISA 案例里的多目标：一句诚实的话

那份需求文档里，目标优先级是这么写的（原文照录）：

```text
| G2 | 目标优先级真实排序：交期 OTD、瓶颈利用率、换型损失、成本、加班，权重各多少 |
     | 数值 | 现在权重是我拍的 |
```

**「现在权重是我拍的」——这是我在整个案例文档里最喜欢的一行。**
它比任何「我们采用了先进的多目标优化」都诚实，而且它精确指出了这个项目的一个真实缺口。

五个候选目标（交期 OTD / 瓶颈利用率 / 换型损失 / 成本 / 加班）里有三个是**比率或非线性**的：

- 瓶颈利用率是 `已排工时 ÷ 可用工时`，分母随日历变，是个分式目标 → MILP 里要线性化或用 CP 的整数除法。
- 换型损失依赖**顺序**，不是解的和式 → 它只能进目标函数，不能进松弛。
- OTD 是 `max(0, ·)` 的计数平均 → 非光滑。

**所以这个案例的真实形状是：5 个目标里只有 1~2 个适合进目标函数，其余 3 个应该做成约束或看板指标。**
这条判断在任何多目标排产项目里都成立，值得你抄。
