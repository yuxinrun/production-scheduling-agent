# 你怎么知道方案好不好：下界与间隙

排产系统上线第一周，一定会遇到这句话：

> 「这个计划比上礼拜那个好多少？」

答不出来的系统，第二周就开始被计划员手工改了。

答这个问题需要**两个数**：你手里这个解的值（**上界**），和「数学上不可能更好」的那个值（**下界**）。
**现场 90% 的排产软件只有上界。** 有下界的，基本都在这一行里做过三年以上。

---

## 一、两根线，中间那块空地叫 gap

```text
    下界 LB  ────────────►  最优 z*  ◄──────────── 上界 UB
    (证明：不可能更低)        (未知)        (构造：这个可行解的值)

    gap = (UB − LB) / LB          ← 求解器行规：分母是下界
```

三个要点，缺一个你的报告就是错的：

| 要点 | 为什么 |
| --- | --- |
| **LB 一定来自证明，不来自经验** | 「我们老师傅说最快也就这样了」不是下界，是上界的另一种说法 |
| **gap 是「区间宽度」，不是「你的解有多差」** | UB=100、LB=80 的 gap 25%，可能你的解恰好就是最优，只是下界松 |
| **gap 单调收窄，不会反弹** | 正确实现里 LB 只升、UB 只降。**看到 LB 变说明你重写了模型** |

## 二、拿一台 4×3 的小车间，全部枚举到底

大例子没法验证，所以我构造了一台**小到可以穷举**的车间：4 个工件、3 台机器、每个工件 3 道工序。

```python
# (机器号, 加工时间)。工件内部按顺序走。
JOBS = [[(0, 5), (2, 1), (1, 4)],
        [(1, 2), (2, 4), (0, 5)],
        [(2, 3), (1, 5), (0, 6)],
        [(1, 6), (2, 6), (0, 1)]]
M = 3
```

先手算两个下界：

```text
每机器负载 = [17, 17, 14]      →  LB2（机器）  = 17
每工件链长 = [10, 11, 14, 13]  →  LB1（工件链）= 14
平凡下界 = max(14, 17) = 17
```

然后**穷举每台机器上的所有加工顺序**。3 台机器、每台 4 个工序 → `(4!)³ = 13824` 组顺序。
每组顺序画到析取图上求关键路径，就是这组顺序下的最早完工时间：

```python
def longest_path(order):
    """给定每台机器的加工顺序，返回关键路径长度。图成环则说明顺序互相矛盾。"""
    succ = {}
    for i, j in enumerate(JOBS):
        for o in range(len(j) - 1):                      # 工艺路线弧（conjunctive）
            succ.setdefault((i, o), []).append((i, o + 1))
    for seq in order.values():                            # 机器顺序弧（disjunctive）
        for a, b in zip(seq, seq[1:]):
            succ.setdefault(a, []).append(b)
    memo, on_stack = {}, set()

    def tail(node):
        if node in memo:
            return memo[node]
        if node in on_stack:
            raise ValueError("cycle")
        on_stack.add(node)
        i, o = node
        v = JOBS[i][o][1] + max([tail(x) for x in succ.get(node, [])] or [0])
        on_stack.discard(node)
        memo[node] = v
        return v

    try:
        return max(tail((i, 0)) for i in range(len(JOBS)))
    except ValueError:
        return None                                       # 有环 = 这组顺序排不出来

combos = list(itertools.product(*[itertools.permutations(ops_of[k]) for k in range(M)]))
vals = [longest_path({k: list(p[k]) for k in range(M)}) for p in combos]
vals = [v for v in vals if v is not None]
print("最优 =", min(vals), " 并列最优组数 =", vals.count(min(vals)))
```

实跑输出（Python 3.12，只用标准库；完整脚本在 [`/snippets/bounds_demo.py`](/snippets/bounds_demo.py)）：

```text
每机器负载 = [17, 17, 14]  每工件链长 = [10, 11, 14, 13]
LB1 工件链 = 14  LB2 机器负载 = 17  平凡下界 = 17
排序组合数 = 13824  其中互相矛盾(成环) = 11568
最优 makespan = 20  并列最优的排序组数 = 2
每台机器 1|rj,qj|Cmax 精确值 = {0: 18, 1: 19, 2: 15}  机器分解界 = 19
下界自己离最优: 17.6% -> 5.3%
按工件号顺序的朴素计划 makespan = 37  比最优差 85.0%
随机 20000 次取到的 makespan 值 = [20, 21, ..., 47, 48]
无环排序组数 = 2256  其中达到最优的占比 = 0.09%
无环排序的 makespan: 平均 35.6  中位 36.0  最差 48
```

**这一台 4 个工件的车间里，藏着六条你每天都能用上的事实：**

1. **`13824` 组顺序里 `11568` 组（83.7%）互相矛盾，根本排不出来。**
   「给每台机器随便定个顺序」大概率得到一个不存在的时间表。这就是为什么
   [析取图](/problem/exact) 的传播规则那么重要——它一半的工作是在**淘汰矛盾**。
2. **随机排 2256 组可行顺序，只有 0.09% 命中最优。** 所以「这次比上次好」这个句子里
   不含任何信息：随机重排就能变好，平均能变好 15.6 个单位（35.6 → 20）。
   **不做 gap 报告的优化项目，最后在跟随机数抢功劳。**
3. **平凡下界 17，真最优 20，差 17.6%。** 也就是说：哪怕你手里那个解已经是最优，
   求解器还是会报告「gap 17.6%」。**gap 是下界的问题，不一定是你的问题。**
4. **机器分解界把 17 提到 19，gap 从 17.6% 掉到 5.3%。** 多花的钱极少（3 台机器各解一个
   4 工件单机问题），收益极大。**收紧下界通常是排产项目里性价比最高的 20% 工作量。**
5. **按工件号顺序排的「朴素计划」= 37，比最优差 85%。** 这是本节最重要的一条，下面单独讲。
6. **随机能排出的最差是 48，最优 20——2.4 倍的差距。** 车间里「排得一塌糊涂」和
   「排得还行」之间真的有这么宽的空间。这也是为什么排产软件敢说自己有价值。

::: tip 为什么你要在自己的项目里做一遍这件事
找一台**你的求解器能在 30 秒内给出可验证答案**的小车间（比如一个工段、一天的窗口），
把上面这段脚本跑一遍，得到你自己的 17 / 19 / 20 / 37 这四个数。
它们会让你后面所有的对话都有底：知道下界有多松、随机有多好、人工有多差。
:::

一张「该在什么时候用哪种」的对照：

| 下界 | 强度 | 单次成本 | 能增量重算吗 | 重排场景适配 |
| --- | --- | --- | --- | --- |
| 工件链（关键路径） | 弱 | `O(n)` | ✅ 只改受影响的工件 | 局部重排时秒级 |
| 机器负载 `Σp / m` | 弱 | `O(n)` | ✅ | 适合做「这台机器今天不可能干完」的红线 |
| 能量界 / 时间窗交集 | 中 | `O(n log n)` | ⚠️ 需先做传播 | 有交期与发布时刻时值回票价 |
| 单机分解界（Carlier） | 中强 | 每台机器一次分支 | ⚠️ 关键机器才重算 | 找瓶颈机器顺带做了 |
| LP 对偶 | 看模型 | 一次 LP | ❌ 结构变了就重来 | big-M 模型慎用 |
| 拉格朗日（volume/bundle） | 强 | 几十~几百次迭代 | ✅ 乘子可热启动 | **变更评估（15 分钟内给答案）的最佳选择** |
| 已知最优 | 视情况 | 查表 | ✅ | benchmark 与验收 |

::: warning 「下界」和「约束」是一体两面
`Σp_jk ≤ cap_k` 既是硬约束，也是 LB2。当某个机器的负载下界 `17` **等于**它的产能上限时，
这条约束是**必然紧贴**的——这时任何「优化这台机器的利用率」的目标都没有意义，
因为它已经 100% 了，且不可能是别的。
反过来：机器 2 的总负载只有 14，而 makespan 至少 17——所以**任何计划里机器 2 都至少空闲 3 个单位**。
这是证明出来的，不是估的，可以直接拿去跟车间主任谈「这台炉子今天必空 3 小时，能不能挪别的产品上来」。
:::

## 四、上界从哪来，以及「人工计划是上界不是下界」

上界便宜：任何一个**可行解**就是一个上界。来源有——

- 求解器在时限内找到的最好解
- 派工规则拼出来的计划（[启发式那一页](/problem/heuristic)）
- 上一次下发的计划
- **计划员手工排的那版**

第四条是坑的重灾区。看本文例子的实测：

```text
按工件号顺序的朴素计划 makespan = 37  比最优差 85.0%
```

假设这 37 就是「我们老师傅手工排的」，而你的系统排到了 22。同一个事实有两种讲法：| 讲法 | 句子 | 问题 |
| --- | --- | --- |
| ❌ 以上界为基准 | 「从 37 优化到 22，提升 40.5%」 | 数字很大、很爽、**毫无意义**。因为 37 不是任何意义下的极限，它只是一个坏解 |
| ✅ 以上界为参照、下界为标尺 | 「手工计划 37，系统 22。数学下界 19，最优可能是 20。所以系统已经吃掉了 17 个单位差距中的 15 个，剩下的 2 个单位里，最多 0 个是我们的空间」 | 长，但**站得住** |

**推论，值得贴在显示器上：**

> **人工计划永远是上界。所以「我们的系统比人工好多少」这个问题，永远有一个答案，
> 而且那个答案的天花板是「人工有多差」，不是「机器有多强」。**

这条推论有两个方向的杀伤力：

1. **人工排得很好时，你的系统「没有提升」是正确结论。** 别去调目标函数制造提升，
   那不是优化，是过拟合你的 KPI。
2. **人工排得很差时，你的系统会拿到一个虚高的成绩。** 上线三个月后计划员学会了
   在你的输出上微调，第二年同比就掉下来了——第二年掉的不是能力，是第一年的水分。

::: tip 正确的对照是「同一条下界下的排名」，不是「比人工好多少」
本文那台小车间里，这五个数全都是穷举出来的，不是估的：

```text
机器分解界 LB = 19        （数学说：不可能低于 19）
最优            20        （穷举 13824 组排序，2 组并列）
全部可行排序的均值 35.6    （2256 组无环排序的平均，中位数 36）
按工件号排      37        （「谁先来我先做」，一个典型的朴素/人工计划）
最差            48
```

这张表的可信度远高于「提升 40%」，因为**每一行都可复现**，
而且「随机解均值」这一行帮你把**算法贡献**和**运气贡献**分开了。
:::

## 五、gap 的三个陷阱（我见过每一个都被踩）

### 陷阱 1：分母不统一

`(UB − LB) / LB` 是行规。但不少自研面板写 `/UB`，或者更糟——不同页面用不同分母。
同一个数，`LB=19、UB=22`：`/LB = 15.8%`，`/UB = 13.6%`。
差 2.2 个百分点不多，但**验收文档里的 gap 和周报里的 gap 对不上，你就要开一次解释会**。

**治法**：把 gap 计算收敛到一个函数，写单元测试，别在任何页面里手写公式。

### 陷阱 2：「gap = 0%」有两种含义，界面上长得一样

| 真实情况 | 界面 |
| --- | --- |
| LB 追上了 UB，最优已证明 | 0% ✅ |
| **求解刚开始 3 秒，LB 还没算出来，用 UB 兜底** | 0% ❌ |

后者极其常见——「LB 初始化为一个很小的值」和「LB 未就绪」是两回事，很多实现把后者
写成前者。更阴的变体：**整数取整把 0.4% 抹成 0%**（整数模型 + 整数 gap 阈值）。

**治法**：报告里加一个字段 `lb_proven: true/false`，`false` 时 gap 显示成 `≥ ?%`。

### 陷阱 3：拿时限内的 gap 当质量指标

`gap ≤ 1%` 是**停止条件**，不是**成绩**。写进验收标准时要说清是哪一种，否则会出现
这种荒诞局面：为了凑「平均 gap ≤ 5%」，团队把时限从 30 秒改成 3 小时，gap 好看了，
重排响应时间毁了——而这个 KPI 才是客户付钱的理由（见 [案例 KPI](/case/kpi)：
夜间全量重排 1~2 小时、变更评估 ≤ 15 分钟）。

::: details 时限内怎么停：一段可以直接抄的收敛记录
```python
class GapLog:
    def __init__(self, target=0.005, stagnation=60):
        self.target, self.stagnation = target, stagnation
        self.rows, self.best_lb, self.last_lb_move = [], -1e18, 0.0

    def record(self, t, ub, lb):
        lb = max(lb, self.best_lb)          # LB 必须单调，防实现里回退
        if lb > self.best_lb + 1e-9:
            self.last_lb_move = t
        self.best_lb = lb
        gap = (ub - lb) / lb if lb > 0 else float('inf')
        self.rows.append((t, ub, lb, round(gap, 4)))
        if gap <= self.target:
            return 'stop:target'
        if t - self.last_lb_move > self.stagnation:
            return 'stop:stagnation'        # 界不动了，继续跑只是烧 CPU
        return 'go'


log = GapLog(target=0.05, stagnation=40)
for t, ub, lb in [(0, 48, 0), (10, 40, 17), (30, 30, 17), (70, 24, 17),
                  (90, 22, 19), (130, 22, 19), (200, 22, 19)]:
    print(f"t={t:>3}  UB={ub:>2}  LB={lb:>2}  ->  {log.record(t, ub, lb)}")
print("rows:", log.rows)
```

输出（Python 3.12 实跑）：

```text
t=  0  UB=48  LB= 0  ->  go
t= 10  UB=40  LB=17  ->  go
t= 30  UB=30  LB=17  ->  go
t= 70  UB=24  LB=17  ->  stop:stagnation
t= 90  UB=22  LB=19  ->  go
t=130  UB=22  LB=19  ->  go
t=200  UB=22  LB=19  ->  stop:stagnation
rows: [(0, 48, 0, inf), (10, 40, 17, 1.3529), (30, 30, 17, 0.7647), (70, 24, 17, 0.4118), (90, 22, 19, 0.1579), (130, 22, 19, 0.1579), (200, 22, 19, 0.1579)]
```

**这段输出里藏着一个真实的坑：`t=70` 已经判了 `stop:stagnation`，但下界在 `t=90` 又涨了一格（17 → 19）。**
如果你老实停了，就永远看不到那个更紧的界。
`stagnation` 窗口对「界是阶梯式跳变」的算法（分解法、拉格朗日）太短，对「界连续爬升」的
单纯形 LP 太长。**这个数必须在你自己的实例上标定，不能抄 defaults。**

原则仍然是对的——**下界长时间不动，说明该改模型（加切割、换松弛、换分解），不该只加时限**；
这一条直接对应 [精确算法那一页](/problem/exact) 的剪枝质量讨论。只是「长时间」这个数，
请用上面那 7 行自己标定一次。
:::

## 六、多目标的下界是一组向量，而这个角点根本不存在

[多目标那一页](/problem/multiobjective) 说「别加权，给前沿」。这一页补上它缺的另一半：
**多目标下的 gap 怎么报？**

先看本文那台小车间的实测。目标取两个：`Cmax`（最长完工）和 `ΣC`（总完工时间）。
穷举 13824 组顺序、剔除成环、去重后剩 **678 个不重复的解点**，Pareto 前沿只有 3 个点：

```text
两目标不重复解点 = 678 个，Pareto 前沿 = [(20, 68), (21, 65), (23, 62)]
下界向量 = (Cmax 17 , sumC 48 )  这个角点可达吗？ False
前沿里 sumC 最小 = 62   Cmax 最小 = 20
```

关键的那一行是 **「角点可达吗？False」**。

```text
  ΣC ▲  （越小越好）
  48 │ ✕ (17, 48)        ← 分量下界拼出来的角点：世上没有这个计划
     │    ╲
     │      ╲   这片「更好」的区域是空的
  62 │        ·········● (23, 62)
  65 │            ● (21, 65)
  68 │        ● (20, 68)
     └───┬──────┬────┬────┬──► Cmax （越小越好）
        17     20   21   23
```

**每个分量单独看都是合法下界，拼成一个「向量下界」就不再是任何解的下界。**
所以你报「我们离最优差 (17.6%, 41.7%)」是**错的**——那个参照点不存在，
差距被系统性放大：`ΣC` 在所有可行解里的真实最小是 **62**，不是 48；
`Cmax` 的真实最小是 **20**，不是 17。

换个目标照样打架。把 `ΣC` 换成「总拖期」（交期取 `d = [10, 12, 15, 14]`，约等于各自链长的 1.05 倍）：

```text
工件链长 = [10, 11, 14, 13]  交期 = [10, 12, 15, 14]
(Cmax, 总拖期) 不重复解点 = 674  前沿 = [(20, 17), (21, 14), (23, 11)]
各自单目标最优: Cmax = 20  总拖期 = 11
```

`总拖期 = 11` 的那个解，`Cmax` 是 **23**：为了让急件准点，整体工期要多付 3 个单位。
**这就是为什么「最优解」在多目标问题里不是一个点，而是一组互相之间不可比较的方案。**

### 那么多目标怎么报进度？

| 报法 | 怎么说 | 诚实度 |
| --- | --- | --- |
| 分量 gap 列表 | 「Cmax 差 17.6%、ΣC 差 41.7%」 | ❌ 参照角点 (17, 48) 不存在，两个差距都被放大 |
| 单目标 gap | 「总拖期差 54.5%」（17 对 11） | ⚠️ 11 确实存在，但它属于 `Cmax = 23` 那个解。**你不能一边保最快工期、一边用拖期的界** |
| **前沿对比** | 「系统前沿 3 个点 [(20,68), (21,65), (23,62)]；按工件号排的那版只有 1 个点 (37, 98)，被前沿每一个点支配」 | ✅ 每个数都能复现，计划员也听得懂 |
| **超体积差** | 见下面的算例 | ⚠️ 唯一合法的「一个数」，但参考点一改，结论就能翻 |
| **逐目标锚定** | 「急件拖期的数学最小是 11，要付 23 的工期；我们选择工期 20 那一端，拖期 17。这是**选择**，不是**失误**」 | ✅ 现场最好用，一次只谈一个目标 |

超体积「一改就翻」不是修辞，是本文例子的实测：

```text
参考点 (24, 72)：完整前沿 HV = 28，加权求和只找到端点 (20,68) 与 (23,62)，HV = 22 → 丢 21.4%
参考点 (30, 80)：完整前沿 HV = 168，同样两个端点 HV = 162 → 丢 3.6%
```

**同一批解、同一个对比对象，把参考点从「贴着前沿」挪到「离前沿很远」，
结论从「加权求和丢掉五分之一」变成「差不多嘛」。**
原因很直白：参考点拉远以后，那个大矩形被最外面那条边撑满，中段丢掉的面积成了零头。

::: warning 用超体积的三条前提
① 所有目标方向一致（全部最小化，混一个「最大化利用率」要先取负）；
② 参考点必须比前沿里最差的解还差，否则面积是 0 或者更糟；
③ 它**对前沿中段最敏感**——恰好是现场最不在乎的那一段。计划员只认两个端点：
最快的那个，和急件最准的那个。所以：**超体积用来做内部回归对比，对外一律讲「两个端点 + 不被支配」。**
:::

## 七、没有下界的时候，怎么谈「好」

现实里你接的第一个项目常常算不出任何有意义的下界（模型没定、数据没齐）。
这时候**三个能谈的锚**和**一个不能谈的**：

| 能谈 | 句子 | 为什么站得住 |
| --- | --- | --- |
| **可行 / 不可行** | 「人工那版违反 3 条硬约束，系统那版 0 条」 | 这是最粗的下界形式：**「0 违反」不可再低**。它是硬事实，不依赖任何松弛 |
| **同一下界下的相对排名** | 「用同一个负载下界 19 度量，四个候选里这个最好」 | 参照一致时，排序是可信的 |
| **影子模式同期对比** | 「这 4 周系统排的和实际执行的，接单量 +3 单、总延迟 −18 小时」 | 比的是**结果**不是**计划**，计划员挑不出毛病 |

| 不能谈 | 句子 | 为什么 |
| --- | --- | --- |
| ❌ 「比人工好 X%」 | 以对方的坏解为分母 | 见第四节。而且**它是在暗示计划员很差**，这是采纳率问题（[那一页](/build/adoption)） |

## 八、怎么跟厂长讲 gap（话术三句）

技术报告和车间白板是两个语言体系。别把 `gap 15.8%` 写在白板上。

| 对象 | 说法 |
| --- | --- |
| 厂长 / 车间主任 | 「**这批活数学上最快就是 19 天，这是算出来的红线，不是估的。我们现在排到 22 天。** 中间这 3 天，一部分是我们的算法还不够好，一部分是这个问题本身排不到 19 天。我们知道上限在哪，每改一次都往它靠一点。」 |
| 计划员 | 「下界是**这台设备光加工就要 17 小时**，谁排都逃不掉。所以我不跟你说『还能优化 30%』——我说『这台炉子今天至少空 3 小时，能不能把别的产品挪上来』。」 |
| 甲方信息化负责人 | 「gap 是**求解器和数学的差距**，不是**系统和人工的差距**。这两个数我们分开报，前者衡量软件，后者衡量价值。混在一起报是行业里最常见的虚标。」 |

三句话的共同结构：**先给一条不可动摇的红线（下界），再说你离红线多远，最后承认剩下的差距有两种可能。**
承认第三种可能性（「我不知道哪一种是主因」），是你可信度的来源，不是弱点。

## 九、上线前必答的 7 个问题

把这一节当成 [投产配置清单](/case/checklist) 的数学部分。

1. 每个待求解的实例，**下界是多少？谁来算？**（必须有一个具体的函数名）
2. 分母是 LB 还是 UB？**全站是不是同一个函数？**
3. `lb_proven` 字段存在吗？未就绪时 gap 显示成什么？
4. 下界停止爬升时，你**改模型还是加时限**？（答案必须是改模型）
5. 你算过**随机解**和**朴素解**这两个参照吗？它们的值分别是多少？（不知道就别宣称提升）
6. 多目标时，你报的是**前沿**还是**分量的 gap 列表**？后者要删掉。
7. 验收文档里的 gap 是**停止条件**还是**成绩**？如果是成绩，重排响应时间 KPI 谁在守？
