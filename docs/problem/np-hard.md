# 为什么排产是 NP-hard

先给结论，因为它决定你后面所有的设计决策：

> **排产问题不存在「把参数调对就能算准」的解法。**
> 存在的是：一个足够好的可行解 + 一个说明它有多好的下界 + 一套能在现场站住的重排机制。

NP-hard 不是一个警告，是一份**架构说明书**。它规定了你的系统必须长什么样：
必须有超时机制、必须有兜底规则、必须报告间隙而不是报告最优、必须能只重排一部分。
这一页讲清楚这份说明书怎么写，下一页开始把它翻译成变量。

## 一、先学会读问题名字：α | β | γ

排序与调度文献用三元组给问题起名字
（Graham–Lawler–Lenstra–Rinnooy Kan，1979 提出；1976 年技术报告）。
**看懂这三个字段，你就能从论文标题里读出「这个问题有没有救」。**

```text
α  |  β  |  γ
↑     ↑     ↑
机器  工件/约束  目标函数
```

| 字段 | 常见取值 | 意思 |
| --- | --- | --- |
| α | `1` | 单台机器 |
| | `Pm` | **平行机**，每台机器一样快，`P` 不带数字表示机器数也是输入 |
| | `Qm` / `Rm` | 速度不同（uniform）/ 关系不同（related，某 job 在某机上耗时不同） |
| | `F` / `J` / `O` | Flow shop（所有工件同路线）/ Job shop（各走各的）/ Open shop（工序顺序无所谓） |
| | `FJm` | **柔性作业车间**：每道工序可以从一群机器里挑一台。现场最常见，也最难 |
| β | `—` | 没有额外约束，纯排序 |
| | `r_j` | 工件有可用时刻（release date） |
| | `prec` | 工序间有先后依赖（工艺路线） |
| | `p_j = 1` | 单位加工时间 |
| | `pmtn` | 允许抢占（做到一半让出去） |
| | `MU_j` | 一台机器同时只能被一个工件用（默认就是） |
| | `nwt` | no-wait：工序之间不许停（热处理、涂装常见） |
| | `b` / `batch` | 批处理机：一炉能装多个，且加工时间取最长的那个 |
| γ | `C_max` | makespan，最后一件干完的时刻 |
| | `Σ C_j` | 总流程时间 / 平均在制 |
| | `Σ w_j T_j` | 加权拖期（`T_j = max(0, C_j − d_j)`） |
| | `Σ U_j` | 逾期工件**个数**（0/1 计数） |
| | `L_max` | 最大滞后 |
| | multi | 多目标，用 `multi` 或写成多个 γ |

读法示例：

- `1 | | Σ w_j C_j` —— 单机、无附加约束、加权完成时间之和最小。
  **多项式可解**：Smith 1956 的比率规则，按 `p_j / w_j` 升序排即可。
- `1 | r_j | Σ w_j C_j` —— 只多了「工件有不同的可用时刻」。
  **强 NP-hard**。一个符号之差，从一行排序代码变成指数搜索。
- `F2 | | C_max` —— 两台机器的流水车间。**多项式**：Johnson 1954 的规则，排序即可。
- `F3 | | C_max` —— **三台机器**。强 NP-hard。
- `Jm | | C_max` —— 作业车间。强 NP-hard（Garey–Johnson–Sethi，1976）。
- `J | prec | multi` —— 这就是真实车间。

::: tip 现场最有用的读法
把你们厂的排产问题写成三元组，贴在 README 第一行。
这一个字符串会替你回答掉一半的需求争论：
「为什么不能实时给出全局最优？」——因为你是 `FJm | prec, r_j, SU_ji | Σ w_j T_j + multi`，
它是强 NP-hard，而且你的 γ 有三个。
:::

**为什么「强」NP-hard 对工程更重要？**
因为弱 NP-hard 有一个逃生门：把数值压小。加工时间从分钟改成小时、把成本除以 1000，
动态规划就能跑。强 NP-hard 没有这个门——难度只跟**工件数和机器数**有关，
数值缩放完全无效。现场的所有车间都是强 NP-hard。

## 三、组合爆炸的真实数字

不是比喻，是阶乘。

<ExplosionChart
  eyebrow="量级 · 自己拖一下"
  title="10 个工件一台机器：363 万。20 个：2.4 × 10¹⁸"
  lead="条长是 log₁₀(搜索空间)。拖下面的滑块，看看「穷举」在真实车间里值多少钱。"
  glow="coral"
/>

三个必须记住的数字：

1. **单机 10 个工件**：`10! = 3,628,800`。一台笔记本 1 秒能穷举完。
   所以「小样儿试试」的时候，精确算法好得离谱——这也是为什么你的原型很惊艳。
2. **ft10（10 工件 × 10 机器）**：约 `10! × 10¹⁰ ≈ 4 × 10⁶⁵` 种排法。
   最优值 930，1990 年代初才被算出来。你的原型跑不动不是代码差，是问题大。
3. **100 工件 × 20 机器**：约 `10³¹⁵⁹`。可观测宇宙的原子数约 `10⁸⁰`。
   这不是「难」，这是**物理上不可能**。

::: warning 别把 n! 说成 JSP 的搜索空间
`n!` 是**单机排序**的排列数。作业车间 `Jm‖Cmax` 的真实空间还要乘上机器分配的组合，
量级是 `(n!)^m` 这一族（本图用的就是它）。写文章时如果只写 `n!` 会被懂行的人抓住：
单机才是 `n!`，那玩意儿还是多项式的。
:::

## 四、40 年没人算完的公开榜单

JSPLib 是调度界的公开算例库（1980 年代流传至今的 ft / la / abz / orb / ryer / yn / ta 系列）。
它的存在本身就是 NP-hard 最好的教材：

| 算例 | 规模 | 状态 |
| --- | --- | --- |
| `ft06` | 6×6 | 早已证明最优（55） |
| `ft10` | 10×10 | 最优 930 已被证明 |
| `la37` | 15×15 | 最优 1397 已被证明（2001 年前后） |
| `la21` | 15×10 | 长期悬着；2021 年 CP-SAT 把最好已知值推到 1046 |
| `ft20` | 20×5 | **仍未证明最优**，最好已知 1165 |
| `abz8` | 20×20 | 上下界长期拉锯：UB 665 / LB 645 量级 |
| `ta18` | 30×15 | UB 1396 / LB 1393，间隙约 0.2% |
| `ta45` | 15×15 | 最优 1997 已被证明 |
| `yn1`–`yn4` | 20×20 | **4 个算例，0 个被证明最优** |

::: tip 引用前请回表核对
上表里的具体数字来自文献与公开榜单的流传值，**存在版本更新的可能**（新求解器每年会推高一些 UB/LB）。
写进方案或论文前，去 jspsolver.org（JSPLib）核对当天的最好已知值。
这里保留它们只为了说明一件事：**在 20×20 的规模上，世界最好的求解器仍然只能给你一对夹逼的数，而不是一个答案。**
:::

看 `ta18` 那一行：上下界只差 0.2%，但**没人能证明最优**。
这就是你要向老板解释的东西——「0.2% 间隙」和「0% 间隙」之间的差距，
可能需要再算 30 年。

这张图里有四个工程决策，每一个都得写进代码：

1. **超时不是异常，是正常路径。** 求解器返回的是「当前最好解」，不是「解」。
2. **gap 是产品的一部分。** UI 上必须显示 `UB / LB / gap`。不显示 gap 的系统会让计划员以为你在骗他。
3. **LB 是免费的信任。** 一句「这个方案最多比最优差 3%」值十次解释算法原理。
4. **收敛趋平就该切局部重排。** 全量重排每小时做一次，其余时间只做局部。见 [重排那一层](/problem/uncertainty)。

## 六、三十行自己看见爆炸

不用装求解器。这段代码在 8 个工件时开始让你不安，10 个时让你关机。

```python
from itertools import permutations
from time import perf_counter

def makespan_single_machine(jobs, order):
    t, total = 0, 0
    for j in order:
        t += jobs[j]
        total += t          # Σ Cj：每个工件的完成时刻之和
    return t, total

jobs = [7, 3, 5, 9, 2, 6, 4, 8]        # 单机加工时间
n = len(jobs)

best, seen = None, 0
start = perf_counter()
for order in permutations(range(n)):     # n! —— 这行就是 NP-hard 的全部体感
    seen += 1
    cmax, sum_c = makespan_single_machine(jobs, order)
    if best is None or sum_c < best[1]:
        best = (cmax, sum_c, order)
elapsed = perf_counter() - start

print(f"n={n}  穷举 {seen:,} 种排列，耗时 {elapsed:.2f}s")
print(f"最优 ΣCj={best[1]}  顺序={best[2]}")
# 剧透：最优顺序其实就是按加工时间升序（SPT）。
# 穷举一百万次得到的答案，排序一行就能得到 —— 这就是「多项式可解」的体感。
```

把它改成 `jobs = [7, 3, 5, 9, 2, 6, 4, 8, 11, 1]`（n=10，363 万种），
你会看到时间跳一个数量级；再加两个工件就到 6000 万，你大概率会 Ctrl-C。
**这个「加两个工件慢十倍」的斜率，就是指数。**

而真正的作业车间（每台机器一条独立路线）不是排列问题，是**排列 × 机器分配**，
穷举连 n=10 都撑不住。这就是为什么下一页要讲数学建模：
不是为了算得快，是为了**让搜索空间可以被剪掉**。

## 七、三条「NP-hard 其实不难受」的理由

| 理由 | 为什么 | 对代码的意义 |
| --- | --- | --- |
| **规模是可切的** | 车间不是全厂一次算。按工序域、按冻结窗口、按厂区切块后，每块几十道工序是常态 | 分层重排：全量夜间跑，局部 30 分钟内跑，派工秒级规则跑 |
| **最优不值钱，可行 + 可解释值钱** | 现场不在乎 `gap=0`，在乎「这个方案会不会让热处理炉空烧、计划员看不看得懂」 | 输出 A/B/C 三个方案 + 每个的 gap + 触发了哪几条规则 |
| **弱项可以被约束排除** | CP 的推理（edge-finding、能量推理）能在毫秒级排除 99% 的分支，不用目标函数参与 | 先建模约束，再谈优化。顺序反了的项目都会慢 |

::: details 一个常见的误解：「NP-hard 所以要用大模型」
NP-hard 说的是**最坏情况**的计算难度。它不意味着启发式不能用，
也不意味着机器学习能绕过它——RL 与 LLM 也一样不能把指数变成多项式（除非 P=NP）。
它们真正能改的是**平均情况**和**建模环节**：
在同类实例上摊销求解时间，或者把「人话需求」变成「正确的三元组」。
这两件事都有价值，但都不是「绕过 NP-hard」。见 [学习与大模型能做到哪一步](/problem/learning)。
:::
