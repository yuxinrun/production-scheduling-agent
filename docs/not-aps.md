# 它不是 APS，也不是聊天机器人

这两个误解在项目里同时存在，而且互相掩护：售前把 APS 叫智能体，研发把智能体做成聊天框。
两边都能通过演示，两边都会在六个月内死掉。这一页把边界画清楚。

## 二、最常见的选型骗局：把「有限产能检查」当「优化排程」

现场有相当多的产品长这样：一条甘特图，设备超载的部分标红，然后跟你说「有限产能可视化，一目了然」。

那不是优化。那是**报表**。

| | 有限产能检查 | 优化排程 |
| --- | --- | --- |
| 发现冲突 | 会 | 会 |
| 消除冲突 | **不会，交给人** | 会，这是它的本质 |
| 需要搜索 | 不需要 | 需要（这才是 NP-hard 的地方） |
| 能回答「最快什么时候交」 | 不能 | 能，但必须给下界 |
| 实现难度 | 一个 SQL 聚合 | 约束模型 + 求解 + 降级链 |

看演示时只问一句：**「你们产能是约束还是报表？」**
对方如果回答「我们能提示超负荷」，那就是前者。这是行业里被反复吐槽的点：用离散排产引擎套流程行业场景、
把产能检查包装成排产系统，上线后天天被车间骂「排出来的计划不能用」。

## 三、也不是聊天机器人

国内做工业智能体比较早的一家（联友科技）公开泼过一盆冷水，原话大意是**单靠大模型排产是幻觉**，
必须 **LLM 交互 + 求解器寻优 + 规则引擎校验** 分层。这个结论和国际侧的实测完全一致：

排产 Agent 里 LLM 真正能做的事，按风险从低到高：

1. **意图翻译**：把「周三前把这三张军品件插进去，但已领料的那批别动」翻成任务规格 + 约束增量。
2. **结果解释**：把求解器输出的目标值、被推后的工单、瓶颈负荷讲成人话，并给出可反驳的因果链。
3. **修复建议**：当方案不可行时，提出「改哪条数据/哪条规则能让它可行」，由人决定。
4. **知识检索**：从工艺规程、制度文件、历史案例里找出可引用的依据（**必须带出处**，本地检索就写本地检索，别宣称 RAG）。

LLM **绝对不能**做的两件事：直接生成时间数字（「大约 3 天能做完」），以及直接触发写操作（下发、改基线、锁工单）。

## 五、什么时候你其实不需要 Agent

诚实的建议，先排除三种情况：

- **你连标准工时都没有**：先做工艺数据建库，任何算法在这种输入上都会给出漂亮而错误的计划。
  真实案例：热处理工序「无标准工时、消耗定额一年维护一次」——这种工序的第一件事是让记忆库承担工时基线自学习，不是上求解器。
- **你的瓶颈只有一台设备且订单 < 30**：写个 EDD + 人工微调的界面，比上一整套 CP 便宜十倍，而且现场更愿意用。
- **你要的是「看得到负荷」**：那买一块看板，别买排产系统，也别自己写 agent。

反过来说，当这三件事同时成立，Agent 才真的有增量：**约束多到没人能全部记住、扰动频到每天必须重排、
且跨系统数据多到人工整合跟不上**。这是绝大多数中等以上离散制造企业的真实处境。
