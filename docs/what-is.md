# 排产 Agent 到底是什么

先把名字拆开，因为「排产」这两个字在中文工业软件里被用得极其随意。

**排产 = 生产排产计划**：给定一批订单，决定**每张工单的每道工序，在哪台设备（或工位/班组/炉号/台架）上，从什么时间到什么时间执行**，
并让这份计划在真实可执行的前提下，把该优化的指标优化到可接受。

它输出的是**一份带时间轴的、占用资源的计划**，不是一段话，不是一张看板，也不是一条 SQL。

输出也不只是一张甘特图。一个能被现场接受的排产 Agent 至少要同时输出四件东西：

1. **计划本体**：`(工单, 工序, 资源, 开始, 结束)` 的集合，资源占用不重叠、满足工艺顺序与日历。
2. **可行性证据**：哪些硬约束被检查过、哪些**因为数据缺失根本没被检查**（这两件事必须分开写，不能合并成「校验通过」）。
3. **归因说明**：为什么这张工单排在这台设备、为什么那张延期 —— 计划员要能反驳。
4. **代价读数**：目标函数值 + **下界** + 间隙。只有上界的界面是「没有速度表的速度限制」。

## 二、三个动作，三个不同的问题

现场语言里「排产 / 排程 / 派工 / 调度」经常混用，但它们在数学上是三个问题：

| 动作 | 英文 | 决策什么 | 时间粒度 | 典型系统 | 难度特征 |
| --- | --- | --- | --- | --- | --- |
| 生产计划 | MPS / S&OP | 每个产品族每周/每月做多少 | 周 / 月 | ERP、IBP | 混合整数规划，规模大但结构松 |
| 详细排程 | Detailed Scheduling (APS) | 每道工序在哪台设备几点到几点 | 分钟 / 班次 | APS | 强 NP-hard，约束耦合紧 |
| 派工 | Dispatching | 现在这台设备**下一个**干什么 | 实时 | MES 工位终端 | 在线决策，规则或 RL |
| 动态调度 | Rescheduling | 出事之后计划怎么改、改多少 | 事件驱动 | APS + MES | 稳定性与最优性的权衡 |

**排产 Agent 主要做第二件事，但必须同时懂第三和第四件**。
只做详细排程的 agent 会在设备一停机时全场作废；只做派工的 agent 永远无法回答「这批订单能不能按期交」。

所以这本手册里，**排产 Agent 的工作几乎全在模型外面**：数据接入、本体建模、约束校验、求解编排、权限熔断、评测治理。
模型负责的是最难自动化但风险最低的那一层 —— 听懂人话、解释结果。

## 四、一个具体的例子，走一遍

某航空发动机厂的机加与热表环节，调研文档里写实的形状是这样的：

- 换型时间实测 **0.5~1 天**，且数据不准（问题清单 #6）；
- 已上的 APS 输出**不可用**，每个加工中心每天要人工调整 **3~4 小时**（#2）；
- 装配齐套率只有 **60%**，也就是每 10 张工单里 4 张排进去就注定开不了工（#1）；
- 部分工序只有单一设备能做，现场叫「独生子设备」；瓶颈设备有效负荷 **40~60%**（#5）；
- 试车日计划达成率 **50%**，根因是上道到料不可视（#7）。

也就是说：**约束是真实的，数据是不准的，人工兜底是每天几小时的**。这决定了排产 Agent 的形态必须先能做归因和点检，再谈优化。
（下面五步流程里出现的「214 张工单 / 波及 17 张」这类具体数字是**我构造的示意量级**，用于说明流程，不是文档数据。）

现在插进来一张军品急件，要求周三前完成 2 台。排产 Agent 要做的事：

1. **齐套预检**：9 项要素（工装、主材、辅材、刀具、工艺路线、人员资质、单件 WIP 质量状态、设备状态、设备能力）逐项判。
   缺主材 → 这一单**不允许排入**，并把缺料归因和到货承诺写清楚。
2. **影响面推演**：如果它排进去，谁会被往后推？沿工艺路线 DAG 做拓扑传播，算出受波及工单与延误天数 —— 客户的验收指标是 **≤15 分钟**出这个结论。
3. **给出 A/B 两个方案**：A 协同重排（波及 17 张，OTD 风险 +2 天）；B 原地顺延（急件晚 1 天，需要加班 6 小时换回 1 天）。
4. **写清为什么**：每台设备的负荷率、被推后的每张工单的交期余量、哪个是冻结窗口内动不了的。
5. **等签字**：计划员微调或驳回，**驳回原因必填**。这一条数据是下一轮迭代的燃料。

第 1 步和第 3 步是算法问题，第 2 步是图问题，第 4 步是**可解释性问题**，第 5 步是**产品与组织问题**。
它们的比例大致决定了项目成败 —— 而这五步里只有一点点地方需要一个语言模型。
