# 七大扰动：56 步处置流程，八步闭环平均只剩 3.7 步

这一页拆的是**出事之后**。

前六页分别在数问题（37 项）、数 KPI（13 行）、数规则与约束（68 条／137 条）、数数据（四区间＋五维）、数人（16 个编号）。
这一页数的是**流程**：`§3.4.1~3.4.7` 那七套「标杆处理流程（八步闭环）」，每套 8 条，合计 **56 个步骤**——
交付包里唯一逐字写了「谁在第几步干什么」的地方。

扰动的清单是这样的（§3.1 正文原话）：设备／炉／台架故障、物料短缺、紧急插单、返工返修、订单变更、特殊过程受阻、ECN 变更。
管理口号只有一句：**统一处置模式，消除「每类扰动一套人工打法、无留痕无复盘」**。
口号后面跟了一个八步闭环：捕获 → 分级 → 评估 → 方案 → 审批 → 下发 → 跟踪 → 复盘。

所以本页只问一件事：**这句口号在 56 步里落地了几步。**

脚本在 [disturbance_probe.py](/snippets/disturbance_probe.py)，纯标准库、可离线重跑。
第三章的全部原文——56 步、表3-1 的 5 列 × 7 行、表3-2 的 7 行、七张规则表 56 条、七张约束表 53 条、

表6-3／6-4 的 24 条约束、表6-10 的八大场景决策链，加上《排产规则提取清单》68 行、37 项问题清单、

## 一、先数名字：「七大扰动」在交付包里有两套名单

「七大扰动」这五个字在文档里出现过，每一次都跟着一个冒号和一串名字。
问题是**那串名字不是同一串**。

```text
==========================================================================
[1] 『七大扰动』在交付包里有两套名单，两套都不完整
==========================================================================
  §3.1 正文列举（7 项）：设备/炉/台架故障 / 物料短缺 / 紧急插单 / 返工返修 / 订单变更 / 特殊过程受阻 / ECN变更
  时序图 2-2 的 E1 节点（7 项）：设备故障 / 急单 / 缺料 / 质量 / 人员 / 外协 / 能源
     E1 原文：「E1 异常事件接入（DZ-01~07：设备故障/急单/缺料/质量/人员/外协/能源）」

  四份正文工件逐个比名字（小节标题剥掉『3.4.x 』和『扰动标杆建议（DZ-0x）』两层壳）：
    DZ-01  2 种写法：设备/炉/台架故障｜设备故障
    DZ-02  四份逐字一致

  匹配规则先写死在这里，免得读者以为是我想怎么配就怎么配：

    『人员』在约束体系里有编号（['HC-04']），在扰动体系里没有；
    『能源』也一样（['SC-05 能耗最低偏好']）——
    有约束、没闭环：这两类事情发生时，不会有八步等它们。

  正文 P-0013 的承诺：
    「六大板块的全景逻辑关系如下图所示，各板块内部要素编号（B-01~B-09规则集、HC/SC约束、DZ-01~07扰动、LOOP-A~D闭环）与设计蓝图、任务…」
    DZ-01 引用问题编号：#23P1
    DZ-02 引用问题编号：（无）
    DZ-03 引用问题编号：#3P0
```

匹配规则那段值得单独抄出来，因为它是本页唯一一个「先声明口径再算」的地方：

> 两个名字各拆成字符集（去掉标点／空格／数字），共享汉字 ≥2 个才算同一个东西。

为什么不直接写「设备故障 = DZ-01」？因为**人眼一看就觉得是同一个东西**，而脚本必须有一条能复算的规则。
交集 4 个字算一个，交集 1 个字不算——这条线画在哪儿不重要，重要的是**画在哪儿要写下来**，
否则下一节里 4 个落不进 DZ 编号的词就会被顺手解释成「其实也是指某某扰动」，红线就这么变成白的。

最有意思的不是「对不上」，是**对不上的那四个词并不不存在于体系里**：

- 『人员』在约束体系里有编号——`HC-04 人员资质约束`；
- 『能源』也一样——`SC-05 能耗最低偏好`。

也就是说：**它们有约束、有偏好项，但没有扰动条目。**
约束的意思是「排产的时候不许违反」，扰动的意思是「出事了走八步闭环」。
一件事只进前者不进后者，后果是——**它发生的时候不会有八步等它**。
炉子跳了有 DZ-01，缺料了有 DZ-02，而「焊工证过期了」「这个班没人能干这道工序」在文档里只有护栏、没有处置流程。

再看追溯。§P-0013 原话承诺「各板块内部要素编号……与设计蓝图、任务拆解章节编码一致，**可双向追溯**」。
把第三章 218 段原文（56 步 + 56 规则 + 53 约束 + 35 衔接 + 27 场景 + 21 框架）里所有 `#数字` 抓出来，
一共只抓到 4 个：`#3`、`#23`、`#27`、`#28`。37 项问题清单里有 37 项。

**七大扰动中有任何编号可追的：4/7。**
剩下三个（物料短缺、订单变更、ECN 变更）在第三章里没有任何一处指向问题清单的行号。
「双向追溯」这四个字，实测只单向成立。

**给做智能体的人一句话结论**：事件分类表一定要做成**一张枚举表 + 一个字典**，别让「类别」这个词散落在正文里。
具体做法：`disturbance.yaml` 里一行一条（id、中文名、别名列表、来源问题编号、处置流程 id），
所有文档、图、代码只允许引用 `id`；CI 里加一条断言——**别处的任何扰动提法必须能在这个字典里查到 id，查不到就红**。
「质量／人员／外协／能源」这四个词，这条断言会在写第一版的时候就拦住你。

## 二、『八步』这个词，在交付包里指代四种不同长度的序列

口号里的闭环是 8 步。文档里所有写着「八步」的地方，是不是同一个 8 步？

```text
==========================================================================
[2] 『八步』这个词在交付包里指代四种不同长度的序列
==========================================================================
  ①《业务管理模式设计方案》§3.1 正文：8 步
     捕获 → 分级 → 评估 → 方案 → 审批 → 下发 → 跟踪 → 复盘
  ②时序图 2-1：7 步   捕获 → 评估 → 方案 → 审批 → 下发 → 跟踪 → 复盘
  ③时序图 2-1：4 步   仲裁/建模 → A/B并行求解 → HC后检 → 白盒归因
  ④时序图 2-2：7 步   捕获 → 评估 → 方案 → 审批 → 下发 → 跟踪 → 复盘
  ⑤时序图 2-3：8 步   接入 → 推演 → HC预检 → 建模 → A/B求解 → 后检归并 → 白盒归因 → 输出
  另有 2 处『八步』只是标题（2-1、2-2），不带序列。

  内联原文里『八步』共出现 7 处（正文 1 + 时序图 6），去掉复制粘贴后是 4 种不同的序列：
    ① 8 步  捕获 → 分级 → 评估 → 方案 → 审批 → 下发 → 跟踪 → 复盘
    ② 7 步  捕获 → 评估 → 方案 → 审批 → 下发 → 跟踪 → 复盘
    ③ 4 步  仲裁/建模 → A/B并行求解 → HC后检 → 白盒归因
    ④ 8 步  接入 → 推演 → HC预检 → 建模 → A/B求解 → 后检归并 → 白盒归因 → 输出
  步数分布：[8, 7, 4, 8]——四个都叫『八步』的序列，长度 8/4。

  规范 8 步 vs 时序图 loop 7 步，差集 = ['分级']
  被省掉的这一步决定要不要惊动 C-01/厂部（表3-1『分级路由』列 7 行全在写它）：分级
  2-3 那条『八步子图时序展开』与 §3.1 的 8 个名字重合 0 个——
    它讲的是 M-04 内部的 8 个动作（接入、推演、HC预检、建模、A/B求解、后检归并、白盒归因、输出），是求解流水线，不是处置闭环，却也标了『八步』。
```

拆完是 4 种序列，长度分别 8、7、4、8。三个观察：

1. **被时序图省掉的那一步是「分级」**。差集只有一个词，但这个词是路由开关——
   表3-1 的「分级路由」列 7 行全在写它（§3.1 也写「分级（局部/跨工序/全厂）」）。
   loop 框里不画这一步，读图的人会以为每个扰动都直接进评估；
   而实际架构里，「要不要惊动 C-01／厂部」这个判断就长在这一步上。
2. **长度 4 的那一套也叫八步**（2-1 里那段）。它把「仲裁/建模 → A/B并行求解 → HC后检 → 白盒归因」标成闭环，
   其实是求解流水线的四个阶段。四个词，八步的名字。
3. **长度 8 的那一套（2-3）跟 §3.1 的八步名字重合 0 个**。
   接入→推演→HC预检→建模→A/B求解→后检归并→白盒归因→输出——这是 **M-04 内部的动作序列**，
   讲的是「一次影响评估怎么算」，不是「一次事故怎么处置」。两件不同的事共用一个「八步」的名字。

第 1 步「捕获」只有 2/7 个扰动的流程里逐字出现，这件事的分量比看上去大得多：
56 步里第 1 步实际写的是「故障捕获」「缺口识别」「插单触发」「异常捕获」「变更受理」「窗口预约」「变更登记」——
**七个不同的词，没有一个是「捕获」**（DZ-01、DZ-04 用「捕获」，所以计数是 2）。
这一条本身不算错，业务化命名是对的；但它说明「八步闭环」的**命名契约没有落实成枚举**：
第 1 步该叫 `capture`，七个扰动的第 1 步都应该是同一个 step 类型的一个实例，中文名可以随便起。
现在是七个中文名各写各的，写代码时得靠人脑做模糊匹配。

**给做智能体的人一句话结论**：把闭环写成**状态机**而不是段落。
`STEP = enum(CAPTURE, CLASSIFY, ASSESS, PLAN, APPROVE, DISPATCH, TRACK, RETRO)`，
每个扰动的流程是 `list[tuple[DISTURBANCE_ID, STEP, 责任人, 时限]]`。
一旦这么建模，「时序图少了 CLASSIFY」这种问题就不可能存在——因为一个不完整的状态机会直接编译不过。

::: info 时限这个词在文档里同时干着三种活

表3-1 的「核心时限」列 7 行，脚本按语义分了三类：**响应型（≤）5 行、触发型（>即）1 行、提前量型（≥）1 行**。

响应型是 `deadline`，触发型是 `threshold`，提前量型是 `lead_time`。
混在一列里，验收的时候就会被统一当成 `deadline` 去测，然后 2 行永远测不出来——因为它本来不是时限。
:::

1. 「双向涟漪推演」的输入是引用图。要做**逆推**（某台设备故障 → 哪些在排工单受影响），

2. 上线初期预测 50~60%，形态判到建议期，意味着**它的每一次输出都必须有人签字才能下发**。
   而流程里给人签字的预算是 **15 分钟**（DZ-01、DZ-03 的审批步写着「15分钟未审自动升级」）。
   一个准确率 50~60% 的建议，要计划员在 15 分钟内判「接受/驳回/微调」，
   驳回还要填原因（形态表明写「驳回原因必填」）。
3. 它同时出现在建议期和自主期两档。自主期那一档的适用列原文是「成熟期：M-03率先达到；A-01/A-02/A-05/M-04随后」——

   也就是说：形态可以慢慢升档，**负载不会等你升档**。

::: danger 这一页最贵的一条结论

**关键路径智能体的能力评估，和它承担的责任数量，是两个人分别写出来的。**

T17 那张难度表现在把 M-04 标成最高难度档（4.0，「依赖全工序图谱」「≤15分钟KPI对数据及时性要求最高」）——
这行字证明写它的人**知道**这两件事难。但同一份交付物里，没有任何一处把「5/7 主责 × 15 分钟 × 建议级需人签」
这三项乘起来算一次容量。算出来的东西很朴素：**要么 M-04 上线初期只做瓶颈设备这一类扰动（把 5/7 降到 1/7），
要么 15 分钟的 SLA 分级给（一级 15 分钟、其他级次日）——两个决定都必须显式写进表3-1，不能靠现场默契。**
:::

**给做智能体的人一句话结论**：给每个智能体算一张**负载表**：
`承担的场景数 × 该场景的 SLA × 是否需要人签 × 上线初期预测准确率`。
这张表一行就能把上面三条矛盾写成一条可判真伪的断言。
M-04 这一行是 `5 × 15min × 需人签 × 0.55`——任何人看到这一行都会立刻去改 SLA 或者减场景。

数一遍：表3-1「分级路由」列里能当阈值用的数字，**0/7 行**。
56 条扰动规则里给出数值阈值的分级定义，**2 条**：

- `DD-R02`：影响面 **<5 工单**为局部级；跨工序为协同级；影响月计划为全厂级
- `TS-R06`：检测资源停机 **>4 小时**或排队 **>20 件**即触发受阻评估

`DD-R02` 是全章**唯一一条能用数字判「这算不算局部」的规则**。而它的归属是 DZ-05（订单变更）。
同时，表3-1 里真正明写「按影响工单数／影响面」分级的只有 **2 行：DZ-01 和 DZ-07**——
**给得出这条线的规则，不在用得到这条线的两个扰动名下。**
所以 DZ-01 的设备故障进来时，「影响工单数」这条梯子要用哪张表的哪条规则，文档里是断的。
（`TS-R06` 同理：它给的是触发阈值而不是分级阈值，且只服务 DZ-06。）

再看梯子的**终点**。第三章 56 步＋56 规则里出现的升级去向有 4 个：
厂部调度中心、生产科长、调度中心、质量科长。
表2-2 的「审批下发」行另写一条：「装、试、修生产指挥部终审，15分钟未审升级主任；其余工艺类型室主任终审，15分钟未审批升级至厂长」。
时序图 W1 又是第三种：L1 自动、L2 计划员、L3 厂部。

**三套梯子、四条路径、没有一个权限矩阵说它们是不是同一套权限。**
「生产科长」和「室主任」是不是同级？「厂部调度中心」和「L3 厂部」是不是同一个审批位？
「升级」这个词在三份工件里各自的终点不同，而**升级终点决定了谁能在 15 分钟之后把方案签下去**。

顺带一个数：表2-2 数出 **8 行**流程环节，正文原话却写「**主线十个节点**与扰动处置支线的流程步骤逐一以流程步骤图展示如下」。
主线节点的个数也有两套：8 与 十。

**给做智能体的人一句话结论**：分级必须是**一个纯函数**，输入可观测的数，输出一个枚举：

```python
grade(impact) -> {LOCAL, CROSS_PROCESS, PLANT_WIDE}
# 输入至少含：受影响工单数、是否触及瓶颈资源、是否跨工序、是否影响月计划
# 阈值来自单一配置源，任何文档只引用 grade 的名字，不许自己重述数字
```

再加一条：**影响面分级和审批权分级是两张表**，写成 `grade → approver_role` 的映射，而不是两套并列的三级。
W1 那张卡片（L1 自动／L2 计划员／L3 厂部）就是这张映射表，只是它被画进了 SVG 的 `<text>` 节点里——
而且被切成了两个节点：脚本原文打出来是
`['/L2计划员/L3厂部）', 'W1 扰动处置审批卡片（分级：L1自动']`，
第一个节点里只有 L1。**图形里的规则，机器读不到，验收也判不了。**

读的人必须先猜这到底是「连续加工偏好」还是「跨车间协同场景」。
（同类的编号复用还有 HC／DZ 前缀被设备台账的 `HC-nn` 撞过一次，那一处也记在规则页。）

::: details 唯一一项绿灯，以及它为什么反过来说明问题

`对交期影响程度` 与 `规则优先级(1~10)` 的关系，在 68 行里完全单调：

- 高影响 35 条，优先级 7~10，均值 **8.5**
- 中影响 26 条，优先级 4~6，均值 **4.8**
- 低影响 7 条，优先级 1~3，均值 **2.0**
- 逆序对（影响低却优先级高于影响高者）：**0**

这条绿灯证明**登记表不是随便填的**——填的人按影响程度排了优先级，而且排得严格单调。

也正因为它单调，下面这条反差就不是笔误，而是设计：

**闭环类规则（名称含 复盘／通知／归档／互认／复审／核查／回传／血缘）10 条，平均优先级 2.9；其余 58 条平均 7.0。
优先级 ≤3 的 7 条里，闭环类占 7 条——全部。**

「闭环」在八步流程里是第 8 步（跟踪、复盘），在规则清单里也是最后一名。
而口号的第二半句正是「消除**无留痕无复盘**」。
一个体系真要不要留痕，看的不是流程图上有没有画第 8 步，而是**第 8 步的优先级数字**。
:::

最后两个数，关于「确认」与「执行」：

- `完全确认 × 部分执行`：**44 条**（68 条里占大头）。
  「部分执行」是一个不承诺任何事的状态——它既不是说没做，也不是说做了，它是「做了但没全做」。
  一条规则的「全」由谁判定，清单里没有列。
- `完全确认 × 未执行`：**1 条**。签了字但没落地，需要有人去问为什么。
- 其中 **R002（五维点检门禁规则）**：确认 = **部分确认**，执行 = **未执行**。
  这条规则就是 A-00 的**全部职责**（五维达标率 ≥90% 是全站上线门禁），
  也是表1-2「数据门禁（A-00）」那一行验收 KPI 的唯一来源。
  第 7 页已经测出 A-00 在四张规划表里 0 行，这里补的是它的**规则状态**：
  **整个编队的上线门禁，处在「没签完、也没跑」的状态。**
- 对照一下 DZ-03 的第一依据 `R028（插单评分卡规则）`：确认 = **完全确认**。
  问题 #3（插单靠领导协调）的交付物，是三十七项问题里优先级 P0 的那一条——它签完了。

**给做智能体的人一句话结论**：两份规则清单要立刻定一个**唯一的家**。
建议登记表（68 行那份，它有影响程度、优先级、执行状态）当主表，加一列 `design_doc_rule_id`（值就是 `GZ-R01` 这种），
**由登记表单向生成文档里的规则表**，而不是两边手写。
两条 CI 断言：`design_doc_rule_id` 必须在文档里存在；两份里同一条规则的名称必须完全相等（或干脆不写第二次）。
第 8 页这一步的所有红线里，这是**改动成本最低、当天就能做完**的一条。

## 这一页的三条带走

1. **流程要写成状态机，不要写成段落。** 八步闭环一旦被写成中文句子，它必然在七个扰动里长成七种样子，
   还会在两张时序图里各被省一步。`STEP` 是一个枚举，每个扰动的流程是一个数组，
   CI 检查数组里有没有 `CLASSIFY`——这比「对账 56 步」便宜两个数量级。
2. **责任矩阵是流程的视图，不是它的兄弟。** 表3-1 和 56 步各写各的结果是 5/7 不一致，
   代价是一个真实承担 5 个步骤的智能体（M-06）在整套规划体系里不存在。
   `owner` 字段只允许出现在步骤上，主责列由聚合生成，聚合结果与编队清单做交集校验。
3. **每条时限都必须带一个起算事件。** 「≤30分钟」这三个字符在交付包里出现五次，
   没有一次说从哪一刻按下秒表——所以它现在不可判真伪。
   `sla(value, start_event, measure_source)` 三元组，缺任何一项都不许进 KPI 表。
