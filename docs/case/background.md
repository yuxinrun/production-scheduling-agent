# 客户与现场

**「先讲算法」是排产项目里最常见的顺序错误。**

算法的难度不取决于工件数，取决于**现场允许你动哪些变量**。
一条「100 台机器 × 500 道工序」的流水线，很可能比「10 台五轴 × 28 道工序，
外加 20 天有效期、军检节点、两装两试返工回路」好解得多：前者是规模问题，
后者是**约束问题**。规模问题的难度写在论文里，约束问题的难度写在业务里。

所以这个案例的第一页不放公式，放底牌：这家厂是谁、七道工序各自怎么排、
调研问出了多少条问题，以及**这些数字加起来对不对**。

::: tip 本页每个数字的出处
《某某智能排产项目调研现状报告 1.0》《业务管理模式设计方案 V1.0》
《问题提炼与目标对齐清单（37 项）9.17.xlsx》《排产规则提取清单 V1.0.xlsx》
《技术能力点检清单》《需求分析与技术栈方案》。
文档里印着的总数（37 / 56 / 68 / 137 / 68,884 / 160,160）我没有直接信，
用 [lisa_totals.py](/snippets/lisa_totals.py) 重算了一遍，真实输出贴在第六节。
:::

## 一、三十秒把这家厂说完

| | |
| :-- | :-- |
| **客户** | 中国航发贵州某某航空发动机有限公司——军工航空发动机，整机与零部件**离散制造** |
| **项目** | 某某智能排产智能体（AI 先锋项目）。英文代号 **LISA**（项目内部代号，名称已脱敏） |
| **规模** | 两厂区 / 10 个分厂 / 七大工序域 / **108 个核心产品 × 28 道工序** |
| **现有 IT** | MES（执行）、ERP/SAP（资源）、QMS（质量）、WMS（仓储）、PLM（工艺）、HR/EAM（人/设备），另有一套只管钣焊与部装的 APS |
| **咨询方** | 上海承丰，已交付 9 大类成果：调研现状、业务模式设计、智能体定义、本体方案、数据集设计与标注模板、MCP 方案、能力点检、MVP 清单、培训材料 |
| **它不是什么** | 不是 APS 升级版，不是 ChatBI，不是「接个大模型自动写计划」——见第九节 |

生产特点浓缩成四个词：**多品种、小批量、长流程、强约束**。
这四个词不是修辞，每个都能直接翻成一条实现约束：

| 特点 | 现场长什么样 | 落到代码里是什么 |
| :-- | :-- | :-- |
| 多品种 | 108 个核心产品，各走自己的 28 道工序 | 工艺路线不是一张表，是上百条链；换型矩阵**非对称**（A→B ≠ B→A） |
| 小批量 | 军品紧急订单占比高，关重件单独管控 | 主目标不是设备利用率，是交期与合规 → 目标函数是**字典序**，不是加权求和 |
| 长流程 | 锻造 → 机加 → 钣焊 → 热表 → 部装 → 总装 → 试车 → 大修，跨两个厂区 | 一次扰动的涟漪跨 7 个责任主体，跨厂还要脱敏 → **必须分层编排**，一把梭必崩 |
| 强约束 | 钛合金焊接 20 天有效期、军检节点、两装两试返工回路、外协依赖 | 硬约束违反即阻断，且**不许人工放行**；有效期还要按跨节假日衰减来算 |

最后那半句最容易被程序员忽略：**有效期是按日历日衰减的，不是按工作日**。
一个 20 天的焊接有效期，跨过国庆 7 天假期，实际只剩 13 天可用工艺窗口——
你的校验代码如果只减工作日，就会在假期后第一天放出一堆违规方案。

## 二、七道工序，七种崩法

调研覆盖七道工序，逐工序问了两件事：「现在靠什么排」和「数据长什么样」。
这张表就是需求说明书——**每一行都在告诉你，七层底座里哪一层先烂**
（层的定义见 [七层底座](/arch/seven-layers)）。

| 工序 | 排产现状 | 核心数据现状 |
| :-- | :-- | :-- |
| 机加工 | APS 固定参数输出不可用，每中心每天人工调整 3~4 小时；换型 0.5~1 天且数据不准 | APS 日志与人工调整**无对照记录**；实绩报工存在断点 |
| 锻造 | 批次合并、换模排序靠人工经验；人员负荷是瓶颈但未建模 | KPI 手工统计；模具寿命台账有记录，但**未用于排产** |
| 钣金焊接 | APS 采纳率仅 20~30%；X 射线探伤合格率约 60%，返工不确定性大；外协进度黑箱 | 焊工资质矩阵未结构化；探伤结果线下传递 |
| 表面热处理 | 继承 APS 排产，组批合炉未完全系统化；人工作业一致性差；工艺结构化数据不准 | 制造执行系统刷新延迟超 30 秒；MES 缺人员技能矩阵，工步与人员技能不匹配 |
| 总装 | 手工 Excel 排产、**无限产能、逾期不重排**；月计划编制 1 天 × 6 人；齐套纯人工点检，装配齐套率仅 60% | 完工月末集中报工入库；MOM/ERP 编码不统一 |
| 大修 | 手工 Excel 排产、无限产能、齐套纯人工点检 | 基于故检报告和修理文件排产，**系统中没有工艺路线** |
| 试车 | 日计划达成率仅 50%；在制品到料不可视；两装两试返工回路靠人工协调 | 台架日历未系统化；转序入库状态不共享 |

::: warning 口径瑕疵：七道工序到底是哪七道
上面这张表（调研现状报告 §2.1）的第 5 行写「总装」，
同文档 §2.2 的场景标题写「装配」，需求方案的执行摘要写「机加、锻造、钣焊、热表、装配、试车、大修」，

**三份材料三种写法。** 这不是吹毛求疵：排程域怎么切，直接决定你的原子级智能体是 7 个还是 8 个，
进而决定接口数量、审批路由和验收范围。开工前把「工序域」钉成一张对照表，
是本项目最便宜的一份文档。
:::

## 三、时间都花在哪：把现状换算成小时

排产系统的价值主张通常写成「更快」。但「快多少」要有分母。
把调研里的现场人工耗时抄成一张表，分母就有了：

/>

**为什么「快 8~12 倍」不是性能指标，而是功能指标？**
因为 2~3 小时的变更评估意味着：现场不会用它。
有人在电话里问「这个件晚三天会怎样」，你回答说「等我下午算完告诉你」——
这个问题在等你的两个小时里已经被拍板了，你的计算只是给既成事实补一份报告。
**响应时间掉到提问者的决策窗口之内，这个能力才第一次被使用。**
这就是 [求解服务怎么编排](/arch/solver) 那一页要把 15 分钟拆成预算表的原因。

## 四、四条断链：为什么「有系统」不等于「有数据」

调研里反复出现同一个句式：某个数据**有**，但**没进排产**。

| 断链 | 材料里的原话 | 后果 |
| :-- | :-- | :-- |
| 计划 ↔ 实绩 | APS 日志与人工调整无对照记录 | 永远算不出「APS 到底差在哪」，采纳率 20~30% 这个数没有根因，只有情绪 |
| 完工 ↔ 入库 | 完工月末集中报工入库 | 计划—实际偏差在月末一次性到账，重排拿不到当下事实 |
| 编码 ↔ 物料 | MOM 用图号、ERP 用物料号，无统一命名规则，BOM 不准 | 齐套校验和物料需求预测失真，且这条是**上线前置项**（P0） |
| 台账 ↔ 决策 | 模具寿命台账有记录未用于排产；人员负荷为瓶颈但未建模 | 数据在库里睡觉，排产照旧拍脑袋 |

这四条解释了为什么七层底座把 **L0 数据基座**放在最底下：
它拦的不是「数据不够」，而是「数据看着够」。
现场自评的数据质量五维（完整性 / 及时性 / 一致性 / 准确性 / 唯一性）**低于 70 分**，
而门禁线是各维 **≥90 分**（R002 五维点检门禁）——中间差的 20 多分，
按调研自己的评估，会把智能体准确率封顶在 **60~70%**。
这就是「准确率一期只承诺 ≥60%」的由来，详见 [数据四区间与五维门禁](/case/data)。

## 五、底座现状：56 项能力点检，10 项硬缺口

咨询方以 OpenTrek（专有云智能体工厂 V3.18.6）为预设底座，对 56 项平台能力做了点检。
结论分布是这样的（数字来源：需求分析与技术栈方案 §4.1）：

```text
满足 21 ｜ 部分满足 25 ｜ 不满足 10        合计 56 → 加总一致
满足率 37.5%；把「部分满足」算进来 82.1%

10 项不满足的构成：
  运筹求解器（LP / MIP / 启发式 / 增量热启动 / 数值稳定性）  5 项
  本体建模 + SHACL 校验 + 图谱推理                          3 项
  消息队列                                                  1 项
  DAG 分析组件                                              1 项
```

**看这 10 项落在哪儿：全部是排产项目的命门，一项不剩。**
求解器 5 项（智能体平台自带的算法节点不做 MIP，这是行业常态：LLM 平台把
「调一次 Python」当作能力边界，不把「解一个 10 万变量的整数规划」当能力）；
本体 + SHACL + 图谱 3 项（意味着规则召回、约束校验、涟漪推演都得自建）；
消息队列 1 项（扰动事件的可靠投递，是「变更评估 ≤15 分钟」的**信息流前提**）。

这三类缺口正好对应 [七层底座](/arch/seven-layers) 的 L3（能力组件）、L4（数据与知识）
和 L1（感知接入）。换句话说：**平台能给你的是 L2 编排层，
而项目失败的三个可能位置，平台一个都不占。** 这是选型时最该记住的一句话。

::: warning 「部分满足」不是「基本能用」
25 项部分满足里，最常见的括号注释是「平台具备 X，但需按军工要求加固」——
审计链、脱敏、权限执行、异常降级全在这批。
「加固」两个字在工时表上的意思是：**你重做一遍，只是可以复用它的界面。**
:::

## 六、先把文档里的总数加一遍

这是每个排产项目开工第一天该做、但几乎没人做的事。
把交付材料里印着的总数按它声称的构成重算一遍——加不起来的数字，
在文档里叫「口径」，在验收会上叫「事故」。

下面是 [lisa_totals.py](/snippets/lisa_totals.py) 的真实输出（Python 3.12，只用标准库）：

```text
==========================================================================
[1] 37 项调研问题：六类分布、P0 分布、贡献度三分
==========================================================================
六类条数 [4, 6, 8, 10, 6, 3] → 加总 37，文档封面写 37 → 一致
P0 分布  [2, 3, 0, 1, 2, 2] → 加总 10，文档写 P0 十项 → 一致；P1 = 37 - 10 = 27，文档写二十七项 → 一致
P0 占比 = 10 / 37 = 27.0%
贡献度三分 [12, 15, 10] → 加总 37 → 一致
  注：这份 xlsx 自己在修订说明里写着「原合计行 11/11/6 与分类行加总不一致，
      本版已按附表1修订为 12/15/10」——文档内部的总数自己加不起来，是常态，
      不是个例。所以凡是拿来当验收口径的数，都要这样重算一遍。

==========================================================================
[2] 56 项能力点检：结论分布与缺口构成
==========================================================================
结论分布 [21, 25, 10] → 加总 56，点检清单写 56 项 → 一致
满足率 = 21 / 56 = 37.5%；含部分满足 = 46 / 56 = 82.1%
10 项不满足的构成 [5, 3, 1, 1] → 加总 10 → 一致
  求解器一项占 5/10 = 50% 的硬缺口——这解释了为什么技术栈方案里
  COPT 是第一个被点名外挂的组件：智能体平台自带的算法节点不做 MIP。

==========================================================================
[3] 68 条规则 / 137 条约束：结构对账
==========================================================================
规则：主线 10（R001~R010）+ 七大扰动 7×8=56（R011~R066）+ ECN 排查 2（R067~R068）
      10 + 56 + 2 = 68，清单实际行数 68 → 一致
约束：硬约束 HC-01~11 适用单元 67 + 软约束 SC-01~13 适用单元 70 = 137，
      文档写 137 条 → 一致（注意口径：137 数的是「适用单元」，不是约束模板条数 24）
执行情况 [5, 51, 12] → 加总 68 → 一致
  完全执行占比 = 5 / 68 = 7.4%；未执行 = 12 / 68 = 17.6%
  确认状态倒是很好：完全确认 50 + 部分确认 18 = 68，未确认 0 条。
  「业务把规则说清楚了」和「系统把规则跑起来了」是两个字段，
  这两个字段的差（68 - 5 = 63 条没完全落地）就是智能体要填的坑。
```

三个值得单独说一说的发现：

1. **`137` 不是约束的条数，是约束的「适用单元」数。**
   硬约束模板只有 11 条（HC-01~11），软约束 13 条（SC-01~13），模板合计 24 条，
   乘以适用工序/资源单元后得到 67 + 70 = 137。**这条口径直接决定你的数据模型**：
   如果按「137 条规则」去建表，你会得到 137 行互相不知情的记录；
   按「24 个约束模板 × 适用单元」建模，才是本体与 SHACL 的形状
   （见 [本体、图谱与 SHACL 护栏](/arch/ontology)）。
2. **68 条规则里，完全执行的只有 5 条（7.4%）。**
   而「完全确认」有 50 条。业务说得清清楚楚，系统一条都没跑起来——
   这 63 条的差，就是智能体的工作量清单。任何一份排产 agent 报价单
   如果没把这 68 行读进去，它估的是 demo 的工时。
3. **唯一自己承认加不起来的那条，恰好在问题清单的合计行里。**
   `11 + 11 + 6 = 28 ≠ 37`。修订说明把它改成了 12/15/10。
   这件事的启示不是「文档有错」，而是**文档知道自己有错并且写下来了**——
   这才是可以交付的状态。你的方案里那些「约等于」，最好也这样留一句。

## 七、上线前置门禁：P0 十项

37 项里有 10 项被标成 P0，客户给的定性是**上线前置门禁**，不是「优先级高」：
不做完，后面的智能体能力没有地基，验收无意义。

| # | P0 事项 | 出自哪一类 | 它挡住什么 |
| :-- | :-- | :-- | :-- |
| 1 | 齐套自动化 | E 齐套协同 | K5 装配齐套率 60% → 100% |
| 2 | APS 替代 | B 计划模式 | K1 采纳率 ≥85% |
| 3 | 插单规则定义 | B 计划模式 | 军品急件无规则 = 计划员互相抢资源 |
| 4 | 到料可视化 | E 齐套协同 | 试车达成率 50% 的第一制约 |
| 5 | 异常 SOP 与记录 | D 执行闭环 | 扰动处置无法回放，也就无法优化 |
| 6 | KPI 口径与采集 | F 度量合规 | 所有 KPI 都无法证明达成 |
| 7 | 数据质量五维门禁 | A 数据基座 | 门禁不过，模型输入失真（准确率封顶 60~70%） |
| 8 | 军工合规留痕 | F 度量合规 | 不过合规评审就上不了线 |
| 9 | 无限产能 → 有限产能 | B 计划模式 | 排出来的计划物理上做不到 |
| 10 | 编码与 BOM 治理 | A 数据基座 | MOM 图号 ↔ ERP 物料号对不上，齐套校验失真 |

**注意第 9 项：「无限产能改有限产能」被列成 P0，说明现状 APS 的输出连「能不能做」都没保证。**
这一条在数学上是分水岭：无限产能假设资源随时可用，问题退化成关键路径计算，多项式可解；
有限产能一进来，排序就变成 NP-hard（[排产为什么难：NP-hard](/problem/np-hard)）。
也就是说，这家厂正站在「能用 Excel 算」和「必须上求解器」的分界线**内侧**，
而 P0 清单要求你把它搬到外侧。

第 6 项和第 8 项看起来像行政工作，实际是**工程前提**：
没有 KPI 口径，你的优化目标就是一句口号；没有留痕，你的方案在军工场景里不具备可交付性
（[审计链：让决策可回放](/arch/audit) 那一页实测过：一次 NTP 校时回拨就能让 6/12 条事件错位）。

## 八、军工四性：把合规文件翻译成接口签名

客户明确提出的四条本质约束，逐条翻译成代码：

| 军工四性 | 客户的原话 | 你的接口上长什么样 |
| :-- | :-- | :-- |
| **可追溯** | 决策链路全程留痕（模型调用 / 工具调用 / 审批 / 写入），审计日志防篡改，留存期限符合军工要求 | 四类事件一种格式入链；覆盖率是**入链前的闸门**，不是事后统计 |
| **可兜底** | 规则兜底、人工确认、熔断降级、渐进授权 | 四层降级链：精确求解 → 启发式 → 规则引擎 → 人工；每层都要**留下自己是降级产物** |
| **可解释** | 白盒归因，方案调整 100% 附带归因说明 | 归因字段必填且结构化：本体 IRI + 规则号 + 数值，不是自由文本 |
| **安全合规** | 私有化部署、数据不出内网、脱敏不可逆、ABAC、密级管控 | 写路径只有一个工具、一个 Scope；跨厂交换前脱敏，化名不可逆 |

智能体专项问卷（A-01~A-30，共 30 项）里有三条，比任何合规条款都更直接影响架构：

| 问卷项 | 现场结论 | 被它决定的设计 |
| :-- | :-- | :-- |
| A-23 反馈方式 | **仅异常时**反馈并填写详细原因，不增加计划员日常标注负担 | 你拿不到「计划员为什么驳回」的日常样本。人机分歧只能靠影子模式与隐式信号采集，别指望标注 |
| A-28 学习方式 | T+1 批量学习，**不做实时在线学习** | 记忆层是批处理管线，不是在线更新。任何「这次跑完就学会」的设计当场否决 |
| A-30 可解释性 | 输出必须完整可解释、带白盒归因 | 归因不是 nice-to-have，是输出的**必填字段**（配合 #53 那条验收） |

::: tip 这三条为什么值钱
它们把「能不能做」变成了「不许做」。程序员最容易犯的错，
是把现场问卷当需求列表读——读的是「客户想要什么」；
这三条该读的是「客户拒绝什么」。**拒绝项才是架构的真正约束**，
因为它背后是组织已经付过代价的失败。
:::

## 九、它不是什么

需求方案 §2.2 的定位原文是：**「运筹求解器 + 规则引擎 + 知识图谱 + LLM 智能体」四层融合系统**，
并且加了一句非常关键的限定——

> LLM 只做编排、解释与兜底，**绝不做数值排产的唯一决策源**。

把这句话展开成四条否定，就是这个项目与「AI 排产」宣传稿的分界线：

| 常见的误解 | 实际约束 | 不遵守会怎样 |
| :-- | :-- | :-- |
| 「大模型来排产」 | 所有数值结论由 L3 求解器 / 规则引擎产出，LLM 负责组织与解释 | 模型把 8 道工序排成 7 道，而且语气很自信；审计链里查不到它怎么想的 |
| 「这是 APS 升级」 | APS 的失败是**无限产能 + 黑盒规则**，不是算力不够 | 换一套更快的 APS，采纳率还是 20~30%，因为计划员看不懂它为什么这么排 |
| 「加个聊天框就行」 | 写路径只有 1 个工具 + 1 个 Scope + 一次性票据 + 电子签名 | 未审批写入拦截率达不到 100%，第 8 项 P0 直接不过 |
| 「知识图谱是展示用的」 | 本体是唯一语义源：SPARQL 可查、Cypher 可推、向量可召回、SHACL 可校验 | 「齐套」在三个系统里有三种定义，跨厂协同会每次都吵一遍 |

四层各自的位置：[MCP 接入层](/arch/mcp)（L1，只读工具面）→
[三级智能体](/arch/three-level)（L2，C/M/A 权限不对称）→
[求解编排](/arch/solver) + [写保护与降级链](/arch/guardrail)（L3/L6）→
[本体与护栏](/arch/ontology) + [审计链](/arch/audit)（L4/L6）。

## 小结

1. **先读现场，再选算法。** 这家厂的难度来自约束（有效期、军检、资质、返工回路），
   不来自规模；规模问题可以用算力换，约束问题只能建模。
2. **七道工序 = 七种崩法**，红色最密的行是总装与试车，客户把最难的两块留给了你。
3. **四条断链的共同句式是「数据有，但没进门」**——所以 L0 门禁必须建在链路入口。
4. **56 项点检的 10 项硬缺口全在命门**（求解器 / 本体 / 图谱 / 消息），平台能给的只有编排层。
5. **文档里的总数要自己加一遍**：137 是适用单元数不是模板数，68 条规则只有 5 条完全执行，
   贡献度合计行曾经自己写着自己算不平。
6. **P0 十项是门禁不是待办**，其中「无限产能改有限产能」把问题从多项式推到了 NP-hard。
7. **军工四性可以逐条翻译成接口签名**；而 A-23 / A-28 / A-30 这三条「客户拒绝项」
   比期望项更能定架构形状。
