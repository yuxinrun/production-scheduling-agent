# 投产配置清单：56 项点检、28 类要自建的东西、0 张建设清单

这一页讲一份**甲方自己写的表**：《黎阳智能排产智能体技术能力点检清单-V1.0.xlsx》。
56 行 × 11 列，10 个域、50 个能力域，每行都带技术栈、协议、Harness 约束、验收基准、优先级、是否必须，
以及最要紧的一列——**候选平台 OpenTrek 能不能满足**。它的文件用途栏写得很直白：
「支撑技术评审、平台选型验证与验收测试」。这就是很多人找的那张「投产配置清单」。

先说清这页跑什么。不评价某个能力该不该有点检项（那是架构决策），只跑三件事：

1. **这张表的数对不对**——逐行重算，和它自己的「分域统计」「说明与统计」两个汇总层对撞；
2. **缺口有没有落点**——「不满足」的那些东西，在 11 列里有没有一列能变成任务；
3. **判据能不能判**——验收基准那一列，今天能不能写出一个 `assert`。

脚本在 [checklist_probe.py](/snippets/checklist_probe.py)，纯标准库，八段输出全贴在下面。
清单里 56 行原文、10 个分域统计、说明与统计全文、《技能与工具清单》的规模，都作为字面量内联在脚本里，
可以离线重跑。密级说明那句「本清单按内部资料管理，涉及平台能力与缺口内容不得外传」我照原文贴在这里，
本页只讨论**结构问题**，不复述任何平台实现细节。

结果先放这里：

```text
  56 项点检的账：满足 21／部分满足 25／不满足 10
  一期必须=是 的 52 项里，完全满足 18（34.6%）→ 65.4% 得自己想办法
  「不满足」10 项里 5 项是 P0 阻断项，且正好是：本体 → SHACL → 依赖分析 → LP → MIP
  备注列自己写了要外挂/自建/自研的：25 行；归并出 28 类部件；独立的采购与自建清单：0 张
  五条 lint 在这张表上挂红：39 条
  35 项体检：绿 8、黄 5、红 22
```

::: tip 这张表最反直觉的一点
**它的统计层是整套交付物里质量最高的，判据层是整套交付物里最不能用的。**
10 个域逐项重算，与「分域统计」「说明与统计」两处汇总**零误差**——这张表是真跑过统计的，不是抄的。
但同一张表里 21 项拿「100%」当通过标准，**只有 2 项说了怎么判、没有一项说抽多少**。
这两件事同时成立，说明做表的人是称职的，只是**没人告诉他验收基准要能被机器执行**。
:::


三个汇总层能对上，不是运气。这说明 P0=40、必须=52、OpenTrek=21/25/10 这些数在后续所有讨论里都可以直接用——
**本页后面每一个结论都建立在这组数之上，所以先花一节把它钉死。**

但「域核查结论」那一格值得单独说一句。它写「既有 10 个域经核查完整覆盖排产智能体体系，无缺失域（详见"域核查结论"工作表）」，
而工作簿只有 3 张 sheet。这是一个非常常见的失败模式：**结论写进了正文，证据表留在某个人的电脑上。**
覆盖性核查的过程没有交付，于是「10 个域是完备的」这个断言，和它下面那 56 行的可信度不是一个量级——
前者的证据是 0 张表，后者的证据是 3 处勾稽。

## 二、两个标签列的交叉表里，有一格按定义就不该存在

优先级和「是否必须」是两套独立标签，各自有定义：

```text
  优先级 →「P0=验收必备（阻断项）；P1=重要（限期补齐项）。」
  是否必须 →「"是"为一期验收必须具备；"否"为可二期增强。」
```

值得学的是那半边自洽：**「P0 一定必须=是」是可以写成一条 lint 的**，而且这张表已经通过了它。
不可取的是另外 12 项——「限期补齐」和「一期必须」同时成立时，甲方在验收现场必然挑一个对自己有利的读法。
自己建表时，这两列要么合成一列，要么把 P1∧是 单独命名（比如「一期目标但非阻断」），别留给现场解释。

顺便注意「必须=否」那 4 项：全部是 P1，其中 3 项平台本来就满足。
唯一「平台不满足 + 可以二期」的是 #31 数值稳定性保障（精度／缩放／不可行诊断）——它在求解器链路上，
而那条链路上已经躺着 5 个不满足了。第五节会看到它为什么值得从「可二期」里捞出来。

```text
    → 一期必须具备的交互能力（角色视图/白盒解释/人机协同/告警）里，平台完全满足 0 项；唯一白送的那项恰好是二期才要的。
```

::: danger 把这 5 项按顺序排一下，会得到一条吓人的链
`#3 本体加载` → `#4 SHACL 校验` → `#25 依赖分析` → `#27 LP` → `#28 MIP`。
这不是「5 个零散缺口」，这是排产智能体的**主干调用链**：语义模型 → 硬约束护栏 → 拓扑关键路径 → 松弛求解 → 精确求解。
链条上任一环缺席，下游全部退化成「大模型直接报一个时间点」——[难度、准确率与形态四档](/case/verdict) 里那四档的下坡路，
起点就在这五行备注里。而且这五项在平台上没有「部分满足」可买：#27/#28 两行备注都是「须外挂求解器」。
:::

再看「交互与体验」这一域的一条反直觉细节：5 项里唯一完全满足的是 **#54 多模态交互**，
而它的「是否必须」= 否。翻译成人话：**平台白送的那一项恰好是二期才要的，一期要的四个（角色视图／白盒解释／人机协同／告警）平台一个都不给。**
这一课很实用：拿平台能力表倒推一期范围时，满足度分布和产品优先级经常是**反相关**的——
因为成熟的国产低代码平台早就把「演示好看」的那几项做好了。

八条里 **六条是清单继承了上游的错误或歧义**，两条数字对得上——而对得上的那两条里就藏着一个坑：
#4 那条 `HC-01~11 全部 67 个适用单元校验通过，硬约束违背率=0` **数字完全正确**（24×7 矩阵的 HC 打勾格子确实是 67，
[/case/data](/case/data) 第八节和 [/case/rules](/case/rules) 都复现过），
但这一格把「SHACL 校验引擎」和「A 体系的生产约束编号」写进了同一句话——而这两套编号共用的 11 个号**语义交集为 0**。
也就是说：**这条 P0 判据在字面上可以完美通过验收，实际校验的是 67 个和护栏无关的 SHACL Shape。**
引用别人的数字不难，难的是引用时确认对方那套编号体系的名字。

::: tip 一条通用做法
凡是「本表引用了别处的数」，就把那个数拆成两半写：`值` 和 `来源口径`。
`核心68,884条（xlsx B 口径；设计方案为 A 口径 71,888，差 3,004 条）` 这样写一格，
就没人会在验收现场说「我们文档里是 7 万多」。
:::

## 八、五条 lint 实跑：一张 56 行的表能同时挂多少条断言

前面几节的发现是零散的。这一节把它们**写成断言跑一遍**——这也是一张点检表应有的交付形态：
不是「读起来很清楚」，是「CI 里绿不绿」。

```text
  L1 判据含「100%」⇒ 同一格须给出样本集/抽样比/判定人
     命中 21 行（列里没有这三样东西，一行都判不了）：#2/3/5/7/8/14/19/21/23/25/27/32/33/39/47/48/49/50/51/53/56

        [ 5] Top-10召回命中率≥90%（按ZD-01/07/08抽样评测），溯源字段100%非空
        [26] 可选路径场景路径选择合理率≥95%（专家抽样评定）

     #41 异常降级与熔断（求解超时/模型异 15s  vs  #27 线性规划求解（产能分配/负荷均衡 60s → 挂红（需 >120s）

       两处口径一致 → 15 秒不是笔误，是按字面实现就会掐死 #27 的那条线。

  L3b 验收写「相对另一个环节的 X%」⇒ 那个环节的时限必须存在
     #29 「精确求解 的 10%」→ 锚点行 #28，其中写了时限的 = 0 项 → 锚点是空的

     #41 验收「模型故障转规则兜底」→ 去向是 #23 排产模板规划（按产品族/工艺路线模板生成初始方案｜平台判定 = 部分满足
     #41 的 OT 原文：部分满足：沙箱超时熔断可用，业务降级链路需自建
     → 降级链路的两条出路：一条要「算法库自研」（#29 不满足），一条要「排产模板结合规则库自建」（#23 部分满足）。
       熔断本身平台可用（#12/#41 的 OT 都写「沙箱超时熔断可用」）——
       于是最容易出现的现场形态：门能按时跳闸，跳下去没有接的东西。

  汇总：L1 21 + L2 10 + L3 1 + L3b 2 + L4 2 = 36 条挂红，全部来自同一张 56 行的表。

```

L1 那 21 行里，只有 #5 和 #47 说了怎么判（抽样评测／抽样核查），**没有一行说抽多少**。
L3b 是本页最新、也最值得抄的一条：**判据之间会互相引用，而被引用的那一格是空的**。
#29 写「启发式求解时间 ≤ 精确求解 10%」、#30 写「增量重解耗时 ≤ 全量求解 20%」，
两个百分比都锚在 #28 上，而 #28 的验收只写「在时限内求得可行解率 ≥99%」——**它自己就没有时限**。
于是这两条相对判据的可判定性 = 0：分子没测过，分母没定义。

L4 更狠：#41 的验收写着降级路径本身——`求解超时自动转启发式，模型故障转规则兜底`。
把这句话拆开对号入座：

| #41 判据里的出路 | 指向的行 | 平台判定 | 备注列自己说要干什么 |
|---|---|---|---|
| 超时转**启发式** | #29 启发式/元启发算法 | 不满足 | 算法库自研 |
| 模型故障转**规则兜底** | #23 排产模板规划 | 部分满足 | 排产模板需结合规则库自建 |

而 #41 自己的 OpenTrek 说明是「沙箱超时熔断可用，业务降级链路需自建」——
**跳闸的机制平台给了，接住的东西两行都不在平台上。**
这就是我做这类系统时最怕看到的形态：每一个部件单独看都有归属，串起来看那条兜底路是断的。
它不是文档错误，是**没有任何一步做过这张对号线**，而做这件事只需要一个 `for` 循环（上面那段输出）。

```text
  ④ 16 个智能体里 3 个在 56 行中 0 落点，其中一个正是 L0 门禁的执行者 A-00。
  ⑤ 判据之间还会互相引用：#29/#30 的时限锚在 #28（无时限）上，#41 的降级去向是 #29（不满足）——
     单行读每条都合规，跨行一读全悬空。这类错误只有做图才能发现，做表发现不了。
  CI 化五条断言（五条全在 [8] 里实跑过，合计挂红 39 条）：
    L1 验收基准含「100%」⇒ 同一格必须给出分母（样本集、抽样比、判定人）；
    L2 OpenTrek 列 = 不满足 ⇒ 必须指向建设清单的一行（负责方 + 工期），否则该行不得进入验收；
    L3 任意两条时间上限 ⇒ 熔断/降级触发线必须晚于被监控项自己的 SLA，且留 ≥1 倍余量；
    L4 判据里写明的兜底去向 ⇒ 那个去向自己的平台判定不能是「不满足」；
    L5 智能体编号 ⇒ 每个编号至少被一行验收基准点名，用 [7] 的反查表当断言跑。
```

五条断言我照抄在下面的伪代码里，它们全部就是上面那段的抽象：

```python
# 对任何一张「能力点检 / 选型对照」表都应该跑的 lint（本仓库 docs/public/snippets/checklist_probe.py 已实现）
def lint_checklist(rows):
    bad = []
    for r in rows:
        # L1 判据可执行：写 100% 必须带分母
        if "100%" in r.验收基准 and not (r.样本集 and r.抽样比 and r.判定人):
            bad.append((r.序号, "100% 无分母"))
        # L2 缺口必须有落点：不满足 ⇒ 指向建设清单的一行
        if r.平台判定 == "不满足" and not (r.负责方 and r.目标完成 and r.预算来源):
            bad.append((r.序号, "缺口无归属"))
        # L3 时间预算自洽：熔断线必须晚于被监控项的 SLA
        if r.kind == "熔断" and r.timeout <= watched(r).timeout * 2:
            bad.append((r.序号, "熔断早于被监控项用满预算"))
        # L4 出路必须存在：判据里写明的兜底去向，自己不能是「不满足」
        for tgt in fallback_targets(r):
            if tgt.平台判定 == "不满足":
                bad.append((r.序号, f"降级去向 #{tgt.序号} 不可用"))
    # L5 引用完整性：智能体编号 ⇒ 至少被一行验收基准点名
    for code in AGENT_CODES:
        if not any(code in r.验收基准 for r in rows):
            bad.append((code, "0 落点"))
    return bad
```

`lint_checklist` 跑在这张表上返回 **39 条**（21 + 10 + 1 + 2 + 2 + 3）。
一张 56 行的表能同时挂五条断言，说明它是**给人看的**，不是给 CI 跑的——
这也解释了为什么它的统计层那么干净：**加总对计算机来说很便宜，判据可执行对写表的人来说很贵。**

## 小结

1. **这张表的统计层是全站最好的**：10 个域逐域重算，与「分域统计」「说明与统计」两处汇总零误差
   （56／40／52／21/25/10 三源一致）。它确实是「真做过核查」的产物，不是抄的。
2. **但它引用了一张不存在的工作表**：说明栏写「详见"域核查结论"工作表」，工作簿只有 3 张 sheet。
   结论进了正文，核查过程没交付。
3. **两个标签列有一格语义打架**：P0∧必须=否 = 0（自洽，可写成 lint），而 **P1∧必须=是 = 12 项**——
   「限期补齐」同时被标成「一期必须」，验收现场必然挑一个读法。
4. **52 项一期必须里平台完全满足只有 18 项（34.6%）**；部分满足 25、不满足 9。
   而提到「外挂/自建/自研」的 25 行里，**15 行是「部分满足」、10 行是「不满足」**——
   只筛「不满足」会漏掉同样要点东西的 15 行。
5. **5 个 P0 阻断项是主干调用链上连续的五个环节**：本体 → SHACL → 依赖分析 → LP → MIP；
   「求解/算法引擎」域 5 项 0 满足、连部分满足都没有；「规划器＋求解」这 9 项 0 满足。
6. **交互域的反相关**：唯一完全满足的 #54 多模态是「可二期」，一期要的角色视图/白盒解释/人机协同/告警 0 满足。
   平台白送的常常是演示好看的那项。
7. **备注列里藏着一张真正的建设清单**：25 行自说外挂/自建/自研，归并出 **28 类部件、覆盖 34 行**
   （买 3、自研/买引擎 2、自研 6、自建 14、对接 2、管理制度 1）。**而 11 列里没有负责方、工期、预算任何一列** →
   没有工期的缺口不是计划，是愿望。措辞六套（自建 12／外挂 11／需对接 4／自研 2／加固 2／配套 1），筛都筛不全。
8. **判据强度写得很足，判定性为零**：41/56 项有阈值，其中 **21 项拿「100%」当标准，只有 2 项说了怎么判（#5/#47）、0 项说了抽多少**；
   #8 的「8 项质量指标」全文无清单（同行只列 4 项）、#39 要对齐的 `review_status` 有 68,912 行是占位符、
   #50 要的「双签」全库 3 个工号且都是模板示例。
9. **时间上限两两一比就穿帮**：11 个时限散在两列、无处求和（端到端那条链是本页加的）；
   **#41 熔断 ≤15秒 比 #27 LP ≤60秒 的合法用时早 45 秒**，且 #12 的 Harness 同样写 15 秒 → 这不是笔误；
   另有 5 项「必须=是」的求解/重排项 0 时限，其中 #28 只写「在时限内」——
   而 #29「≤精确求解 10%」与 #30「≤全量求解 20%」这两个百分比，**锚的正是那个没有时限的 #28**。
10. **判据之间还会互相引用，且被引用的一方不在平台上**：#41 的验收写「超时自动转启发式」→ #29 不满足（算法库自研）、
    「模型故障转规则兜底」→ #23 部分满足（排产模板需自建）。跳闸的机制平台给了，接住的东西两行都不在平台上。
11. **清单引用了上游的错误**：#1 继承 19,800（实测 22,634，19,800 是表14 少写 406 的那格）、#1 把没交付的 M 元数据写进能力名却只验 T1~T5、
    #2 沿用 docx 全文 0 次的 68,884、#2 把设计文档的「中类抽审 ≥10%」写成「专家确认率 100%」。
    两处勾稽一致（#4 的 67、#23 的 108 族×4=432）——**引用数字能对上是可能的，只是没人做**。
12. **反向对账最刺眼**：16 个智能体只有 2 行提到编号；**13 个从未被单独点名，3 个（A-00／C-02／M-06）连区间都罩不住**；
    而 A-00 正是那道对所有智能体生效的 L0 门禁的执行者——**守门员不在点检范围内**。
13. **技能依赖列 100 行全空**：这 100 个技能之间谁调谁、缺一个会不会级联，交付物里没有机器可读表达；
    #33 的判据要求的恰恰是「缺口项有补齐计划」。
14. 35 项体检：绿 8、黄 5、红 22。五条 CI 断言（100% 带分母、不满足⇒有归属、熔断线晚于被监控项 SLA、
    兜底去向自身可用、编号⇒至少被点名）在本页全部实跑，合计挂红 **39 条**
    ——**这就是这张表离「能跑在 CI 里」的距离**。
