# 37 项问题：数据说话

咨询方交付了一张 xlsx：四个工作表、37 行问题、九栏内容。
多数人读它的方式是「哦，问题不少」，然后翻到 P0 那一列开始排期。

这一页要做另一件事：**把这张表当成输入数据，重算一遍。**
算完会出现三个反直觉的结论——P0 不是难度榜、最难的一类一个 P0 都没有、
而整份清单里没有一个字提到算法。

脚本在 [pain_matrix.py](/snippets/pain_matrix.py)：37 条正文按原文内联，只用标准库，
换台机器结果一样。下面的输出是真实跑出来的。

---

## 一、先说这张表的结构

| 工作表 | 内容 | 行数 |
| :-- | :-- | :-- |
| 问题分类归纳汇总 | 六类的条数 / P0 数 / 贡献度分布 / 涉及工序 / 处置方向 | 6 |
| 附表1-问题提炼与目标对齐 | 37 条问题 × 九栏（主题、影响评估、关键任务关联、建议方案、咨询方任务、某某任务、优先级、贡献度） | 37 |
| 附表2-来源追溯 | 每条问题回指调研证据：问卷题号 + 来源文件 | 37 |
| 差异清单 | 类别与工序口径的差异说明（本版为空，即已消化） | 0 |

附表2 是这张表最被低估的部分。37 条问题一共引用了 **40 个独立问卷题号**，
出现 **85 次业务问卷（B-xx）引用、3 次智能体专项（A-xx）、5 次角色问卷（R-xx）**。
也就是说，「齐套性检查完全依赖人工」这条不是某个人在会上提的，
而是机加 B-01/B-09/B-30/B-33 + 锻造 B-33 + 钣金 B-01/B-33 + 智能体调研 A-04 + 日报共同指向的收敛点。

::: tip 这才叫需求侧的可追溯
后端讲审计链的时候我们实测过：一次 NTP 校时回拨就能让 6/12 条事件错位
（[审计链](/arch/audit)）。而**需求也应该有链**：问题 → 证据题号 → 原始问卷。
这张表有这条链，所以它敢在修订说明里写「原合计行加不起来，本版已修订」——
**能被复核的文档才敢承认自己错。** 你的 PRD 如果只有结论没有题号，
三个月后没人能证明那条需求不是拍脑袋加的。
:::

## 三、汇总页声明的分布，逐条重算加不加得起来

```text
问题条数 = 37，类别数 = 6，序号覆盖 1..37 完整 = True

==========================================================================
[1] 汇总页声明 vs 附表1 逐条重算
==========================================================================
  A 数据基座与主数据治理  n= 4(声明 4 √) P0=2(声明2 √) 高/中高/中=2/1/1(声明2/1/1 √)
  B 计划模式与排产规则   n= 6(声明 6 √) P0=3(声明3 √) 高/中高/中=3/2/1(声明3/2/1 √)
  C 资源与约束建模     n= 8(声明 8 √) P0=0(声明0 √) 高/中高/中=0/3/5(声明0/3/5 √)
  D 执行闭环与异常返工管理 n=10(声明10 √) P0=1(声明1 √) 高/中高/中=2/5/3(声明2/5/3 √)
  E 齐套与跨工序协同    n= 6(声明 6 √) P0=2(声明2 √) 高/中高/中=3/3/0(声明3/3/0 √)
  F 指标度量与军工合规   n= 3(声明 3 √) P0=2(声明2 √) 高/中高/中=2/1/0(声明2/1/0 √)
  六类合计 37 条；P0 合计 10 条；贡献度合计 高12 / 中高15 / 中10 = 37 条
  → 全部一致。但这份表并非天生一致：它的修订说明写着「原合计行 11/11/6
    与分类行加总不一致，本版已按附表1修订为 12/15/10」。11+11+6=28≠37。
```

三点值得注意：

1. **九宫格全对**：六类的条数、P0 数、贡献度分布，与逐条重算**完全一致**。
   这是「可以拿来当验收口径」的最低标准，也是这张表愿意被复核的证明。
2. **它曾经算不平。** `11 + 11 + 6 = 28 ≠ 37`——差的正好是 9 条。
   修订说明没有藏着，直接写在表里。你收到的多数客户文档不会这样，
   所以**默认动作是自己加一遍**（[lisa_totals.py](/snippets/lisa_totals.py) 干的就是这件事）。
3. **序号覆盖 1..37 完整 = True**：没有漏号、没有重号、每条只归一个类。
   这三件事在一份人工维护的 xlsx 里并不常见。

## 四、P0 十项 ⊂ 高贡献十二项：包含关系，不是并列关系

```text
==========================================================================
[2] P0 十项 与 高贡献十二项：包含关系，不是并列关系
==========================================================================
  P0 = [1, 2, 3, 7, 8, 9, 10, 15, 16, 17]
  高贡献 = [1, 2, 3, 4, 7, 8, 9, 10, 15, 16, 17, 30]
  P0 里贡献度不是「高」的：无（空集 = P0 ⊆ 高贡献）
  高贡献但没进 P0 的：[4, 30]
     #4 [E类 P1] 跨工序/跨车间/跨厂区无协同排产规则（各工序自定规则，热表厂区每天投诉）
        影响：锻造→机加→热处理→装配链式衔接无规则；跨厂异步协同≤2小时目标缺规则基础；厂区投诉每天发生
     #30 [D类 P1] 贯改排故类任务占比高但无标准流程（装配/大修约占月总订单50%，无标准流程、无审批、优先级靠管理层指定）
        影响：装配/大修正常订单插单几乎没有，但工艺变更、贯改排故类任务约占月总订单50%；处理无标准流程、无插单审批，优先级由管理层指定，重排频次高且不可度量，直接冲击局部重排≤30分钟与计划达成率目标
  覆盖率 = |P0 ∩ 高| / |高| = 10/12 = 83.3% → 只排 P0 会漏 16.7% 的高贡献问题
```

**P0 是高贡献的真子集。** 这个方向的包含关系说明：客户标注 P0 时用的判据是「能不能上线」，
不是「对智能体目标贡献多大」。于是有两条**对目标贡献最高、但不挡上线**的问题被标成了 P1：

| # | 问题 | 为什么没进 P0 | 为什么它其实很贵 |
| :-- | :-- | :-- | :-- |
| 4 | 跨工序/跨车间/跨厂区无协同排产规则 | 没有系统就投诉，但停产不会因此发生 | K8（跨厂协同 ≤2h、SLA ≥95%）的唯一实现路径。它是 [三级智能体](/arch/three-level) 里 M-01/M-02/C-02 存在的理由——**没有它，你的分子级智能体没有需求** |
| 30 | 贯改排故类任务占月总订单 50%，无标准流程 | 现状靠人工兜着，兜得很丑但兜住了 | 装配/大修一半的活儿没流程、没审批、优先级由管理层指定。K4（局部重排 ≤30min）真正的负载就是这 50%，你的重排引擎要为它设计，不是为正常订单设计 |

::: warning 排期时最容易漏的一种任务
不是没人做的事，是**现状靠人肉兜着、所以看起来不像问题**的那类事。
#4 和 #30 都属于这一类：现场不会因为缺它而停产，所以没人把它报成故障；
但你的方案上线之后，这两块的人肉协调会全部转成对系统的实时要求。
**「≤15 分钟出影响面评估」这种 KPI，实现难度几乎全部来自这种从来没被系统承载过的活动。**
:::

## 五、双零类 C：数学难度全在没被标 P0 的那一格

```text
==========================================================================
[3] 类别 × 优先级 画像：哪一类被优先级体系系统性低估
==========================================================================
  A 数据基座与主数据治理  n= 4 P0=2 高=2
  B 计划模式与排产规则   n= 6 P0=3 高=3
  C 资源与约束建模     n= 8 P0=0 高=0 ← 双零类：P0=0 且 高贡献=0
  D 执行闭环与异常返工管理 n=10 P0=1 高=2
  E 齐套与跨工序协同    n= 6 P0=2 高=3
  F 指标度量与军工合规   n= 3 P0=2 高=2
  C 类（资源与约束建模）8 条里装的是：换型矩阵、瓶颈设备保护、钛合金焊接 20 天有效期、
  人员资质矩阵、虚拟设备人员负荷、维修预估 30-40% 准确——本项目全部的数学难度。
  结论：P0/P1 衡量的是「上线阻碍」，不是「建模难度」。照 P0 排技术难度，C 类整个被排到最后。
```

把 C 类这 8 条逐条翻译成建模对象，就会看到它们在数学上是什么：

| # | 现场问题 | 建模对象 | 数学结构 | 难度落点 |
| :-- | :-- | :-- | :-- | :-- |
| 5 | 瓶颈资源有标识未管理（五轴、热处理炉、锻床、真空电子束、试车台架） | 独生子关键资源 + 保护性排产 | 有限产能单机 + 保护带 | 这些设备**没有替代路径**，一个故障就是一条链的延误 |
| 6 | 换型时间不准且无排序规则（0.5~1 天，自评影响「非常大」） | 序列相关换型时间 setup(i,j) | 每台机器一个非对称 TSP | 换型排序与加工排序**耦合**，规模是乘进去的 |
| 14 | 特殊过程与人员约束未建模（钛合金焊接 20 天有效期、资质矩阵缺、缺勤无法考虑） | 时间滞后约束 + 技能受限资源 | time-lag + RCPSP 类 | 有效期跨日历衰减；资质是**硬**约束，不能靠加班解决 |
| 20 | 物流工装车与分解/装配人力未纳入资源模型 | 辅助可再生资源 | 可再生资源容量约束 | 工装车不是设备台账里的设备，建模时最容易漏 |
| 23 | 设备故障与保养协同缺失（无替代设备清单、维修无预计修复时间、保养让步生产） | 随机可用性与维护窗口 | 机会约束 / 场景树 | 没有 MTTR/MTBF，就只能按「一定不坏」排产——然后每天重排 |
| 24 | 手工作业以虚拟设备排产，人员实际能力与负荷未核实 | 虚拟资源容量核算 | 容量口径错误 | 这是**可行性**问题，不是优化问题：产能本身被高估了 |
| 33 | 产能负荷凭经验、无负荷红线、车间间不允许负荷转移 | 可行域定义 | 约束集合本身 | 「不允许转移」这条组织规则就是约束；它决定了你的解空间 |
| 36 | 维修时间预估准确度仅 30~40%，故障数据只记录不分析 | 时长分布估计 | 生存分析 | 用点估计排产 = 把 60% 的错误当成 0% |

**这八条里没有一条 P0，也没有一条「高贡献」，但它们决定了方案是不是可执行的。**
一个更直白的说法：[排产为什么是 NP-hard](/problem/np-hard) 那一页里的归约，
用的就是 setup 时间、时间滞后和独生子关键资源这三样——**它们全在 C 类**。
而 C 类在客户的优先级体系里排最后。

这就是排产项目延期的经典配方：
按 P0 排前两个月，把所有「建模难度」当作「配置工作量」，
在联调时突然发现方案不落地，回头补约束模型，补完发现求解时间超了三倍，
再回来做 [拉格朗日分解](/problem/lagrangian) 或 [启发式](/problem/heuristic)。
**避免这个循环的唯一办法，是把「上线阻碍」和「建模难度」拆成两张排期表分别估。**

::: tip 一句话记住这张交叉表
**P0 决定你能不能上线，C 类决定你能不能上线之后还说得清楚。**
前者是客户催你的，后者是你自己会半夜想到的。
:::

扫一眼这张表还有个副产品：**#35 是整张表里唯一一条承认「AI 会犯错、所以责任要先定」的问题**——

## 七、可验收性：只有 16 条自带数字

```text
==========================================================================
[4] 三十七项里几条自带数值锚点（可验收性的硬指标）
==========================================================================
  A 类：1/4 条带数值 = 25%
  B 类：4/6 条带数值 = 67%
  C 类：3/8 条带数值 = 38%
  D 类：2/10 条带数值 = 20%
  E 类：5/6 条带数值 = 83%
  F 类：1/3 条带数值 = 33%
  合计 16/37 = 43.2% 条问题在影响评估里给了数字
  带数值最多的类是 E（齐套与协同）——因为它的 KPI 早就写在报表上；
  最少的是 A（数据基座）——唯一那个数还是「自评低于 70」，一个负数式的锚点。
```

**43.2% 带数字，意味着 21 条问题没有验收标准。**
D 类 10 条只有 2 条带数字，而 D 类恰恰是条数最多的一类——
「异常记录缺失」「返工不确定」「信息传递靠微信」这些，
做没做完、做好没做好，全靠人的感受。这就是为什么 #9（KPI 缺口径缺采集）是 P0：
**在一个 57% 的问题无法量化验收的清单上，先建度量体系比先做功能更值钱。**

E 类 83% 带数字也不奇怪：齐套率 60%、达成率 50%、协同 ≤2 小时——
这些数早就在报表里，因为它们是**被追责的指标**。
一个组织的量化程度，从来分布「会挨骂的地方」，不分布在「最难的地方」。

## 八、业务清单里没有算法

扫了 37 条 × 5 个内容栏，共 185 个格子：

```text
  [技术] 运筹     命中  0 条 ｜
  [技术] 本体     命中  0 条 ｜
  [技术] 图谱     命中  0 条 ｜
  [技术] SHACL  命中  0 条 ｜
  [技术] 算法     命中  0 条 ｜
  [技术] 优化     命中  2 条 ｜ 建议方案1  咨询方任务1
  [体系] MVDS   命中 11 条 ｜ 影响评估3  关联性10  咨询方任务2

  [体系] 原子级    命中 10 条 ｜ 关联性10
  [体系] 分子级    命中  8 条 ｜ 关联性8
  [体系] 化合物级   命中  5 条 ｜ 关联性5

    「优化」是唯一的例外，命中 2 条，但两处都是业务语义（KPI 关联、MES 性能优化），
    没有一处指目标函数或求解过程。
```

这不是说咨询方不专业——他们给的是**业务模式设计**，本来就不该由他们选求解器。
但这张表说明了一件对承接方极其实际的事：

> **你不可能从需求清单里读出算法。**
> 需求告诉你「谁负责、堵在哪」，算法选型是另一份文档（技术栈方案 §4）的事，
> 而那份文档是你写的。

清单里出现频次最高的是「规则」（23 条）和「MVDS/模型驱动验证」这类体系词，
层级词（原子级/分子级/化合物级/Copilot）覆盖 **20/37 条**。
所以业务已经替你回答了一个问题：**智能体分几级、各管什么**（见 [三级智能体](/arch/three-level)）；
但它没回答的第二个问题——**每一级里算什么**——完全在你手里。

## 九、三个读法，和那张表的厚度

同一张 xlsx，读法不同，得到的东西不同：

| 读法 | 得到什么 | 不读会怎样 |
| :-- | :-- | :-- |
| 当**待办清单**读 | P0 十项 → 前两个月排期 | 漏掉 #4、#30 两条高贡献 P1，上线后才发现协同和贯改没人管 |
| 当**验收清单**读 | 只有 16/37 条自带数字，其余要先补口径 | 做完了证明不了：#9 那条 P0 会反过来卡你 |
| 当**架构输入**读 | C 类 8 条 = 全部建模难度，且零技术名词 | 把建模当配置工作量估，联调时求解时间超三倍，回头改架构 |

最后一组输出告诉你哪些栏可以直接当契约用：

```text
  影响评估     均值  71 字 / 最短  27 / 最长  177 / 空栏 0
  关联性      均值  37 字 / 最短  24 / 最长   59 / 空栏 0
  建议方案     均值  55 字 / 最短  21 / 最长  111 / 空栏 0
  咨询方任务    均值  29 字 / 最短  14 / 最长   50 / 空栏 0
  某某任务     均值  31 字 / 最短  16 / 最长   48 / 空栏 0
  37 条 × 5 栏 = 185 个格子，0 个空格，完成度是真的。
  但「影响评估」平均 71 字，两张待办栏只有 29 / 31 字——
  后果分析写得比行动方案厚一倍多。排期时要去追这倍差的空白：
  每一条问题都要问出「谁做、做什么、怎么算做完」，否则影响评估只是文学。
```

::: warning 字数不是质量，但字数分布是信号
**同一份文档里，越空的栏越可能是雷。**
待办栏（29/31 字）比影响栏（71 字）薄一倍多，说明「问题已经想明白、动作还没定」。
这种分布出现在项目早期是正常的，出现在评审会上就是延期预告。
:::

## 小结

1. **交叉表全对，但它是修过的。** 原合计 11/11/6=28≠37。凡是拿来当验收口径的数，自己加一遍。
2. **P0 ⊂ 高贡献。** 客户的 P0 是「上线门禁」语义；被留在 P1 里的 #4（跨厂协同）和 #30（贯改占 50%）
   恰好是 K8 和 K4 的真实负载来源。
3. **C 类是双零类，装着全部建模难度。** 优先级体系衡量阻碍，不衡量难度——两件事必须分开估。
4. **16/37 条自带数字，21 条没有验收标准。** 先补口径再做功能，#9 自己就是 P0。
5. **业务清单不会告诉你用什么算法。** 九个技术词零命中，而层级词覆盖 20/37 条：
   业务回答「谁负责」，技术栈那一章由你写。
6. **栏位厚度是信号**：影响评估均 71 字、待办栏 29/31 字，倍差就是项目里还没定的部分。
