这份清单列出**必须由你方提供的外部信息**。P0/P1/P2 的代码侧已经全部落地，所以下面每一条写的都是
「给什么形式的数据/口径、给到之后在哪个界面或哪条命令上生效」——不给的那块功能不是壳子，而是
**只会跑在演示数据上**，这一点界面会如实标出来，不会假装接了真系统。

格式统一为：给什么 / 什么形式 / 用来做什么 / 不给的后果。

### F4 只读工具面白名单（`GET /api/mcp/tools`）

外部 Agent 框架接入方式：`POST /api/mcp/rpc`，JSON-RPC 2.0，protocolVersion `2024-11-05`，
`Authorization: Bearer <登录 token>`。方法只有 `initialize / ping / tools/list / tools/call`，
其余方法返回 400 `MCP_METHOD_UNSUPPORTED`；`tools/list` 要 `agents:read`，`tools/call` 要 `agents:run`，
越权 403 `ABAC_DENIED`。**每次调用都写审计链**（`mcp.tool_call`，含参数摘要、耗时、返回字数）。

| 工具 | 取什么数 | 必填参数 |
| --- | --- | --- |
| `lisa_health` | 版本、库引擎、订单/方案/资源计数 | — |
| `list_orders` | 订单台账（状态/优先级/交期/齐套） | — |
| `order_detail` | 单工单工序链 + 三时点齐套结论 | `order_no` |
| `kit_check` | 齐套九要素实算（取值、缺口量化、责任部门） | `order_no` |
| `kit_summary` | 全厂齐套通过率与缺口责任分布 | — |
| `resource_load` | 每台/每型设备占用工时与负荷率 | — |
| `plan_detail` | 方案 KPI、约束结果与工序明细 | — |
| `hard_constraint_scan` | 14 条硬约束逐条判定 + 未评估项 | — |
| `data_quality` | 主数据质量门禁与分项扣分 | — |
| `main_data_freshness` | 六张供给侧表的新度 | — |
| `change_impact` | 扰动事件涟漪影响与延误量化 | `change_code` |
| `search_knowledge` | 知识/规则检索（带出处） | `query` |
| `rule_detail` | 单条规则完整定义与出处 | `code` |

工具返回里凡是 `未接入 / 未校验` 的字段，都表示上游没给数据，**不会当成 0，也不会当成已满足**；
`INSTRUCTIONS` 里已把这条口径写进 MCP 协议文本，外部模型接入时会收到。

### 验收口径（拿到 F1 后 5 分钟能自查）

1. 「设置 → 模型编排」填 base_url / model / 密钥环境变量名 → 保存。填 `http://` 或非内网主机应被拒（`LLM_URL_INSECURE` / `LLM_HOST_NOT_INTERNAL`）。
2. 点「测试连接」→ 返回真实模型名与毫秒级延迟；连不通返回 `LLM_UNREACHABLE`，界面如实报错。
3. 「智能体中心」跑一次齐套编排 → 运行详情顶部出现「内网模型推理」，含调用次数与 token；每步有「模型推理」徽标，`mcp.kit_check(...)` 形式的取数动作与耗时可见。
4. 关掉模型（`enabled=false` 或拔网线）再跑一次 → 徽标变「确定性编排」，`mode=fallback` + 原因写明，**排产结果照常产出**，这就是 F5。
5. `GET /api/audit?action=mcp.tool_call` 能看到每一次工具调用；`GET /api/audit/verify` 返回 `ok=true`。

### 4）D6~D8 + 工装/资质/检验 → 齐套九要素的六张供给侧表

模板都在 [deploy/templates/](deploy/templates) 下，表头带 UTF-8 BOM，Excel 另存为 CSV 即可。**六类都是按自然键 upsert**（重复行更新，不会重复插），任何一行非法就**整批拒绝**并回报行号，不会写一半。

| 数据种类（CLI 的 `kind`） | 模板 | 来自 | 自然键（重复即更新） | 表头必须包含（缺列整表拒绝 `ADAPTER_HEADER_MISSING`） | 值域与留空默认 |

**四个必须对得上的外键**（对不上不会报错，但齐套算不出来，这是最常见的「导了却没生效」）：

1. `materials.product_code` = 产品型号（`products.code`，如 `LY-001`）。**一类产品必须同时有主材行和辅材行**，否则该要素判「BOM 未覆盖」（是缺项，不是未接入）；
2. `stock.material_code` / `inbound.material_code` = `materials.code`。BOM 里有、库存里没有的物料按可用量 0 计算——所以「库存快照必须是全量可用量」，不是只导有差异的行；
3. `tools.domain` / `qualifications.capability` = 资源能力域（和产能台账的 `domain` 同一套字，如「机加」「焊接」「热处理」「无损检测」「试车」），字对不上等于没有；
4. `inspections.order_no` + `seq` = 工单号 + 工序序号。

日期时间接受 `2026-12-05 08:00`、`2026-12-05`、`2026/12/05`、`2026-12-05T08:00` 四种写法。

#### 让它自动跑：三条通道，混用随意

配置存在设置项 `adapters` 里，页面「数据」面板底部的**外部主数据接入**区可以直接看每条通道的上次/下次同步时间、行数、错误码，管理员有「立即同步」按钮。

注意：通道配置**不走**通用设置接口（`/api/system/settings` 会跳过 `adapters`），必须走专门的 `PUT /api/system/main-data/adapters`（仅 `admin`）——它才会做 https 和只读 SQL 的校验：

```json
{
  "sources": [
    {"name": "WMS 库存", "kind": "stock", "channel": "file",
     "path": "/data/drop/wms_stock.csv", "interval_minutes": 15, "enabled": true},
    {"name": "ERP BOM", "kind": "materials", "channel": "http",
     "url": "https://erp.intra/api/lisa/bom", "token_env": "LISA_ERP_TOKEN",
     "interval_minutes": 60, "enabled": true},
    {"name": "MES 工装", "kind": "tools", "channel": "db",
     "dsn_env": "LISA_MES_DSN", "sql": "SELECT code, kind, domain, status, life_remaining FROM v_lisa_tool",
     "interval_minutes": 30, "enabled": true}
  ]
}
```

| 通道 | 要你们给什么 | 硬限制（写别的会被拒绝） |
| --- | --- | --- |
| `file` | 源系统按上面表头**定时导出**到一个共享目录，告诉我目录 + 文件名 + 导出频率 | 单文件上限 20000 行；UTF-8（BOM 可有）；缺文件/空文件记在该通道状态里，不影响别的通道 |
| `http` | 一个返回 JSON 数组（或 `{"items": [...]}`）的**内网 https** 接口 + 只读 token 的环境变量名 | 明文 `http://` 直接拒绝（`ADAPTER_URL_INSECURE`）；token 只写变量名，不写值 |
| `db` | 中间库/只读视图的连接串（放环境变量）+ 一条 `SELECT` | 非 `SELECT` 开头的语句拒绝（`ADAPTER_SQL_NOT_READONLY`）；连接串**不出现在配置文件和日志里** |

对应的 `.env`（**这些值单独交付，不要贴聊天**）：

```bash
LISA_ERP_TOKEN=只读接口token
LISA_MES_DSN=postgresql+psycopg2://lisa_ro:密码@mes-host:5432/mes_readonly
LISA_ADAPTER_POLL_SECONDS=60      # 进程内轮询秒级间隔，默认 60；测试环境自动关闭
```

不想让应用进程自己轮询，就交给 cron/systemd timer 定时跑同一套逻辑：

```bash
docker compose exec backend python -m app.management adapters          # 只跑到点的通道
docker compose exec backend python -m app.management adapters --force  # 全量拉一次
```

每次同步（含失败）都进审计链 `adapter.sync`，并把该数据种的 `DataSource` 标成 `online`/`degraded`。
读：`GET /api/system/main-data/adapters`（通道状态 + 六类数据时效）；手动触发：`POST /api/system/main-data/adapters/run`，body `{"force": true}`（仅 `admin`，页面「立即同步」按钮走的就是它）。一条通道失败只影响它自己，其余通道继续同步。

#### 导入之后齐套怎么判（这就是「真实」的部分）

- **主材/辅材**：需求 = `qty_per` × 订单数量，按 `product_code` 展开；可用 = `on_hand - allocated` 且只认 `quality_status = 合格`；不够时看 `inbound` 里 `status ≠ 延期` 且 **ETA 不晚于齐套点**的量。缺口写成「`MT-…` 缺 2.0kg（提前期 45 天）」，并给归属方（主材→采购部、辅材→仓储部）、处置动作和闭环时限（主材 36 小时、辅材 24 小时）。
- **三个检查点用的是同一条链，结论可以不同**：排产前/排产后缺料只算「缺项」；**开工前**只要缺口落在关重件要素（主材、工艺路线、人员资质、设备状态、设备能力）上就直接判**「阻断」**，该工单不允许开工。
- **工装/刀具**：路线涉及的能力域里没有「可用」工装 → 缺项（工装室，8 小时）；刀具 `life_remaining < 20`（`CUTTER_LIFE_MIN`）→ 缺项并列出编号（工具室，12 小时）。
- **人员资质**：能力域没有 `active` 且 `valid_until` 未过期的人 → 缺项（人力资源部，48 小时）；同时 **HC-10 开始真实拦截**排产结果，会指名是哪道工序缺哪个资质。
- **WIP 质量**：该工单任一工序结论为 `待判`/`不合格` → 缺项，归口质量部（16 小时）。
- **设备状态/能力**：靠 A 组产能台账 + 资源实时状态判定，不属于这六张表；能力域全部停机或在保养 → 缺项/阻断。
- **时效**：任一来源超过 24 小时没更新，数据页标「过期」提醒；要素本身没数据则判「未接入」，整单状态降级为 **`待接入`**——既不计违规，也不给「齐套」，得分按占比算（`已满足要素数 / 9 × 100`）。

**验收口径**：六张表导全后，齐套页九个要素应全部变成实心状态（灰色虚线 = 未接入），综合得分 100 才显示「齐套」；只要还有一类没导，就显示「待接入」并列具体要素名。这时你可以拿任一订单的缺口清单去和物资部/设备部对账——对不上就是你们导出的表口径问题，不是算法问题。

### 6）E1 密级等级表 → `settings.clearance`（改设置即可，不用改代码）

| 配置项 | 含义 | 取值口径 |
| --- | --- | --- |
| `levels` | 等级表，**按可读范围从小到大排列**，如 `公开 < 内部 < 秘密 < 机密` | 来自 E1 制度文件。少于 2 级、有重名、有名含空格 → 保存被拒（`CLEARANCE_LEVELS_INVALID`） |
| `data_default` | 工单**没打标**时按哪一级算 | 来自 E1。必须是 `levels` 里的一级，否则保存被拒（`CLEARANCE_DEFAULT_INVALID`）——否则这批工单会变得谁都无法判可读 |
| `enabled` | 总开关 | 关掉 = 所有账号看到全量数据。只允许在密级建模验收前的调试期使用，界面上会常驻红色告警条 |
| `report_hidden` | 是否如实上报被隐藏的条数 | 建议 `true`。关掉之后界面只剩「数据就这么点」的错觉，等于帮倒忙 |

入口有两个，同一个校验：「设置 → 安全合规 → 密级模型」（可拖动排序、增删等级、看每级有多少工单和账号），
以及 `PUT /api/system/settings`（仅系统管理员，body `{"values": {"clearance": {…}}}`）。

**生效范围**（都是 SQL 谓词级过滤，不是取回来再删）：订单列表与详情、齐套检查与齐套率、甘特与方案条目、
扰动事件与影响推演明细/依赖图、全局搜索、统计与 CSV 导出、驾驶舱全部卡片、以及 MCP 只读工具面。

**三条 fail-closed 口径**，投产前请确认这三条就是你们的制度口径：
1. 人的密级为空或不在等级表里 → 当作**最低级**处理（看得最少），不当作「无限制」。
2. 数据的密级不在等级表里 → **谁都看不到**，并在密级模型面板里列出这些「表外标签」的条数，
   提醒要么把等级加回表、要么重新打标，而不是靠关总开关绕过。
3. 等级表被改坏（直接改库绕过校验）→ 读取接口返回 **503** 而不是拿半对的表判「谁能看什么」。

派生数据的密级由来源数据推：扰动事件的密级 = 其受影响工单里的最高级（未知标签按最高算，宁可高标）。
启动时会自动重算一次存量，接口为 `POST /api/changes/relabel`（幂等，只改变了的行）。

### 7）E5 审计外部锚点 → `data/audit_anchor.jsonl`

库内那条 SHA-256 链只能证明「记录之间没被改过」，证明不了「整张表没被连根换掉」——
DBA 改表后用同一个算法重算一遍，链照样自洽。所以加了第二条**独立的、库外的**证据链：

| 项 | 说明 |
| --- | --- |
| 算法 | `HMAC-SHA256`，逐条链式（每条锚点包含上一条的锚点哈希），一条被改后面全部对不上 |
| 密钥 | 只从环境变量读，变量名默认 `LISA_ANCHOR_SECRET`（可经 `LISA_ANCHOR_SECRET_ENV` 改名）。**库里和日志里只出现变量名，永不出现值** |
| 内容 | 每条锚点记录它覆盖的 `seq_from..seq_to` 区间、该区间条数、库内链尾哈希、锚定时间、操作人 |
| 锚定 | `POST /api/audit/anchor`（权限 `audit:anchor`，默认给系统管理员与生产指挥部），或「审计页 → 锚定当前链尾」 |
| 校验 | `GET /api/audit/verify` 返回 `anchor` 段与 `tamper_evident`；`GET /api/audit/anchors` 返回最近 20 次锚定历史 |
| 无密钥 | 锚定直接拒绝（`ANCHOR_SECRET_MISSING`，HTTP 422）。**宁可没有锚点，也不写一个谁都能重算的假锚点** |

双向都能发现篡改：
- 改锚点文件里的任一字段 → 验签断在该行，返回 `broken_at: {line, seq_to}`；
- 只改库不改锚点（或反之）→ 锚点声称覆盖的 `seq` 在库里对不上 → `ANCHOR_RANGE_MISSING` / `ANCHOR_VS_DB_MISMATCH`。

**你们要做的两件事**：① `.env` 里给 `LISA_ANCHOR_SECRET`（密钥单独交付，不要贴在聊天里，也不要提交进仓库）；
② 把 `data/audit_anchor.jsonl`（在 `lisa-data` 卷上）定时拷到 LISA 写不了的落点——WORM、日志集中平台或另一台主机的只追加挂载。
拷贝周期就是「攻击者可自由操作的窗口」，建议 ≤ 一个工作日。若 E5 提供的是 TSA/日志平台而非文件，告诉我协议，我把锚点写成推送到那边。

验收 5 分钟自查（配好密钥后）：
1. 审计页 → 锚点条应显示「已锚定 1 次」，`未锚定 0 条`；
2. `curl -H "Authorization: Bearer <admin>" <host>/api/audit/verify` → `"tamper_evident": true`；
3. 手工把 `data/audit_anchor.jsonl` 第一行任一字符改掉 → 再校验 → `broken_at.line == 1`，界面变红；
4. 用 Navicat 改一条 `audit_logs.detail` 并**重算整条库内链** → 库内链 `ok: true`，但 `anchor.drift == "ANCHOR_VS_DB_MISMATCH"`——这就是那条链单独做不到的事。

### 8）E8 厂区读取范围 → `settings.plants` + `users.plants`

密级管的是「这份数据有多密」，厂区管的是「这个账号归哪块业务」。两条是**并列的两道门**，
一条放宽不等于整体放宽，所以代码里是叠加而不是替换。

| 项 | 说明 |
| --- | --- |
| 开关 | `settings.plants.enabled`，**默认 `false`**：升级当天不会把任何人看黑，等 E8 清单到位再打开 |
| 主清单 | `settings.plants.names`，在「设置 → 安全合规 → 厂区读取范围」增删排序，至少 2 个，名字不能空、不能重 |
| 未标注 | `settings.plants.data_default`：工单/设备没写厂区时按这一厂算，它必须留在清单里，否则保存被拒（`PLANT_DEFAULT_INVALID`） |
| 账号范围 | 「设置 → 用户与角色」每人一行 chip，或直接 `PUT /api/system/users/{username}/scope`（仅系统管理员）。**空 = 不受限**，不是「什么都看不到」 |
| 生效范围 | 订单列表/详情、汇总、齐套、甘特与方案、驾驶舱指标、全局搜索、CSV 导出、MCP 只读工具面——凡是从工单派生的读数都过这两道门 |
| 失败口径 | 账号声称一个清单里不存在的厂区 → 该条读数**为空**（fail-closed），不是「当作没写」 |
| 诚实计数 | 被范围挡掉的行数按厂区分布回传：`hidden_by_plant`、`plants_enabled`、`your_plants`；列表页头部会写「N 张因读取范围未显示」——**看不见不等于不存在** |
| 越权留痕 | 直接访问看不到的工单 → 403 `PLANT_DENIED`（密级不够则是 `CLEARANCE_DENIED`），两种都写审计链 |

给到 E8 之后的落地顺序（不改代码）：
1. 先在「厂区读取范围」里把主清单改成你们的真实厂名，**保持开关关闭**；
2. 逐个账号勾范围并保存，此时界面已显示每人将看到什么；
3. 打开 `enabled`，用最低权限账号登录复核一遍：列表数、驾驶舱数、导出行数都应吻合；
4. 有历史工单缺厂区标注的，先按 `data_default` 补齐或改标，再开开关。

### 9）H5 备份与恢复 → `python -m app.management backup / verify / restore`

逻辑快照（JSON.gz）而不是只有二进制：恢复要能落到**另一台机器、另一个引擎**上（SQLite ↔ PostgreSQL 同一套代码）。

| 文件 | 内容 |
| --- | --- |
| `lisa-backup-<时间>.<微秒>-<摘要8>.json.gz` | 全部表的数据 + 头部（版本、环境、引擎、行数、审计链头、脱敏后的连接串） |
| `….json.gz.sha256` | 整个文件字节的 SHA-256，`sha256sum -c` 直接可用 |
| `….json.gz.meta.json` | 只读头部，列表页不用解压就能报出这份快照的信息 |

| 命令 | 作用 |
| --- | --- |
| `python -m app.management backup [--out DIR] [--keep N]` | 生成快照，按 `LISA_BACKUP_KEEP`（默认 14）清理旧的，结果里附带当前引擎的 `pg_dump` / `sqlite3 .backup` 原生命令 |
| `python -m app.management backups` | 列出本地快照 |
| `python -m app.management verify <文件名>` | 核字节校验和、内容摘要、行数、与当前表结构的差异 |
| `python -m app.management restore <文件名> --yes` | 整库回滚：清空业务表 → 按依赖顺序写回 → 重置 PostgreSQL 序列 → 逐表核对行数 → **重算审计链**，任一步不过就整体回滚 |

拦篡改是两层的：改掉文件里任何一个字段，要么字节校验和对不上（`BACKUP_CHECKSUM_MISMATCH`），
要么连 `.sha256` 一起伪造时内容摘要对不上（`BACKUP_DIGEST_MISMATCH`）——后者算的是**表数据本身**，
重算不出来。恢复前还有一道 `BACKUP_TABLE_UNKNOWN` / `BACKUP_COLUMN_UNKNOWN`：
快照里有当前程序不认识的表或列，说明文件比程序新，拒绝用旧程序覆盖新数据。

**恢复不开放 HTTP**：整库回滚必须停服后在命令行 `--yes` 执行，界面上只给清单、立即快照和校验。
「设置 → 系统 → 备份与恢复」里能看到快照目录、保留份数、最近快照的行数与大小，点「校验」把结果写进审计链。

环境变量：`LISA_BACKUP_DIR`（快照目录，默认 `backend/data/backups`，容器里就是 `lisa-data` 卷）、
`LISA_BACKUP_KEEP`（保留份数）。Docker 部署下这些文件天然跟着 `lisa-data` 卷走。

验收 5 分钟自查（在测试机上，别在生产库上第一次试恢复）：
1. `python -m app.management backup` → 打印 `total_rows` 与 `checksum`，退出码 0；
2. `python -m app.management verify <那份文件>` → `"ok": true`；
3. 随便改一下文件末尾一个字节 → 再 verify → `BACKUP_CHECKSUM_MISMATCH`；
4. 不带 `--yes` 执行 restore → 报 `BACKUP_CONFIRM_REQUIRED`，库里一行没动；
5. 带 `--yes` 恢复 → 报 `audit_chain.ok=true`，随后新增一条工单能拿到比快照里最大值更大的 id（序列已续上）。
   这一条我在本地 PostgreSQL 上用临时库 `lisa_restore_check` 跑通过（快照 6 行 → 改动 → 恢复 6 行 → 新单 id=2），临时库用完即删。

### 10）H9 后台任务队列 → `jobs` 表 + `LISA_JOB_WORKER`

排产编排（MILP + 齐套 + 影响评估）以前压在一条 HTTP 请求里跑，网关 60 秒就 504，而且重启即丢。
现在 `POST /api/agents/run` 只做参数校验和入队，立刻返回 `202 {job, run: null}`，真正的编排由工人线程领任务跑。

| 项 | 说明 |
| --- | --- |
| 任务种类 | `agent.run`（编排场景，payload 带 `scenario / change_id / options`）、`adapter.pull`（到点拉外部数据） |
| 领任务 | `UPDATE … WHERE id=? AND status='queued'` 的 CAS 抢占，多副本同时开工人也不会把同一个 run 跑两遍 |
| 心跳 | 每 15% 进度写一次 `heartbeat_at`；工人被 kill 后 `recover_stale` 把超时任务重新排队，超过 `max_attempts` 才判死（`JOB_WORKER_LOST`） |
| 取消 | `POST /api/jobs/{id}/cancel`（权限 `jobs:cancel`）只取消**排队中**的任务；已经在算的不硬砍——砍在半路会留下半成品方案 |
| 观测 | `GET /api/jobs`、`GET /api/jobs/{id}`、`GET /api/jobs/health`（队列深度、最老排队秒数、静默工人）；智能体页有「后台任务队列」面板 |
| 密级 | 任务表带 `clearance`，列表与详情都走同一套读取范围过滤，越界 403 `CLEARANCE_DENIED` |
| 结果 | `result` 只存 run 编号、方案编号与聚合结论，**不放业务明细**——队列不是绕过密级的第二条通道 |

环境变量：`LISA_JOB_WORKER`（`0` 则该进程不起工人，只做 API；多副本时只留一个 `1`）、
`LISA_JOB_POLL_SECONDS`（默认 1.5）、`LISA_WORKER_ID`（默认 `主机名:进程号`，写进任务方便排障）。
测试环境不起线程，由 `drain()` 同步跑完，所以单测不依赖时序。
